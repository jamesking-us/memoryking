# Task-outcome benchmark: second real-agent run (2026-11-21, Claude Sonnet via the Claude Code CLI, commit 2954501)

Five arms x 10 tasks x 3 repetitions: 150 runs, 300 agent sessions (the three sessions of the isolation probe are not counted). No session timed out or exited with an error, and no run was repeated, discarded or excluded. Aggregate figures only; stream outputs, diffs and working directories were kept outside the repository. This run follows the [first run](2026-11-21-claude-sonnet-5-5.md), which stays as measured. The code under test changed in between (roadmap P4-9), so the two runs are not the same experiment.

## What was tested

- Code: commit `295450114d123edf6dc4c64cf22c8d6ed3f23bba` (the working branch head), for the harness and for every store, daemon, hook and bridge in the run. Nothing was pulled or changed during it.
- Agent: Claude Code CLI 2.1.330, `--model sonnet` (served as `claude-sonnet-5-5`), on the owner's signed-in account. Tokens are input (with cache reads and writes) plus output, both sessions summed; "computed cost" is the CLI's own figure, not a bill.
- Limits, as in the first run: 60 turns and 900 seconds per session (never reached), a new empty home directory per session, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, `--setting-sources ""`, `--strict-mcp-config`, `--disable-slash-commands`, `--permission-mode acceptEdits --permission-prompts none`, and the same least-permissive allowed-tools list in every arm: python and unittest; `Bash(memoryking:*)` in arm `on`; the five memory tools `remember`, `recall`, `save_progress`, `resume` and `hand_off` in arms `mcp` and `setup`. `fetch` was not on the list, so a `recall` followed by a `fetch` was refused in those arms. Up to 4 runs in parallel on one shared host. Two flags were added to every arm's command for audit: `--include-hook-events` (stream records of hook start and result) and `--debug-file` (so the session-end hook's completion could be read). In arm `setup` the hook settings were passed with `--settings` and the MCP configuration with `--mcp-config`.
- Order: the 140 stage-2 runs were shuffled together (arms, tasks and repetitions interleaved, fixed seed); the 10 stage-1 runs came first.
- Stages: stage 1 ran only arm `setup` (10 tasks, repetition 1) to find out whether the product works when installed as intended. Its mechanism counts are below; the mechanism worked (saving in 10 of 10 runs), so its runs were kept as repetition 1 of `setup`. Stage 2 ran repetitions 1 to 3 of `off`, `notes`, `on` and `mcp` and repetitions 2 and 3 of `setup`.
- Arm `mcp` as the current code prepares it: the server entry in `mcp.json` has no `alwaysLoad` option (only arm `setup` writes it), but the bridge's lean tools carry the per-tool `_meta` `anthropic/alwaysLoad`. All 30 `mcp` runs listed the memory tools directly in the session's tool list and none used the tool-search step. That differs from the first run, where the tools were listed by name only. The `mcp` arm still has no hooks and no start briefing.
- Isolation probe before stage 1, with hooks and MCP enabled as in arm `setup`: session 1 was told a made-up codeword and saved it (store A, three observations: the `remember` call and the two hook captures). Session 2, started with a new home directory in the same working directory but pointed at an empty separate store B (its own socket, credential and hooks), answered "unknown". The control, session 2 pointed at store A, answered with the codeword and no tool call, so the start text alone carried it into the model's context. Nothing but the store carried the codeword.
- Prompts: exactly the harness's prompt files; neutral working directories (`/tmp/mk-outcomes2/work/w<hash>`); nothing about benchmarks in prompts or environment (the wrapper passes only `PATH`, proxy and certificate settings, the arm's `MEMORYKING_*` variables and the new home).

The four knowledge tasks are `alert-sink`, `job-states` (decisions), `partner-feed` and `staging-collector` (environment facts), picked after the first run. On the other six tasks the agent does well with no memory at all (`off` 16 of 18) and the arms lie between 14 and 17 of 18.

- `setup` against `off`: 11 task-repetition pairs won by `setup`, none by `off` (p = 0.001 by run, which is too small because repetitions of a task are correlated). By task, `setup` was higher on 5 tasks and lower on none (p = 0.0625). The whole gain is on the knowledge tasks (10 of 12 against 0 of 12).
- `setup` against `notes`: 4 pairs for `setup`, 3 for `notes` (p = 1.0). A notes file did as well as MemoryKing here: `notes` 26 of 30 and 11 of 12 on the knowledge tasks, `setup` 27 of 30 and 10 of 12. The `notes` prompt tells the agent to keep notes, and 24 of 30 `notes` runs did.
- `setup` against `on`: 4 pairs for `setup`, 2 for `on` (p = 0.6875), not distinguishable. `setup` against `mcp`: 14 for `setup`, 1 for `mcp` (p = 0.001 by run, 0.031 by task). `notes` against `off`: 12 against 2 (p = 0.013 by run, 0.375 by task). Nothing is corrected for the ten comparisons.
- Cost: `setup` used about 109,000 more tokens per run than `off` and about 55,000 more than `notes` (the start briefing of about 5,000 characters in both sessions, the tools in the prompt, and the extra turns), and was slower on average, with timings that are noisy on a shared host. Nothing here shows a saving in tokens or time.
- Memory use: in `setup` all 30 runs saved in session 1 (the session-end hook captures every session) and all read in session 2 (the start hook); 21 of 30 also saved by an explicit `remember` call (never on `cache-lock`, `ledger-match` or `wrong-total`). In `on`, 28 of 30 saved and 28 of 30 read. In `mcp`, 23 of 30 saved with `remember` and 27 of 30 called `recall` in session 2. Notes left on disk: `notes` 24 of 30, `off` 2 of 30.

## Why the `mcp` arm failed, and other failures worth knowing

- `mcp` (0 of 12 on the knowledge tasks although 23 of 30 runs saved): the model could not read what `recall` returned. The bridge answers a lean `recall` with the briefing as the text block and the receipt, status and sources as `structuredContent`. Called directly the bridge returns the briefing text, but in this CLI version the model is shown only the `structuredContent` JSON and the text block is dropped; the transcripts show agents reporting "a single source with no readable content". The same happens to `remember`'s one-line reply. In the `setup` arm the defect is hidden, because the start hook prints the briefing itself. The `fetch` call the agents then tried was refused because this run's allowed-tools list did not include it, a limit of the driver that does not explain the dropped text.
- `on` (CLI): the host denied some `capture` commands (six, each with a parenthesis in the quoted text as far as the transcripts show). In `alert-sink` repetition 2 the only save was denied, session 2 recalled "no relevant memory" and the agent sent mail; `config-aliases` repetition 1 never recalled in session 2. These are agent and host-permission effects on the CLI route, not store failures.
- `staging-collector` (failed in 2 of 3 `setup` runs, 2 of 3 `on` runs and 1 of 3 `notes` runs) and `config-aliases` `setup` repetition 2: the carried facts were in the start text and the agent used them, but the hidden check wants the payload passed to `post` as a dict (the agent passed a JSON string), batches of 50 through `chunks` (one `on` run sent 120 in one call), or the old `describe()` output kept. The memory worked; the agent made a design choice the check does not accept.

## Limits

Ten synthetic tasks, one model, one agent host and version, and one machine with four runs in parallel; three repetitions, which add pairs but not independent tasks; the knowledge-task split was made after seeing the first run; the allowed-tools list excluded `fetch`; and the hooks and briefing are the intended installation for Claude Code only. Ten tasks can show only a large effect. This is not evidence of real-task quality, of production performance or of any saving in tokens or time.

## Follow-up check after the reply-shape fix (4 runs; confirms the mechanism, not an effect size)

Roadmap P4-9 changed the lean MCP reply shape after the run above: a lean reply is now its text block alone, with no `structuredContent`, and a `recall` or `resume` is the Markdown briefing followed by one trailer line. This check asks one question: does the briefing now reach the model in the host that dropped it? It is 4 runs, so it cannot say how large any effect is.

- What ran: arm `mcp` only, the four knowledge tasks (`alert-sink`, `job-states`, `partner-feed`, `staging-collector`), repetition 1, the same wrapper, flags, isolation, limits and parallelism as above (Claude Code CLI 2.1.330, `--model sonnet`, new empty home per session, 60 turns and 900 seconds per session, four runs in parallel), except that `mcp__memoryking__fetch` was added to the allowed-tools list. Code: commit `f249efb7a5bded582dcb4bf367d4cd4fab049dff` for the harness and the bridge. No run was repeated, discarded or excluded; no usage limit was reported. 8 agent sessions, plus 1 session for a separate permission probe (below): 9 of the 12 allowed. No isolation probe was repeated, because the wrapper and the arm are the ones already probed above.
- How it was read: from each session's stream, the result the host handed the model for each memory-tool call (its content blocks and whether the result carried `structuredContent`), and the hidden check.

4 of 4 passed against 0 of 12 for the same arm and tasks in the run above. In all four, the model received the briefing as the text block of a result with no `structuredContent`, every memory-tool result in these 8 sessions was text only, and no session used `fetch` or `resume`. This confirms that the dropped-briefing mechanism is fixed for this host and version. The earlier 0 of 12 had that one cause, the 4 of 4 is consistent with it, and nothing more should be read from four runs: the tasks, the model and the host are the same single choice as above, and there is no comparison arm in this check.

Permission probe (1 session, not a benchmark run): a session was asked to run three `memoryking capture` forms under the allowed-tools entry `Bash(memoryking:*)`, with text that contains braces, quotes and parentheses. The host refused the heredoc form ("Contains brace with quote character"), accepted `capture --file` after the text had been written with the file tool, and accepted a quoted `--text` containing parentheses only. That is why the note for command-line agents now shows the file form first (`capture --file FILE`, with standard input as the alternative). It is one session of one host version.
