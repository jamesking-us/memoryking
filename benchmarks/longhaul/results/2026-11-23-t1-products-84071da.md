# Long-history benchmark: track T1 beside other memory products on the current code (2026-11-23, Claude Sonnet via the Claude Code CLI, commit 84071da)

Track T1 (needle at scale) on a fresh seed, 16, at history sizes 200 and 2,000: 12 tasks at each size, five arms, one repetition: **120 real agent sessions, no probes, no re-runs, none excluded.** Aggregates only; event streams, stores and working directories stayed outside the repository.

**What this is.** The first-stage comparison ([seed 11](2026-11-22-s0-s1-a7c08d0.md)) was made with MemoryKing code that has since changed (roadmap P2-11, P2-12, P2-13); the other products had not been run beside the new code. This run does that, with one agent, one model, one repetition and 12 tasks per size. A pass is a hidden check passed by one agent on a small synthetic fixture, not evidence of real-task quality, and a seeded history is not a lived one. With 12 tasks and four comparisons, 7 wins against none is the least that passes after Holm correction (p = 0.0156 raw, 0.0625 corrected: it takes 8 against none, p = 0.0078 and 0.031); 6 against none gives 0.031 raw and 0.125 corrected. Read the tables as what this design can show, not as a ranking of products.

**Two labels used throughout.** `mcp_memory`, `basic_memory` and `mcp_memory_service` are **written in full**: every seeded session was written into the product through its own write tool (`--allow-unfaithful-seeding` for the last two, because their own hooks would have stored little or nothing from sessions of a few turns). That is generous to those products and is not what a real session would have given them. `memoryking` is **as captured**: seeded through the hook events a real session fires, from the same transcripts, which is what a real session gives it.

## Design, fixed before the first session

- Five arms x 12 tasks x 2 sizes x 1 repetition = 120 sessions, the whole approved budget. Size 200 is two groups of six tasks, size 2,000 one group of twelve, seeded once per arm and group; every run works on a copy of its store.
- Seed 16 had never been generated or read before this run (seeds 11 to 15 were not used).
- **Analysis, fixed before the run.**
  - *Primary, success:* `memoryking` against each of the four other arms, exact two-sided sign test paired by task and pooled over the two sizes as the earlier records pool (a task's outcome is its pass rate over the two sizes; ties dropped), Holm-corrected over four. Per-size tables with Wilson 95% intervals; the 24 (task, size) pairs as a secondary.
  - *Primary, cost:* input tokens per session (uncached input plus cache reads plus cache writes, the same in every arm), `memoryking` against each of the four, exact two-sided Wilcoxon signed-rank test paired by (task, size) (24 pairs; zero differences dropped, ties given average ranks), Holm-corrected over four; the median paired difference (`memoryking` minus the other) and its sign are reported. Agent seconds: the same test, secondary (the machine was shared).
  - *Without a test:* passes per 100,000 input tokens per arm, seed cost per arm and size, memory characters in the context. Descriptive only: these numbers beside the first stage (seed 11) at 200 and 2,000 sessions for the arms both runs have.
  - For `memoryking`: prompt-hook carry, `recall` calls and the parameters used, and failure classes (never surfaced, surfaced but not used, wrong value used, task error) with the corrected needle matching (the generator's own sentences that state a slot's current value, compared on letters and digits, as `hookprobe` defines them). The other products' failures are classified the same way.
  - Whatever it shows is reported, including where MemoryKing loses or ties. No comparison was added after seeing data; anything else is labelled exploratory.
- Limits fixed: at most 120 sessions, model `sonnet` only (no Haiku or other model call anywhere), up to four in parallel, the same agent flags, allowed tools, isolation and scope sentence as the earlier runs, a shuffled order (fixed seed) across tasks, arms and sizes, a restartable driver with a durable ledger so that no session is started twice, a usage-limit refusal waited out for up to two hours. A session that failed for a harness reason would be recorded and excluded with the reason, never run again.

## Failures, classified

Every failed run was classified from its event stream with the rule of the earlier records: **never surfaced** (the needle sentence of a failing slot is in no hook output or tool result the model was shown), **surfaced but not used** (shown, and the code used no value for the slot), **wrong value used** (shown, and another value was chosen), **task error unrelated to memory**. A run with any slot never surfaced counts as never surfaced. As a check of the matching, on the 150 slots of the passed runs the needle sentence was found in the shown text for 146 (`basic_memory` 33 of 34, `mcp_memory_service` 9 of 12, every slot of the other three), so it works on each product's output format; a few passes are guesses or paraphrases.

| Arm | Failed | never surfaced | surfaced, not used | wrong value used | task error |
| --- | ---: | ---: | ---: | ---: | ---: |
| `memoryking` | 6 | 2 | 3 | 1 | 0 |
| `mcp_memory` (written in full) | 11 | 11 | 0 | 0 | 0 |
| `basic_memory` (written in full) | 7 | 7 | 0 | 0 | 0 |
| `mcp_memory_service` (written in full) | 18 | 18 | 0 | 0 | 0 |
| `log` | 3 | 3 | 0 | 0 | 0 |

- **`memoryking`: all six failures are at 2,000 sessions** (none at 200). Never surfaced (2): rate-limit (the limit's sentence was in no result; the agent called `recall` twice, set a placeholder of 10 and said so) and retention (the archive folder never surfaced; the agent implemented the days and left the folder undone). Surfaced, not used (3): id-format, money-rounding and port-config, where every needle was in a result among records about the same attribute of other components or earlier values and the agent said the records contradicted each other and wrote no value (in port-config it did implement the function, with a prefix it judged better supported than the needle's, so the check saw neither value). Wrong value used (1): export-delimiter, the header label, where the agent used `ref` and called it a placeholder.
- **The other products**: every failure is never surfaced. The agents searched the product's own tools (a mean of 6.2 memory-tool calls a run for `mcp_memory`, 5.7 for `basic_memory`, 1.1 for `mcp_memory_service`, of which 13 of 24 runs made none and relied on the start hook) and the needle sentence was not in what they were shown. ## Limits of this run

One agent, one model, one CLI, one repetition, 12 tasks per size, one seed: the results are one draw. Seeded histories, not lived ones; the three other products are seeded by writing every session in full, which is generous to them, and `memoryking` is seeded as captured, so the groups answer different questions and an advantage for either is bounded by that. A pass is one hidden check on a small fixture. The machine was shared, so seconds and seed times are noisy. Comparisons with seed 11 (older code) and seed 15 are across different histories and are descriptive. Each other product is installed with its default settings and exposed as its documentation says for a Claude Code user, without tuning its prompt or search for this task: a differently configured product, or an agent told how to search it, could do better. Not run: the products that need a model other than Sonnet (claude-mem, Mem0, Graphiti), sizes other than 200 and 2,000, and tracks T2 to T5 (corrections, deletion, scopes, hostile text, question answering, lived sessions), so nothing here says how any product handles those. MemoryKing at 2,000 sessions passed half its tasks, below the raw transcripts searched by the agent (6 of 12 against 10), and at that size the agents' own `recall` results carried more needles (19 of 24) than the prompt hook's injection (14 of 24).
