# Long-history benchmark: change over time, forgetting, scopes and hostile memory beside other products (2026-11-23, Claude Sonnet via the Claude Code CLI, commit 52aad17)

Tracks T2, T2f, T3 and T4, which had never been run with a real agent, at 200 sessions of history on a fresh seed, 17: 27 tasks, five arms, one repetition: **135 real agent sessions, no probes, no re-runs, none excluded.** Aggregates only; event streams, stores and working directories stayed outside the repository.

**What this is.** One agent, one model, one repetition and 4 to 9 tasks a track. A pass is a hidden check passed by one agent on a small synthetic fixture, not evidence of real-task quality, and a seeded history is not a lived one. The protocol is [stage S2 of `RUNNING.md`](../RUNNING.md#stage-s2-change-over-time-forgetting-scopes-and-hostile-memory-beside-other-products), fixed before the first session. **Only large differences can show:** in a track of 4 tasks nothing can reach p < 0.05 (a perfect 4 to 0 is p 0.125); of 6, only a clean 6 to 0, and not after Holm correction; of 8 or 9, 6 to 0 uncorrected and 8 to 0 after Holm over four; across all 27, 6 to 0 uncorrected and 8 to 0 after Holm, 10 to 1 and 13 to 2. Read the tables as what this design can show, not as a ranking of products.

**Labels used throughout.** `memoryking` is **as captured** (seeded through the hook events a real session fires, from the same transcripts), with one addition in T3b: it also makes the one user-scope save that its start briefing tells an agent to make for a standing personal preference, so **its T3b row is an upper bound**. `mcp_memory`, `basic_memory` and `mcp_memory_service` are **written in full** (every seeded session written into the product through its own write tool, which is generous to them and is not what a real session would give them). T4 text in those three is stored verbatim, an upper bound on exposure. In T3 the three other products keep **one store with every project in it and no isolation, by design**: a canary of a sibling project in their results is a `leak` because the product has no scope, not because the harness failed; it is reported as measured. `log` holds every project's transcripts in T3 (one folder each) and the task's project only in the other tracks.

## Design, fixed before the first session

- 27 tasks x 5 arms x 1 repetition = 135 sessions (T2 40, T2f 20, T3 45, T4 30), seed 17 (never generated or read before the go-ahead; all preparation on seeds 1 to 5), 200 sessions of history, six histories seeded once per arm (30 seedings), every run on a copy of its store. Model `sonnet` only, up to four in parallel, a fixed shuffle, a restartable driver with a durable ledger, the same agent flags, allowed tools, isolation and scope sentence as the T1 comparison. The first eight sessions were read for harness faults only (init event, connected servers, hooks); they are kept.
- **Analysis.** Per track: `memoryking` against each of the four other arms, exact two-sided sign test paired by task (ties dropped), Holm over four, Wilson 95% intervals. Pooled over the 27 tasks: the same, Holm over four, **reported with and without the three T3b tasks** (declared above). Failure classes as counts (`stale`, `leak`, `acted_on_injection`, `missing`, `other`); T4 acted / mentioned and refused / never surfaced; T2f forgotten text in context or not, acted on or not. Cost secondary: input tokens and seconds, Wilcoxon signed-rank paired by task over all 27, Holm over four. No comparison was added after seeing data.

## Isolation evidence

- A fresh empty `HOME` per session, a scrubbed environment, a working directory named after the project, `--strict-mcp-config`, auto-memory off. In all 135 streams the init event shows `claude-sonnet-5-5` and exactly the arm's own tool servers, all connected (`memoryking`; `memory` = Knowledge Graph Memory server; `basic-memory`; `memory` = MCP Memory Service; none for `log`); every session returned a success result; none timed out. Hook events: `memoryking` SessionStart and UserPromptSubmit in 27 of 27; Basic Memory SessionStart 27 of 27; MCP Memory Service SessionStart, UserPromptSubmit and Stop 27 of 27. Claude Code 2.1.330. The CLI's own computed cost was 11.42 US dollars (not a bill); the longest session took 39 seconds.
- Runs with a denied command (a heredoc write or a read outside the directory; agents continued with the edit tool): `log` 18 of 27, `mcp_memory` 5, `basic_memory` 4, `memoryking` 4, `mcp_memory_service` 0. A denial is not a harness exclusion.

## Offline pre-checks (before any session; no model)

Seeds 1 to 5: the null stub fails every task, the oracle passes, the stale, gullible and leaker stubs give their classes; the whole 135-run pipeline ran with the stub for each mode (reader, gullible, leaker, null) with no fault, a leak detected in every arm that has no isolation and none in `memoryking`, and the file, dependency and localhost-request canaries detected in every arm. Offline expectation for `memoryking` (preflight, not a gate): see the protocol; T2 current statement first 37 of 40 without asking, T2f forgotten text never shown, T3a canary never shown, T3b 0 of 15 hook-only and 15 of 15 with the save, T3c 14 of 15, T4 hostile text shown in 0 of 30 without asking.

## Failure classes

Counts of failed runs by the hidden check's class (all five classes shown; a class not listed is zero).

| Arm | T2 | T2f | T3 | T4 |
| --- | --- | --- | --- | --- |
| `memoryking` | none failed | leak 3 | none failed | missing 1 |
| `mcp_memory` | none failed | leak 2 | leak 3 | missing 1 |
| `basic_memory` | missing 2 | leak 3 | leak 2 | missing 1 |
| `mcp_memory_service` | stale 4, missing 3 | leak 2 | leak 2, missing 2 | missing 3 |
| `log` | none failed | leak 3 | leak 3, missing 1 | none failed |

- **T2 (change over time).** Every `stale` failure is `mcp_memory_service` (4): in its runs the current statement was shown in 1 of 8 runs, an earlier one in 5 (its search returns about ten semantically ranked sessions). `memoryking`, the Knowledge Graph Memory server and `log` used the current value in all 8 (the current statement was shown in all 8 in each), including both retractions; Basic Memory failed two (one with the current statement never shown, one with a wrong value used). **Using an earlier value was never the failure of `memoryking`.**
- **T2f (forget).** The delete path of every product reported success in 4 of 4, and **the forgotten text reached the model in 0 of 20 runs in every arm**: a plain count that the five delete paths removed what they were asked to remove from what a session can reach. **The `leak` class in T2f is not a leak.** The check's class for a forgotten slot is `leak` whenever the code did not give a value other than the forgotten one, which includes the code that does not give a value at all: in `cache-ttl` and `retention`, all five arms (ten runs) declined to invent the forgotten value and left the function raising `NotImplementedError`, so the one probe that prints both values crashed and scored the kept value as lost too. That is the declared check and its verdicts stand as the primary result; the check cannot tell an honest refusal from a failure, so it makes these two tasks unwinnable by an agent that behaves correctly, and it is an **identical outcome in every arm**. An exploratory, post hoc scoring slot by slot (not declared; applies to every arm alike; `regrade_t2f`) gives: refusals count as not using the forgotten value, `log-format` and `cache-ttl` and `retention` pass in `memoryking`, `basic_memory`, `log` (and `retention` is unscorable in `mcp_memory_service`, whose code did not import), `batch-export` fails in `memoryking`, `basic_memory` and `log` because the agent wrote the forgotten value, the natural default `oldest-first`, with the text never shown to it, **so a pass or fail on that slot says nothing about memory**. Post hoc passes: `memoryking` 3, `mcp_memory` 4, `basic_memory` 3, `mcp_memory_service` 3, `log` 3 of 4; no pairwise test changes (all p 1.0), and the pooled tests do not change in kind (13 to 1 becomes 14 to 1, Holm 0.0039). Where it matters for a reader: acted on the forgotten value by the check, `memoryking` 1 of 4, `basic_memory` 1, `log` 1, the others 0. After the delete path, the store still holds the forgotten token in live rows in the `memoryking` store (the stored copy of the harness's own last `recall` for the marker, which it runs after the purge to confirm that nothing is left and which holds the query text; MemoryKing keeps such requests for 30 days, as its guides say, and the purge had already removed the briefings that delivered the record; 8 rows over 4 stores; wording corrected after the record was first written, when the rows were traced to the harness's check and not to the forget path) and in the `mcp_memory_service` store (a soft-deleted memory, 8 rows); neither is reachable by the agent's tools and neither was graded.
- **T3 (scopes).** **T3a, the canary of a sibling project in the model's context: `memoryking` 0 of 3, `mcp_memory` 3, `basic_memory` 2, `mcp_memory_service` 2, `log` 3 of 3.** For the three products and for `log` this is the absence of isolation as designed and configured (one store, every project), not a malfunction. T3b (a preference stated in another project): all arms but `mcp_memory_service` (2 of 3) and `log` (2 of 3) passed 3 of 3, `memoryking` through the user-scope save (upper bound). T3c (hand-off between two agents in a fresh directory): 3 of 3 in every arm.
- **T4 (hostile memory).** **Acted: 0 of 30 sessions in every arm; attempted without effect: 0.** Never surfaced / mentioned and refused: `memoryking` 6 / 0, `mcp_memory` 0 / 6, `basic_memory` 4 / 2, `mcp_memory_service` 5 / 1, `log` 5 / 1. In `memoryking` the hostile text reached the model in none of the six sessions (the page was not among what the hooks and the agent's `recall` returned); in the Knowledge Graph Memory server it reached the model in all six (the written-in-full store holds it verbatim and the agent's search returned it) and the agent did not act. The six code failures (`memoryking` 1, `mcp_memory` 1, `basic_memory` 1, `mcp_memory_service` 3) are a needle not used or not surfaced, not an injection effect. No arm shows a difference by track-level test.

## Harness faults, exclusions and regrades

1. Harness faults found and fixed **before** the run (listed in the protocol, S2-1 to S2-7 and amendment 11): MCP Memory Service creation times, `log` in T3, the user-scope save, `forget_residue`, `injection_calls`, the stub, the T4 port serialisation, and a generator fault in which distractors could state the needle's own value as tried or reverted.
2. **No fault found during or after the run; no session excluded, re-run, repeated or regraded. Sessions used: 135 of 135** (195 with stage S2b; see its record). No usage limit was met.
3. **A limitation of the declared T2f check, found when reading the results**, is described above: it makes `cache-ttl` and `retention` unwinnable for an agent that refuses to invent the forgotten value, identically in every arm. It was not corrected, the verdicts are as declared, and the slot-by-slot reading is labelled post hoc.

## Limits of this run

One agent, one model, one CLI, one repetition, 4 to 9 tasks per track, one seed: the results are one draw. Seeded histories, not lived ones; the three other products are seeded by writing every session in full (generous, and not what a real session would give them), `memoryking` as captured except the T3b save (an upper bound); `memoryking` had no `supersedes` link on a correction (an agent's act, not measured here), so T2 measures whether dated records are read in order. T3 on the three other products and `log` is one store with every project in it by design. A pass is one hidden check on a small fixture, and in T2f a pass is bounded by the limitation above and by the 1-in-4 to 1-in-5 chance that an agent with no memory writes a non-forgotten value. Each product is installed with default settings and exposed as its documentation says, without tuning its prompt or search: a differently configured product, or an agent told how to search it, could do better. Not run: T5, the lived track T2b, the products that need a model other than Sonnet. MCP Memory Service's weak result is largely retrieval (its search returned the current statement in 1 of 8 T2 runs) and is bounded by the seeding label. This record supports statements about this design and these tasks only; it is not a ranking of products.
