# Long-history benchmark: stage S0 pilot (2026-11-22, Claude Sonnet via the Claude Code CLI, commit ef3c4f0)

Track T1, history size 200, the 6 tasks of group 0, 9 arms, one repetition: 54 measured sessions, plus 13 probe sessions and 3 re-runs, 70 real agent sessions in all (the approved ceiling). Aggregates only; event streams, stores and working directories stayed outside the repository.

**What this is.** A check of the harness. Six tasks at one size cannot rank products: with 6 tasks, the smallest result that reaches p < 0.05 between two arms is 6 wins against none, and nothing below comes near it. The pilot did what it is for: it found five faults in the harness (two of them in the hidden checks, two that disadvantaged named products) and measured what the full run will cost. A pass is one run of one agent on a small synthetic fixture, not evidence of real-task quality.

## Isolation evidence

- A fresh empty `HOME` per session; scrubbed environment (no `memoryking` command on `PATH`); the working directory holds only the task repository and the arm's own files; `--strict-mcp-config`; auto-memory off except in `native`. In all 54 streams the init event shows the same model and CLI, `acceptEdits`, and exactly the arm's own tool servers: none in `off`, `notes`, `log` and `native`; `memoryking`, `memory`, `basic-memory`, `memory` (MCP Memory Service) and `mcp-search` (claude-mem) in the others, all connected.
- `off` probe: a codeword planted in a seeded history was not found (answer UNKNOWN, no memory tool in the tool list, no hook event). The six measured `off` runs scored 0 of 6, with no memory content in the context. Nothing but the arm's own mechanism carries history.
- `native` probe: the codeword was answered with no tool call and no file read, so the host loads the seeded `CLAUDE.md` in headless mode with `--setting-sources user,project` (the open point in RUNNING.md is settled).
- Hook output reaches the model: in the `memoryking` probe the start hook's briefing was in the context and the codeword was answered with no tool call.
- 12 of the 54 sessions had one denied Bash command (a heredoc or a command writing outside the directory), spread over all arms; the agent then used its edit tool. It does not favour an arm.

Two reading notes. First, three of the failures share one needle: the export header, stated only in an assistant turn as "the integration notes say ... Order#". Where it surfaced (`notes`, `mcp_memory`) the agent treated it as unsettled and said so; the three arms that passed that task used it. That is a property of the task's needle wording as much as of a product. Second, no failed run was a task error unrelated to memory, and no run timed out.

### MemoryKing's two failures: cause and the product change each suggests

Both were retrieval misses with one broad `recall`. Offline, on a copy of the seeded store with the same queries and no model: the broad query for the header returned 8 items without the sentence; a query naming the attribute ("orders export header column label") returned it, and so did "record identifiers zero-padded digit count" for the width. Three properties of the briefing showed in these runs:

1. The briefing is capped at 8 items whatever the budget (3,300 characters of a 6,000-token budget were used), and about half of them are the same session twice: the user-turn capture and the session capture of the same text. Collapsing captures of one session into one item would roughly double the distinct facts returned.
2. Items are ranked by overlap with the subject words (`orders export`), so distractors about the same subject fill the list. Accepting a `limit` argument, or filling the budget, would let one query cover several attributes.
3. The start briefing is the newest sessions of the project (it showed an unrelated "typing hints" session), not what the task asks about. A prompt-time hook that recalls for the user's prompt (MCP Memory Service has one) would put the right items in front of the agent before it chooses a query.

## Where a competitor did better than MemoryKing

- Files that hold the whole history: `native` (6 of 6), `notes` and `log` (5 each) passed more than `memoryking` (4). At 200 sessions the extractive notes (14,000 characters) and the transcripts fit in the context or are cheap to read, so retrieval is complete; that is the size where a notes file is at its best, and the 2,000-session stage is where it should stop being so.
- `mcp_memory` (5): its search returns every matching session whole (26,800 characters of memory per run against MemoryKing's 6,500), so the width sentence reached the agent in `t1-id-format` where MemoryKing's 8 items did not. It paid for it in tokens (163,000 against 119,000 per session) and seconds (16 against 10). It also dumped its whole graph once (156,000 characters, refused by the host as too large).
- MemoryKing was the cheapest memory arm: 119,000 input tokens and 10.3 seconds per session, close to `off` (96,000, 9.9 seconds), against 150,000 to 180,000 and 15 to 26 seconds for the other products.

## Harness faults and fixes

Each fix has a test and is a separate commit from this file. Hash prefixes are of the working branch.

1. **Two hidden checks failed code that followed the history** (`f1b3450`). `id-format` required a hyphen between prefix and digits that no fact states, and `export-delimiter` read the file as UTF-8 although the history settles UTF-16 for the orders export. The checks now read any one separator or none, UTF-16 with or without a byte order mark, and quoted fields. Found by reading the failed runs of the file arms, which had the right values. The agent's file changes were replayed from each stream onto the task repository (no model): the replay under the old check reproduces all 54 as-run verdicts, and under the corrected check 9 runs change from fail to pass (`id-format`: `notes`, `log`, `native`, `mcp_memory`, `basic_memory`, `mcp_memory_service`; `export-delimiter`: `log`, `native`, `basic_memory`). These 9 are listed as excluded from the as-run column and counted as regraded. They were not re-run: 9 sessions plus the other re-runs would pass the ceiling of 70, and a replay of the same code is the more faithful correction. This is a deviation from the protocol's "run each faulted run once more", and it is stated here and nowhere softer.
2. **The `native` arm's `CLAUDE.md` was not counted as memory in the context** (`4f8f15e`, before the runs): the host loads it before the first turn, so the stream shows no event for it and the column read 0.
3. **No raw copy of a run survived** (`1e429f3`): the run directory was removed after the run, which left a failure analysis with a summary only. `run` now keeps the stream and the final code under `<results>/raw/`, never committed. The streams for this pilot were saved by the run script I wrote for this pilot.
4. **`--no-session-persistence` disabled the session-end capture** (`d1670ef`). With it, the host writes no transcript, which is what MemoryKing's session-end hook reads (and which other products' session-end hooks may read): the first `memoryking` probe left the store unchanged, and every measured run showed 0 observations added. With the flag removed, the second probe stored both captures. This affects only the "written" measure, not any T1 outcome: a T1 run is one session with no later reader. The 54 measured runs ran with the flag, so their hook writes are not measured; fresh homes are removed after each run, so nothing is resumed either way.
5. **The working directory was called `work`** (`4d10915`). claude-mem and MCP Memory Service take the project from the directory name, so their start hooks searched a project with no history: claude-mem answered "This project has no memory yet" in the 6 measured runs, and MCP Memory Service's hook found 0 tagged memories. The directory is now `<run>/ws/<project>`. Verified by probes (both hooks then injected the seeded history) and by the 3 `claude_mem` runs above. The 6 `mcp_memory_service` runs and the other 3 `claude_mem` runs were not re-run (ceiling); they remain as-run results, marked †.

Also: the seeded stores carry a digest that includes the hidden checks, so fix 1 made `run` refuse them. After confirming that the regenerated history is identical to the generated one, I rewrote the digest in each seed record (the old value is kept in the record). A script of mine mistook the digits in a result line for a rate-limit message and set two completed results aside for a retry; I stopped the script before the retry started and restored both results, so no extra session ran. No usage limit was met in the whole pilot.

## Exclusions

- 9 as-run verdicts replaced by the regraded ones (fix 1): the runs listed in fault 1.
- 12 runs marked † (fix 5): kept as data, and not a measure of those products' start hooks. The 3 `claude_mem` re-runs are reported apart.
- Nothing was dropped, repeated to obtain a pass, or timed out.

## What the full run needs changed

1. **Audit every family's hidden check against the other attributes of its subject.** Each family's history also settles other attributes (encoding, separator, jitter, tax handling, bind address) that a careful agent follows, and a check that reads them wrongly fails the careful agent. This pilot's 6 tasks had 2 such faults. Add an offline step to `validate`: build, for each task, code that follows every attribute the history states for the subject, and require the check to pass it. Do this before S1, and re-seed or re-digest after any change (the digest should cover the history and the tasks separately).
2. **Decide the needle wording.** Needles stated as an assistant's report of someone else's document ("the integration notes say ...", "found in the upstream spec") are doubted by the agent when it also sees stronger-looking statements. `export-delimiter` was passed by 3 of 8 memory arms, the lowest of the six tasks. Either state every needle as a user decision or keep the variants and report them as a separate class. The protocol cannot change after results, so this is for the owner to decide now.
3. **`claude_mem` is structurally disadvantaged by seeded transcripts.** Its observations come from tool events, and a seeded session has one tool turn of diff text; the facts are user and assistant statements, which it keeps as prompts and summaries that its search view did not show. 6 of 6 failed, and a re-run with its start hook working still failed. Report it as measured with seeded history, and let the lived track (T2b) carry its fair test. Its seeding cost is real (7.5 minutes per 200 sessions, about 1,940 observer calls at 2,000 sessions); S1's three sizes would use about 2,400 of the 2,500-call cap with the per-run calls, so raise the cap or drop the 2,000-session seeding for it.
4. **The two plugin products need their re-runs** (6 `mcp_memory_service` and 3 more `claude_mem` runs, 9 sessions) before S1 starts; the pilot's rule is that its runs are kept as data and repeated only for a harness fault, and fix 5 is one.
5. **Timing is not a constraint.** The 54 sessions took about 4 minutes of wall time at 4 in parallel (9 to 26 seconds each). Seeding dominates: 2 minutes for Basic Memory and 7.5 minutes for claude-mem at 200 sessions, about 10 times that at 2,000 (extrapolated, not measured).
6. **Tools behind the host's search step.** MemoryKing's tools are always loaded; the other products' tools were not (their documented configuration leaves them behind tool search, which costs a turn, and which they all used). That is each product as installed, and it should be said beside every table.
7. **The "memory written" measure is empty in T1**: in a one-session task no agent called a write tool. It is meaningful only after fix 4, in the lived track.
8. **`--permission-mode acceptEdits` denies some Bash heredocs** (12 of 54 sessions, all arms); the agent recovers with its edit tool. If the denials are to be removed, add the edit tools to the allowed list for every arm.

Limits of this pilot: one repetition, 6 tasks, one size, one model, one agent host and version, one shared machine; two hidden-check faults found after the runs and corrected by replay; two products' start hooks disabled by the harness for their measured runs; Mem0 and Graphiti not run.

**Added after the pilot.** Two statements above were corrected by the work that followed, and the original text is left as written: the explanation of the `claude_mem` failures (the statements did reach the plugin, which stored every prompt verbatim; its seeding fired two summaries a session and sent failures as successes, and its search listing put observations written from diff comments first; see `SYSTEMS.md`, "Seeding fidelity"), and the count of hidden-check faults (29 of the 39 tasks had a check that rejected at least one conforming implementation; see `RUNNING.md`, "Protocol amendments after the pilot").
