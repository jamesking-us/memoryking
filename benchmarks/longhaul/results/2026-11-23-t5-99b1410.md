# Long-history benchmark: question answering on LongMemEval `_s` beside other memory products (2026-11-23, Claude Sonnet via the Claude Code CLI, commit 99b1410)

Track T5: 60 questions stratified by type from `longmemeval_s_cleaned.json` (SHA-256 `d6f21ea9d60a0d56f34a05b609c79c88a451d2ae03597821ea3d5a9678c3a442`, draw seed 20), five arms, one reader call and one judge call per question per arm: **600 model calls (300 reader, 300 judge), none repeated, none lost, none excluded, no harness fault.** Aggregates only; nothing from the dataset beyond question ids and scores is kept here, and streams, stores and answers stayed outside the repository.

**What this is, and is not.** Each system ingests a question's haystack (about 46 to 50 sessions, about 500,000 characters) into an empty instance, returns a retrieved context for the question under one budget, a fixed reader answers from that context alone, and a fixed judge grades. **The retrieval function of each arm is the harness's construction of "what this system returns for a question"** (`context_for` of each adapter: no query is written by hand and no model retrieves); it is not an agent searching with several queries, so this says nothing about the products used as their documentation tells a Claude Code user. It is comparable in kind, not in number, to what other products publish (a different subset, reader, judge and budget). The protocol is [stage T5 of `RUNNING.md`](../RUNNING.md#stage-t5-question-answering-on-longmemeval-s-beside-other-products), fixed before the first call.

## Design (fixed before the first call)

- 60 questions, stratified by type, draw seed 20 (not made, printed or scored before the go-ahead; every earlier check used draws 1 to 5); one context budget for every arm, **12,000 characters** (about 3,000 tokens at four characters a token); reader and judge `claude -p --model sonnet --no-session-persistence --setting-sources '' --disable-slash-commands --tools ''` in an empty directory with a fresh `HOME`, the prompts of `benchmarks/longhaul/prompts/`; every call announced in a durable ledger first. Arms in the order `basic_memory`, `mcp_memory_service`, `memoryking`, `mcp_memory`, `log`, four at a time. **`log` instead of `notes`**: with only a haystack `notes` would hand over the newest part of one capped file, no retrieval at all.
- How each was fed: `memoryking` every chat turn as one observation (`role: text`) at its session's date, retrieval a `recall` briefing for the question; the Knowledge Graph Memory server one entity per session with every turn whole as an observation, retrieval a search for each content word of the question with entities ranked by the distinct words they matched; Basic Memory one note per session with every turn whole, `reindex`, retrieval `bm_search` (ten results); MCP Memory Service `memory_store_session` with every turn whole and the sessions' own dates, retrieval `memory_search` under the project tag; `log` the raw turns, retrieval by ranked shared words.
- **Analysis, fixed in advance.** Accuracy per arm with Wilson 95% intervals, overall and by question type; `memoryking` against each other arm by exact two-sided McNemar paired by question, Holm over four; evidence recall (whether the text of an answer-bearing turn of the evidence sessions is in the retrieved context: any and all, measured on text); characters of retrieved context; ingest and retrieval seconds. 60 questions: differences of about 15 points between arms can show; per-type counts (4 to 16 questions) are descriptive.

## Setup and isolation

Claude Code 2.1.330, `--model sonnet` for every one of the 600 calls (no other model; no API key); the host's own login. Versions: MemoryKing 0.1.0 at commit 99b1410, Knowledge Graph Memory server `@modelcontextprotocol/server-memory` 2.2.1, Basic Memory 1.0.0, MCP Memory Service 13.0.0. Every call returned a reply the judge parsed as yes or no (0 unparsed). The stage ran from 12:51 to 15:32 UTC on a host that otherwise did only analysis work; the ingest seconds below are from this run (four arms at a time, so shared CPU).

## Paired tests

`memoryking` against each other arm, exact two-sided McNemar by question (60 questions each, none dropped), Holm over four:

| Against | `memoryking` only right | Other only right | Both or neither | p | p (Holm over 4) |
| --- | ---: | ---: | ---: | ---: | ---: |
| `mcp_memory` | 34 | 0 | 26 | 1.2e-10 | **5e-10** |
| `basic_memory` | 3 | 9 | 48 | 0.146 | 0.438 |
| `mcp_memory_service` | 6 | 10 | 44 | 0.455 | 0.604 |
| `log` | 10 | 5 | 45 | 0.302 | 0.604 |

**`memoryking` is distinguishable only from the Knowledge Graph Memory server, and there it is ahead (34 questions to 0).** Against Basic Memory (3 to 9), MCP Memory Service (6 to 10) and the raw transcripts (10 to 5) the counts go against `memoryking` for the first two and for it against the last, and none of the three is significant after correction: with 60 questions a gap of 4 to 6 questions (7 to 10 points of accuracy) is within what this design cannot separate.

## Retrieval against reading

Of the questions with an answer-bearing turn, evidence found in the context and the answer right / wrong, then not found and right / wrong: `memoryking` 37 / 10, 4 / 7; `basic_memory` 44 / 9, 3 / 2; `mcp_memory_service` 44 / 7, 1 / 6; `log` 31 / 11, 5 / 11; `mcp_memory` 6 / 12, 1 / 39. `memoryking`'s context held the evidence in 47 of 58 such questions (81%), Basic Memory's in 53 (91%) and MCP Memory Service's in 51 (88%); when the evidence was in the context the reader was right about 79% of the time for `memoryking`, 83% for Basic Memory and 86% for MCP Memory Service, so most of the gap is retrieval (`memoryking` returned fewer characters, 10,772 against about 11,700 to 12,000, and missed multi-session evidence more often: all of a multi-session question's turns in 33% of its questions against 67% and 53%).

## Notes on the other arms

- **Knowledge Graph Memory server: 9 of 60 is a statement about the harness's retrieval function for it, not about the product's search by an agent.** The server's only search is a literal substring match on one string; the adapter searches each content word of the question and ranks entities, returning 4,722 characters on average (the others about 11,700 to 12,000) and the evidence in 31% of the questions. A real agent would also try other words. Reported as measured, with that limit.
- **Basic Memory ingest took 150 seconds per haystack** (about 2.5 hours for 60), 12 times `memoryking`'s 12.9 s; MCP Memory Service 31 s (13.8 s when timed alone in the offline check; four arms shared the CPU here).
- **`log`** is raw turns ranked by shared words: a retrieval baseline, not a product.

## Harness faults, exclusions and regrades

None found during the run; no call repeated, lost or excluded; no question regraded. Faults found and fixed before the run are listed in the protocol (T5-1 to T5-5; MCP Memory Service's refusal of repeated passages was one, found by the offline proof). **Calls used: 600 of 600** (300 reader, 300 judge). Model: `sonnet` only.

## Limits

One reader, one judge (both Claude Sonnet, so a self-grading effect is possible and not measured), one draw of 60 questions, one budget, one repetition: the intervals are wide (15 to 25 points) and the McNemar tests on 60 questions separate only large differences. The retrieval of each arm is the harness's own construction (above), which favours products with a documented broad search and disfavours one whose search is a literal match. Three of the five arms are fed whole turns with their own dates in one scope, which is not how any of them is used in a coding session. Not run: the same questions with a different budget or reader; an agent searching the products with several queries.
