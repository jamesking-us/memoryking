# Long-history benchmark: track T1 re-measured after roadmap P2-11 (2026-11-22, Claude Sonnet via the Claude Code CLI, commit 033a9f0)

Track T1 (needle at scale) on a fresh seed, 13, at history sizes 200 and 2,000: 12 tasks at each size, four arms, one repetition: **96 real agent sessions, no probes, no re-runs, none excluded.** Aggregates only; event streams, stores and working directories stayed outside the repository.

**What this is.** One re-measure, with one agent, one model, one repetition and 12 tasks per size, of the prompt and ranking changes made after the first real-agent run ([the seed-11 record](2026-11-22-s0-s1-a7c08d0.md); [the offline record of the changes](2026-11-22-offline-hook-p2-11.md), which used a scripted reader only). The question was whether MemoryKing, as `memoryking setup claude-code` now installs it, does better than the seed-11 run showed, and whether its prompt-time hook helps. A pass is a hidden check passed by one agent on a small synthetic fixture, not evidence of real-task quality, and a seeded history is not a lived one. With 12 tasks, 6 wins against none reaches p < 0.05 uncorrected; after Holm correction over the three primary comparisons the smallest p is multiplied by three, so it takes 7 wins against none (p = 0.0156, 0.047 corrected). Read the tables as what this design can show, not as a ranking of products.

## Design, fixed before the first session

- Arms (four): `memoryking` (exactly what `setup claude-code` installs at this commit: start, pre-compact and session-end hooks, the prompt-time recall hook, the lean bridge with `alwaysLoad`), `memoryking_nohook` (the same without the prompt-time hook), `log` (raw transcripts to `grep`), `notes` (the bounded extractive notes file). 12 tasks x 2 sizes x 4 arms = 96 sessions, the whole approved budget.
- Seed 13 had never been generated or read before this run (seeds 11 and 12 were not used). Size 200 is two groups of six tasks, size 2,000 one group of twelve.
- **Analysis, fixed before the run.** Primary, three comparisons, Holm-corrected over three: `memoryking` against `log`, against `notes` and against `memoryking_nohook`; exact two-sided sign test paired by task, pooled over the two sizes as the seed-11 record pools (a task's outcome is its pass rate over the sizes). Also by (task, size) pair, 24 pairs, as a secondary. Wilson 95% intervals per size. Descriptive only (a different seed, so no test): this run's `memoryking`, `log` and `notes` beside the seed-11 numbers at 200 and 2,000. Per run: pass or fail and failure class, input, cache and output tokens, seconds, memory characters in the context; for the two MemoryKing arms also whether the prompt hook fired and how many characters it injected, whether its injection, the start briefing and any `recall` result carried each needle sentence, how many times `recall` was called, and a class for every failure (never surfaced, surfaced but not used, wrong value, task error). Whatever it shows is reported, including no gain or the no-hook arm winning.
- Limits fixed: at most 96 sessions in all, model `sonnet` only (no other model, so no product that needs one), up to four in parallel, a restartable driver with a durable ledger so that no session is started twice (a session that was started and did not finish is recorded as interrupted and not run again; only a refusal for a usage limit is waited out, up to two hours, and retried). The order of the 96 runs was shuffled with a fixed seed across tasks, arms and sizes.

## Setup

- Code: the working-branch commit `033a9f0` with no harness change; every session used it. Its verification (`tools/check.py`, 13 steps, and the PostgreSQL test patterns) passed before the first session.
- Agent: Claude Code CLI 2.1.330, `--model sonnet`, served as `claude-sonnet-5-5` in all 96 sessions (read from each session's init event), on the host's Claude login, no API key set or passed. Flags as `benchmarks/longhaul/agent.sh`: 60 turns, 900 seconds (never reached; the longest session took 23 seconds), `--permission-mode acceptEdits --permission-prompts none`, the same allowed-tools list in every arm plus the arm's own tools, session persistence on. Up to four sessions in parallel on a shared four-core host. The CLI's own computed cost of the 96 sessions was 6.97 US dollars (not a bill).
- Seeding: `memoryking` and `memoryking_nohook` through the hook events of a real session ("as captured", no model); `notes` and `log` by the extractive rule or as files. Seed seconds and store size per history (one run each, on a host that was also seeding other arms): MemoryKing 6.8 s and 2.4 MB at 200 sessions (7.9 s for the no-hook copy), 47 s and 15.1 MB at 2,000 (44 s for the no-hook copy); `notes` and `log` under 0.1 s, 0.13 MB and 1.3 MB.

## Isolation evidence

- A fresh empty `HOME` per session, a scrubbed environment, a working directory named after the task's project that holds only the repository and the arm's own files, `--strict-mcp-config`, auto-memory off. In all 96 streams the init event shows the same model, the same CLI and `acceptEdits`, and exactly the arm's own tool servers: the `memoryking` server connected in the 48 MemoryKing runs, none in `log` and `notes`. No run ended `other`, timed out or had an error result.
- **The two MemoryKing arms share the same seeded content and differ only in the prompt hook.** For every one of the three histories the observation rows (project, source, content hash, classification, observed time, readers), the searchable text, the anchors, the term statistics, the grants and the projection items are identical between the two seeded stores (hashed over the sorted rows); only event timestamps and observation ids differ, because they were created at seeding time. The generated `settings.json` of the two arms differs only in the `UserPromptSubmit` hook entry (and run-directory paths); `mcp.json`, the allowed tools and the prompt are the same. In the streams, the prompt hook fired in 24 of 24 `memoryking` runs and in none of the `memoryking_nohook` runs; the start briefing fired in all 48.
- Denied commands (a Bash command that wrote through a heredoc or read outside the directory) occurred in 15 of 24 `log` runs (it works by shell commands), 3 of 24 `memoryking`, 3 of 24 `memoryking_nohook` and 2 of 24 `notes`; 6 of those runs failed (`log` 2, `memoryking` 1, `memoryking_nohook` 2, `notes` 1, all at 2,000 sessions). Agents normally wrote their code through `python` or the edit tool and continued. In one failed run (`log`, id-format at 2,000) the agent wrote no code after a denial; its needle had also never surfaced, so it stays in its memory class. A denial is not a harness exclusion, and none was excluded.

**Did agents call `recall` more or less often than in the seed-11 run?** More. ## MemoryKing failures, classified

Every failed run was classified from its event stream with the rule of the seed-11 record, but with the needle sentence defined as above: **never surfaced** (no needle sentence of a failing slot is in any hook output or tool result the model was shown), **surfaced but not used** (shown, and the code did not use it), **wrong value used**, **task error unrelated to memory**. A run with any slot never surfaced is counted never surfaced.

| Arm | Failed | never surfaced | surfaced, not used | wrong value used | task error |
| --- | ---: | ---: | ---: | ---: | ---: |
| `memoryking` | 8 | 5 | 3 | 0 | 0 |
| `memoryking_nohook` | 10 | 7 | 3 | 0 | 0 |
| `log` | 5 | 3 | 2 | 0 | 0 |
| `notes` | 12 | 12 | 0 | 0 | 0 |

All 18 MemoryKing failures are at 2,000 sessions: none at 200, where the seed-11 run lost 9. With the hook, 5 never surfaced (the sentence for one of two needles was in no result: batch-export, export-delimiter, id-format, rate-limit, retention) and 3 surfaced but not used: in date-style, money-rounding and port-config both needles reached the model among many records about the same attribute of other components, with different values, and the agent said it could not find the team's convention (it wrote nothing in two of the three, and used a default decimal count in the third). The eight tasks the hook arm lost are lost by the no-hook arm too; the no-hook arm also lost log-format and net-timeouts. `log`'s five failures: three never surfaced and two surfaced but not used (date-style at both sizes is among them).

**Why the hook does not decide the 2,000-session result.** There the hook carries 5 of 24 needles (a project holds about a hundred records about the same component and a prompt does not name the attribute), `recall` with the prompt carries 10 and a careful query 13, and the agents' own `recall` queries reached 18 (hook on) and 17 (hook off). The agent's second look, not the hook's first, is where the needles are found.

## Is the default-on prompt hook supported by this run?

Weakly, not statistically. With the hook on, MemoryKing passed 16 of 24 against 14 without it (2 tasks to 0, p 0.50), at no cost in tokens (129,000 against 135,000 input tokens, 12.6 seconds each) and no loss at either size; it carried 24 of 24 needles at 200 sessions and the agents there answered from it with fewer `recall` calls and passed every time. It did not do worse anywhere, and the offline carry predicted what the streams show. But the no-hook arm passed as many at 200 sessions, and the difference at 2,000 (4 against 2 of 12) is within what one repetition of 12 tasks produces by chance. The run therefore does not show that the hook is needed, and does not show that it hurts; it shows that at 2,000 sessions neither variant approaches `log` (8 of 12). Whether the hook stays on by default is still the owner's decision; nothing here argues for turning it off, and nothing in this run is evidence that it is the reason for the 200-session gain.

## Harness faults, exclusions and regrades

1. **No harness fault was found before or during the run** (the offline pre-checks and the stub pipeline passed first), so no harness fix was made. The driver and the analysis scripts live outside the repository, as before; compared with the seed-11 driver the driver now never starts a session twice (it counted and retried a started but unfinished session before) and measures the two-hour usage-limit wait by the clock rather than per thread.
2. **An analysis-side matching difference, found after the run and fixed before the numbers were final.** The first pass of the classification script used the seed-11 script's needle definition (a clause that holds one of the slot's value strings), which misses a needle stated in words that differ from the slot's value (for example "oldest first" for `oldest-first`). It counted 21 of 48 needles in the hook arm's prompt injection (18 of 24 at 200 sessions, 3 of 24 at 2,000) and 6 of its failures as never surfaced; with the generator's own sentences, as `hookprobe` defines them, the numbers are 29 of 48 (24 and 5 at the two sizes, exactly the offline measure for this seed) and 5. The numbers in this record use the second definition. **The seed-11 record's carry counts (20, 2 and 1 of 24) and its "never surfaced" class used the first definition and so probably understate what reached the model there** (offline, the scripted measure of seed 11 before the change gave 22, 3 and 0); the seed-11 comparison above uses pass counts only and is not affected.
3. No session was excluded, re-run, repeated or regraded; no usage limit was met; no run timed out or had an error result. Sessions used: 96 of 96.

## Limits of this run

One agent, one model, one CLI, one repetition, 12 tasks per size, two sizes; seeded histories, not lived ones; a pass is one hidden check on a small fixture; the machine was shared, so seconds are noisy; the seed-11 and seed-13 comparison is across different histories and is descriptive; the 200-session gain is not attributable to one change because the no-hook arm gains as much; the prompt sentence and the harness's scope sentence are the same in every arm; MemoryKing is compared with two baselines, not with other memory products (those arms, and the 20-session size, were not part of this approval); tracks T2 to T5 (change over time, forgetting, scopes, hostile text, question answering, lived sessions) were not run, so nothing here says how MemoryKing handles corrections, deletion, scopes or injection.
