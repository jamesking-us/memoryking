# Long-history benchmark: stages S0 (repeat) and S1, track T1 (2026-11-22, Claude Sonnet via the Claude Code CLI, commit a7c08d0)

Track T1 (needle at scale) on the measured seed 11: 12 tasks at history sizes 20, 200 and 2,000, nine arms, one repetition: 312 measured sessions (the six tasks of group 0 at size 200 are stage S0, the rest is stage S1), plus 12 probe sessions: 324 real agent sessions, no re-runs. Aggregates only; event streams, stores and working directories stayed outside the repository.

**What this is.** A first measured comparison on one track, with one agent, one model, one repetition and 12 tasks per size. A pass is a hidden check passed by one agent on a small synthetic fixture, not evidence of real-task quality, and a seeded history is not a lived one. With 12 tasks, 6 wins against none reaches p < 0.05 uncorrected (the protocol text says 10; that was an arithmetic slip and is corrected in `RUNNING.md`); after Holm correction across the eight comparisons the smallest p of a table is multiplied by eight, so it takes 9 wins against none. Read the tables as "what the design can show", not as a ranking of products.

**Two labels used throughout.** `basic_memory`, `mcp_memory_service` and `mcp_memory` are **written in full**: every seeded session was written into the product through its own write tool (`--allow-unfaithful-seeding` for the first two, because their own hooks would have stored little or nothing from sessions of a few turns). That is generous to those products and is not what a real session would have given them. `memoryking` and `claude_mem` are **as captured**: seeded through the hook events a real session fires.

## Setup

- Code: the working-branch commit `d81b134` plus one harness commit, `a7c08d0` (the prompt-time hook's injection now counts as memory in the context; see Harness faults). Every measured run, in both stages, used `a7c08d0`.
- Agent: Claude Code CLI 2.1.330, `--model sonnet`, served as `claude-sonnet-5-5` in all 312 sessions (read from each session's init event), on the owner's Claude login; no API key was set or passed. Flags as `benchmarks/longhaul/agent.sh`: 60 turns, 900 seconds (never reached), `--permission-mode acceptEdits --permission-prompts none`, the same allowed-tools list in every arm plus the arm's own tools, session persistence on. Up to 4 sessions in parallel on one shared four-core host that other jobs also used; the order of the runs was shuffled (fixed seeds) across tasks, arms and sizes. The CLI's own computed cost of the 312 sessions was 21.75 US dollars (not a bill).
- Products, installed under `/tmp/mk-lh-<name>/` and not reinstalled (their tests in `tests/test_longhaul_systems.py` passed, 14 tests): MemoryKing 0.1.0 as `memoryking setup claude-code` installs it (start, pre-compact and session-end hooks, the prompt-time recall hook, the lean bridge with `alwaysLoad`), the reference MCP memory server 2.2.1, Basic Memory 1.0.0 with its Claude Code plugin at tag v1.0.0, MCP Memory Service 13.0.0 with its Claude Code plugin at tag v13.0.0, claude-mem 16.0.3, Python 3.12.3. No fake model in any arm. Mem0 and Graphiti were not part of this run.
- Seeding: `memoryking` and `claude_mem` through the hook events of a real session ("as captured"); `mcp_memory`, `basic_memory` and `mcp_memory_service` through their write tools ("written in full"); `notes`, `native`, `log` by the extractive rule or as files. The tools are behind the host's tool search for every product except `memoryking`, as each is documented.
- The generated tasks, the null/oracle validation (the stub without memory fails and the oracle passes for all 12 tasks at 20, 200 and 2,000), and the seeded stores' history digest were checked before the first run.

- No run ended `other`, none timed out, none had an error result; the longest session took 68 seconds.
- Denied commands: the same allowed-tools list in every arm denied a Bash command that wrote a file through a heredoc, or read outside the directory, in 61 of 312 sessions (`off` 3 of 36, `notes` 5, `log` 22, `native` 9, `memoryking` 5, `mcp_memory` 8, `basic_memory` 2, `mcp_memory_service` 4, `claude_mem` 3 of 24). The agent normally continued with its edit tool. `log` is hit most because it works by shell commands. In 4 failed runs (`claude_mem` 2, `mcp_memory` 1, `log` 1) the agent wrote no code after a denial; in all four the sentence stating a needle had not surfaced either, so they stay in their memory class and are not excluded.

### MemoryKing: what reached the model, and what that suggests

- **The prompt-time hook fired in 33 of 36 runs** with 1,300 to 3,000 characters of recalled items (it injected nothing for the date-style task at all three sizes: its prompt shares few words with any stored item). Its injection carried a needle sentence for **20 of 24 needles at 20 sessions, 2 of 24 at 200 and 1 of 24 at 2,000**. The start briefing (the newest sessions of the project) carried a needle for 9 of the 72 (7 at 20 sessions, 1 at 200, 1 at 2,000), and a `recall` result for 16 (1, 5 and 10 at the three sizes). At 200 and 2,000 the five items the hook is allowed (`PROMPT_LIMIT`) were filled by sessions that share the subject's words (other components with the same attribute, drafts, reverted values) and the needle was not among them.
- **The agent rarely asked again.** The `recall` tool was called in 10 of the 36 runs. At 200 and 2,000 sessions the runs that called it passed 6 of 9 and the runs that relied on the hooks passed 1 of 15 (descriptive: agents recall when the injection looks insufficient, so this is not a causal estimate). In the S0 pilot (before the prompt hook existed) the agents asked `recall` themselves and MemoryKing passed 4 of 6 at 200 sessions; with the hook, 1 of 6 on the measured seed and 3 of 12 over both groups. The injection text ("Use them only if they help") reads as a complete answer when it is a top-5 list, and the agent stopped looking.
- Offline, on the money-rounding task of group 0, a query naming the attribute ("decimal places of the invoice amounts rounding mode") with the floor off returned the needle sentences from the seeded store. The information was stored; retrieval for the whole task prompt did not reach it.
- **Changes this suggests** (not made here): fill the hook's token budget instead of stopping at 5 items; show only one item per session (the same session appears as the user-turn capture and the session capture, and short captures repeat); build the hook's query from the prompt's subject and attribute words rather than the whole prompt, so that filler does not lower the score of a real match (in the probes the floor removed a planted item once a scope sentence was added); say in the injection when it is a partial list and name `recall` as the way to ask for the rest; and make the start briefing relevant to the prompt when the project has more sessions than it can show.

### Where another arm beat MemoryKing, and why

- **`log` (32 of 36 against 18): the raw transcripts, searched by the agent.** The agent greps the subject's words and reads whole matching sessions, as many times as it needs; at 2,000 sessions it still passed 9 of 12. It costs more tokens (145,000 against 118,000) and seconds (14.4 against 11.6). Pooled over sizes, `log` did better than `memoryking` on all 12 tasks and worse on none (12 to 0). The comparison sets retrieval that the agent drives itself against a hook that decides once.
- **`notes` and `native` at 20 and 200 sessions (11, 12, 11, 10 of 12 against 11 and 3):** everything fits in the file, so retrieval is complete; they lose it at 2,000 (1 of 12 each, against `memoryking`'s 4). That is the design of a bounded file and the reason for the size axis.
- **`mcp_memory` and `basic_memory` at 200 (10 of 12 each against 3):** **written in full**, so every session's turns are in the product, and the agent searched with its own queries several times (memory characters 38,000 and 25,000 against 9,000). This is the generous seeding the labels warn about, and both stop being better at 2,000 (3 and 4 of 12 against 4), where `mcp_memory` also costs 323,000 input tokens a session.
- `mcp_memory_service` (written in full) was not distinguishable (17 against 18 of 36); `claude_mem` (as captured) passed 3 of 24 and `memoryking` beat it at the sizes both completed.

## Harness faults, fixes, exclusions and regrades

1. **The prompt-time hook's injection was not counted as memory in the context** (found in the probes, before any measured run; fixed in `a7c08d0` with a test). Only the start hook's output was counted, so the `memoryking` arm's prompt hook, and the other products' prompt and file-context hooks, showed 0 characters. The analysis now counts the output of the start, prompt and pre-tool-use hooks (an empty JSON answer is not memory) and records the output size of every hook event. It changed no agent's input, only the measure; no run was affected because it was fixed first.
2. **The probe's tiny history cannot exercise the prompt hook** (a limit of the checklist, not of the harness): see the probe table. The hook was checked on the real stores instead.
3. **Driver faults on my side, not in the repository:** the observer-call counter for `claude_mem` runs included the seed's logged calls (corrected in the ledger from the saved logs: 68 live calls, not about 1,500), and the seeding gate refused the 20-session `claude_mem` seedings on a wrong threshold (fixed, then seeded). Neither cost a session.
4. Checks: `regrade` over all 312 saved outputs changed no verdict (the hidden checks behaved; each failed run's code was read against its history in samples, and the checks' own audit tests passed). **No run was excluded, re-run, regraded or repeated.** Sessions used: 324 of the ceiling of 337 (12 probes + 312 measured); no usage limit was met.

## Limits of this run

One agent, one model, one CLI, one repetition, 12 tasks per size; seeded histories, not lived ones; a pass is one hidden check on a small fixture; the machine was shared, so seconds are noisy and seed times are inflated by concurrent seedings; the three "written in full" products are an upper bound and `claude_mem` and `memoryking` are as captured, so the two groups answer different questions; the prompt sentence and the harness's scope sentence are the same in every arm but do not suit a lexical recall floor equally; the denied-heredoc behaviour was left as the protocol has it; claude-mem has no 2,000-session result. Tracks T2 to T5 (change over time, forgetting, scopes, hostile text, question answering, lived sessions) were not run, so nothing here says how MemoryKing handles corrections, deletion, scopes or injection.
