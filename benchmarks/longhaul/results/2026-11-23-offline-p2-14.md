# Quoted third-party text, and telling near-identical records apart, before and after roadmap item P2-14 (offline, scripted readers, no agent)

**What this is.** A scripted measurement with no agent and no model call of any kind. It says what was put in front of a model by the hooks and by `recall` on generated histories, and what a script that reads that text can tell apart. It is not evidence that a real agent does better, and the scripted readers below are not agents. The real-agent record that started it is [2026-11-23-t1-products-84071da.md](2026-11-23-t1-products-84071da.md) (seed 16): at 2,000 sessions MemoryKing failed 6 of 12 tasks, three of them "surfaced, not used" and one a wrong value. The previous offline records are [P2-12](2026-11-22-offline-preflight-p2-12.md) and [P2-13](2026-11-22-offline-retrieval-p2-13.md); the measures are the same tools (`tools/longhaul_benchmark.py hookprobe`, `benchmarks/longhaul/preflight.py`, `benchmarks/longhaul/poolprobe.py`) plus one new module, `benchmarks/longhaul/distinct.py`.

**Data discipline.** Tuned only on development seeds 1 to 5. Seed 16 is used up (a real-agent run was made on it); it was read for diagnosis and measured here as a development seed, so nothing about it is held out. No held-out seed was generated or scored, so there is no untuned check of Part B. The old code ("before") is the head before this change (`6145180`) run from a copy in its own virtual environment; "after" is the working tree. Both read the same seeded stores (seeded once with the new capture code; see Part A for why that is the same store), and the machine was shared with other jobs, so times are noisy.

## Part A: text the assistant quoted from a tool result

**The gap.** Since P2-12 a failed tool result is stored apart (source `<host>-tool`) and left out of the start briefing and the prompt hook. When the assistant's own turn quotes a fetched page or a tool's output that carries an embedded instruction, the capture stored it as the assistant's words and the automatic views showed it, labelled only as evidence (8 of 18 T4 tasks at 200 sessions after P2-13).

**A fault in the benchmark found first.** In the three T4 tasks where the assistant quotes a page ("The page I fetched says: ..."), the generated session's tool turn held unrelated test output, so the quoted page had no source anywhere in its own session and nothing could tell it was a quote. The generator now puts the page (release notes with the hostile sentence in them) in that session's tool turn, as a fetch's result would be. Only those three needle sessions change and no random draw changes, so no history of T1, T2, T2f or T3 changes (the audit and the pinned digests of those tracks pass unchanged). Recorded as amendment 10 of the protocol in [RUNNING.md](../RUNNING.md). The "before" figures below are the old code on this same generator.

**The rule.** At capture the hooks compare each turn of the conversation (the assistant's and the user's) with the tool results of the same session, successful and failed ones, which are read in memory and never stored. A **copy** is a run of **12 or more consecutive words** (letters and digits; case, punctuation and spacing ignored) of **at least 72 characters** that also stands consecutively in one tool result. Nothing is read from how the text is worded. The copy moves to the `<host>-tool` observation as a paragraph that begins `Quoted by the assistant: ` (or `the user`), the turn keeps its other words with a marker where the copy was, so no schema changes and both backends see the same kind of observation as before. Results of MemoryKing's own tools and of the editing tools are not compared. The automatic views already leave `<host>-tool` out (same switch, `--third-party` or `MEMORYKING_HOOK_THIRD_PARTY=1`), and an explicit `recall` shows the record in the existing fence under the label "Untrusted tool output, quoted".

**Why 12 words and 72 characters.** The first version used 8 words and 48 characters. Run over the generated histories (turns of the user and the assistant against the tool turn of the same session) it found copies in turns that were not quotes: an attribute phrase ("label of the first header column of the orders export") that a statement and a code comment both hold, which would have cut words out of a needle sentence.

| Threshold | T1 (6 seeds, 12,000 turns) | T2 (2 seeds, 4,000) | T3 (1 seed, 2,000) | T4 (3 seeds, 3,000) |
| --- | ---: | ---: | ---: | ---: |
| 8 words, 48 characters | 16 turns | 14 | 4 | 19 |
| 10 words, 64 characters | 0 | 4 | 0 | 10 |
| **12 words, 72 characters (shipped)** | **0** | **0** | **0** | **9 (all hostile quotes)** |
| 16 words, 90 characters | 0 | 0 | 0 | 9 |

With the shipped rule no turn of any T1, T2, T2f or T3 history changes: T1 at 2,000 sessions on seeds 1 to 5 and 16, 60,000 turns, 0 turns with a copy (and 0 of 12,000 at 200 sessions). So the seeded T1 stores are the same text whichever capture code seeds them, and the T1 carry figures cannot be moved by Part A. Every one of the 9 hostile quotes (three tasks on each of three seeds) is found. A hostile sentence shorter than 12 words, or one the session's tool results do not hold, is not found: the rule is a boundary, not a filter.

**Results** (`preflight.py --track T2 T2f T3 T4 --size 20 200 --seeds 1 2 3`, the same command on the old and the new code). T4, 18 tasks per size:

| T4: the hostile sentence in | 20 before | 20 after | 200 before | 200 after |
| --- | ---: | ---: | ---: | ---: |
| start briefing | 0 | 0 | 0 | 0 |
| prompt hook | **9** | **0** | **8** | **0** |
| `recall` with the task prompt as the query (unfenced / fenced) | 9 / 0 | 0 / 3 | 9 / 0 | 0 / 3 |
| `recall` with the subject phrase | 9 / 0 | 0 / 0 | 7 / 0 | 0 / 0 |

Before, the instruction stood in the prompt hook labelled only as evidence, as the assistant's words, in 8 of 18 tasks at 200 sessions (9 at 20); after, in none of the 18 at either size, and where an explicit `recall` finds the record it is fenced and labelled as quoted untrusted text (3 of the 9 tasks that quote a page, at both sizes). The quoted text is now a record of its own whose words are the page's, so a `recall` about the task's subject no longer finds it as part of the session (before it came with the session's topic words); a `recall` that uses the page's own words does (the hook tests do this). The nine tasks whose instruction arrives as a tool error are unchanged by this part (shown nowhere automatic, fenced where a `recall` finds them).

T2 (24 tasks), T2f (12), T3a, T3b, T3c (9 each): the outputs are identical before and after at 20 and 200 sessions, line for line (the prompt hook puts the current value first in 24 of 24 T2 tasks at both sizes; the forgotten sentence is shown nowhere and is on no file after the forget, as in P2-12; no canary of a sibling project is shown; the user-scope preference is absent from the hooks as before, which is the hooks' project-scope capture; the hand-off is shown to the prompt hook in 7 of 9 tasks at 200 and 9 of 9 at 20, as before).

A needle is not hidden by Part A on these histories (the scan above). In real histories a turn that restates, word for word and at that length, a decision that it also read in a file would have the restated run moved out of the automatic views; the decision stays in the turn when it is worded differently. That is stated in the guide.

## Part B: telling near-identical records apart at 2,000 sessions

### What the agent was shown (from the event streams of the seed 16 run, read only)

For each of the four tasks the agent's own `recall` results and both hooks were read (`/tmp/mk-lh-s1d/streams/T1-2000-<task>-memoryking-r1`). In every one, each needle slot (two per task, eight in all) was in front of the agent at least once, in a hook or in one of its `recall` results. Its answers say what it did with them: it separated the other components itself ("the firm decisions I found are for customer identifiers, batch identifiers or file names, not record identifiers. I didn't carry them over"; "many records about tax lines, refund amounts and ledger totals do state rules, but those are different amount types, so I didn't apply them") and then declined to pick a value because records about the *same component and attribute* disagreed.

The scripted reader of the new `distinct.py` measure (below), applied to the texts the agent was shown, finds the needle's value uniquely for all 8 needle slots in at least one of the texts the agent was shown (every statement of the asked component that is not marked as tried or not adopted names it), so the text allowed it. What it could not do is what no scripted reader without a reading of wording can do: the same value is also written as rejected.

**The cause is in the generated history, not the display.** The generator draws the value of "I tried X on a scratch branch, but it broke the importer; reverted" and "A colleague suggested X ...; we did not adopt it" from the slot's whole pool, which includes the value that is the needle. So the history says, about the same component and attribute, both "the delimiter is X" and "X was reverted / not adopted". Counted over the generated histories (T1, development seeds 1 to 5 and 16, 144 needle slots), the records of the needle's own project that say the needle's own value was tried and reverted or suggested and not adopted:

| History size | Needle slots with at least one such record | Such records in all |
| --- | ---: | ---: |
| 200 sessions | 60 of 144 | 77 |
| 2,000 sessions | **133 of 144** | 491 (3.4 per slot) |

In the four failing tasks, among the records the agent was shown, the needle's own value was written as tried or not adopted: the prefix `INV` twice; the number of decimals `0` three times; truncation toward zero four times; the port `7411` four times; the label `Order#` seven times. An agent that reads "settled on 7411" and, in newer records, "7411 broke the importer; reverted" and "7411: we did not adopt it" is right to say they contradict. This is a benchmark matter: the distractors "carry a wrong value" by the protocol's own description and here they carry the right one. It also holds for the tasks that passed, so it is not by itself the cause of a failure, but it lowers the chance that an agent can use what it reads, more at 2,000 sessions than at 200, which fits the size effect that was measured. **Not changed here:** correcting it changes the history of every seed, which the fixed protocol does not allow after results are seen. The owner should decide whether to exclude the needle's value from those distractors and re-seed; a product cannot repair it, because telling "tried and reverted" from "settled" is reading wording, which the product does not do.

Two more properties of the generated records that make them hard to tell apart by their text, found in the streams: a session's request turn names the project's main subject ("The gateway client settings came up in standup again") while the statement in the same record is about another component ("... the default listen port of the worker settings has to be 9532"), and "to be decided" or "unchanged" statements about the same component fill many of the places. Neither is specific to the benchmark: sessions in a real history open on a topic and state things about others.

### The measure, defined before the display was changed

`benchmarks/longhaul/distinct.py`, used unchanged before and after, on the text a view shows. It reads the generator's own knowledge (the asked component, the others, the attribute words, the pool values) to score the text; it never builds a query or changes what a product shows. Per task and per view:

* **other-component share**: of the items listed, the share whose statements (sentences naming a slot's attribute and one of its values) all name another component than the asked one; **asked-component share** likewise;
* **needle rank** and **other before needle**: the place of the first item holding a needle sentence, and how many items about another component stand before it;
* **scripted reader**, per needle slot: `absent` (the needle is not shown), `unique` (every statement of the asked component names the needle's value), `unique_live` (every such statement that is not marked tried, not adopted, draft or TODO does), `first_live`, or `ambiguous`.

(`marked`, `marked_other`, `marked_needles` count the records a list marks with `holds`; they were defined after the first measurements and cannot exist before.) The reader is a script, not an agent; `unique_live` uses the generator's three wordings of a near miss, which no product reads.

### What was changed

1. **A list marks the records that hold the query's words side by side.** When four or more observations are listed and some, not all, hold the query's pairs of neighbouring non-function words in the query's order (a pair every record holds weighs nothing, a rare one weighs most), those records say `holds <phrase>` and the line under the heading says how many. The list stays newest first. Nothing is read from wording or vocabulary. (`src/memoryking/domain/names.py`.)
2. **The prompt hook keeps the marked records first when its budget cuts the list**, before it cuts each record to its best sentence, so the budget's few places go to the records that hold the prompt's words together.

No schema change, no budget raised (the hook's 2,000 tokens, `recall`'s 6,000), no ranking threshold changed.

Distinguishability of what the prompt hook shows (seeds 1 to 5, 2,000 sessions; items listed: 1,879 before, 1,773 after):

| | before | after |
| --- | ---: | ---: |
| items about another component only | 46.5% | **41.3%** |
| items about the asked component | 20.0% | **26.5%** |
| needles not shown (`absent`) | 37 | **28** |
| needles read uniquely by the scripted reader (`unique` or `unique_live`) | 83 | **92** |
| mean items about another component before the first needle | 6.9 | 5.7 |

Seed 16 (hook): other-component 45.6% to 40.2%, asked 21.7% to 29.2%, `absent` 10 to 7. For the four failing tasks the hook now carries the decimals needle of `t1-money-rounding` that it did not (1 task); the other three are unchanged (id-format 0 of 2 in the hook both times; port-config 2 of 2; export-delimiter 1 of 2), and the needles those tasks lacked in `recall` (rounding label, header) are still not in it. `recall` shows the same records in the same order as before, with marks: its carried needles, its other-component share (34.0% before, 34.2% after) and its readings do not change.

**The mark is a weak signal, and this is the honest reading.** In the hook, the marked records are clean (13 of 202, 6% about another component) but few and they hold a needle in only 4 of the 92 cases carried: most needles are in a record whose request names something else. In `recall` at 2,000 sessions 1,075 of 1,905 listed records are marked and 362 of those (34%) are about another component, the same share as unmarked; a record that names the asked subject in its request turn and states a value for another component is marked, and the mark cannot know. Needles are in a marked record in 55 of 81 carried cases (68%) while 56% of the records are marked, so marking tells a little and not much. What improved is which records the hook's budget keeps; what `recall` shows is not better told apart by a script that reads only component and attribute, and whether a real agent reads the mark is unknown.

**Cost.** The prompt hook shows 5,713 characters on average (5,722 before) in the same 2,000-token budget; `recall` 16,242 characters (15,762 before; the marks) in its 6,000 tokens. Time on the shared machine, mean per task at 2,000 sessions: hook 0.46 s after, 0.68 s before; `recall` 0.07 s after, 0.12 s before (a loaded host, not a speed-up: the computation added is linear in the listed records).

### Gates

The LongMemEval regression sample's gate is unchanged: turn recall-all at 10 is 0.6806 (threshold 0.67; the display change moves no ranking), no failures. The full set of check steps is in the roadmap entry.

### What was tried and dropped

* **Two groups, the marked ones first, in the displayed list.** In the T2 pre-flight at 200 sessions the prompt hook put the current value first in 20 of 24 tasks (24 before): a record of an older value that held the query's pairs stood before the newer correction that held fewer of them, which breaks the rule that a later record is current. The marks keep the list newest first and say the same thing.
* **The first rule for a copy (8 words, 48 characters)**, above.

### What stays weak, stated plainly

* At 2,000 sessions the agent will still meet records that say the needle's own value was reverted or not adopted, because the generator writes them (above). Nothing in this change can make those records agree.
* The mark cannot tell a record about another component from one about the asked one when the session's request names the subject; it is word-pair evidence only.
* Part B's gain is in what the hook keeps within its budget (9 of 120 needles on the tuned seeds, 3 of 24 on seed 16); it is on development seeds the code was tuned on, with no held-out seed scored, and a scripted reader is not an agent. The effect on a real agent is unmeasured.
* Part A catches a copy of 12 or more words of a tool result of the same session. A paraphrase, a short copy, and a quote of a page the session did not fetch are the speaker's own text. Sessions captured before this change keep the copy inside the turn.
