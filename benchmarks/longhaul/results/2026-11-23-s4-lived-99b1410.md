# Long-history benchmark: the lived track T2b beside other products (2026-11-23, Claude Sonnet via the Claude Code CLI, commit 99b1410)

Four tasks of four real sessions each, nothing seeded, five arms, one repetition, fresh seed 19: **80 real agent sessions (20 runs), no probes, no re-runs.** **Four runs are excluded for a harness fault that this run found (compiled bytecode left in the working directory; below), so the result of the stage rests on 16 runs.** Aggregates only; event streams, stores and working directories stayed outside the repository.

**What this is.** A check that the seeded results of the earlier stages are not an artefact of seeding: each product installed as its own quick-start says, writing its own memory, a fact stated in session 1, corrected in session 3, the code reset before session 4. One agent, one model, **4 tasks per arm**: with 4 tasks no test can reach p < 0.05 (a perfect 4 to 0 is p 0.125), so **this stage is descriptive and nothing in it is a ranking or a significance claim.** The protocol is [stage S4 of `RUNNING.md`](../RUNNING.md#stage-s4-the-lived-track-t2b-beside-other-products), fixed before the first session. **Label: lived.** Every arm wrote (or did not write) its own memory; there is no "as captured" or "written in full" label.

## Products and configuration

Named factually; each installed as its own documentation tells a Claude Code user, default settings, no model of its own: `memoryking` (MemoryKing 0.1.0 at commit 99b1410, exactly what `memoryking setup claude-code` installs: start, pre-compact and session-end hooks, the prompt-time hook, the lean bridge), `mcp_memory` (Knowledge Graph Memory server `@modelcontextprotocol/server-memory` 2.2.1, its nine tools, the README's suggested prompt as `CLAUDE.md`), `basic_memory` (Basic Memory 1.0.0 with its Claude Code plugin), `mcp_memory_service` (MCP Memory Service 13.0.0 with its Claude Code plugin), `notes` (a `NOTES.md` in the working directory and the sentence "You can keep notes for later sessions in NOTES.md in this directory.").

## Design and isolation

- Tasks `export-delimiter`, `retry-policy`, `rate-limit`, `id-format` x 5 arms = 20 runs of 4 sessions: session 1 states a fact (and one other) and asks for the function; session 2 a side task (one more test); session 3 corrects the fact; before session 4 the Python files go back to their starting text, added Python files are removed, notes and memory files stay; session 4 asks for the function again with no value in the prompt. A run passes when the final code uses the corrected value; the earlier value is `stale`. A fixed shuffle of the 20 runs, four runs at a time, the sessions of a run in order, one working directory and one store per run, each session a separate CLI session with a fresh empty `HOME`, `sonnet` only, the same flags, allowed tools and scope sentence as the earlier stages; after each session the harness waited (up to 90 seconds) for what the session left running before starting the next.
- In all 80 streams the init event shows `claude-sonnet-5-5` and exactly the arm's own tool servers, all connected; every session returned a success result; none timed out. The first four runs (none of them `memoryking`; the first `memoryking` run was the tenth) and then the `memoryking` run were read for harness faults. **`memoryking`'s session-end hook fired with the real CLI in `-p` mode: the store's observation count rose after every session in all four runs (3, 5, 8 and 10 observations after sessions 1 to 4: two from the hook each time and one from the agent's own `remember` in sessions 1 and 3).** CLI-computed cost 3.10 US dollars (not a bill). Nothing else heavy ran on the host.

## Harness fault found while reading the results, and the exclusions

**S4-6. Compiled bytecode survived the reset.** The between-session reset deletes the Python files that the agent added and restores the repository's own, but the interpreter's `__pycache__` (compiled `.pyc` of the module, written when the earlier sessions ran the tests) stayed in the working directory, so session 4 could recover a value from it. In four runs the agent did exactly that in session 4 (it disassembled `limiter.cpython-313.pyc` or `ids.cpython-313.pyc` with `marshal` and `dis`, or ran `strings` on it): `id-format` and `rate-limit` for `mcp_memory` and for `basic_memory`. That changed what the agent saw (a value outside memory), so **those four runs are excluded** (rule applied to the agent's actions, not to its outcome: any session-4 tool call that read a `.pyc`; two of the four had passed and two had not). They are not run again (no sessions beyond the 80). The harness is corrected after both stages finished (see the protocol); the other 16 runs had the same stale `.pyc` present and never read it, so they are kept, and the as-run counts of all 20 are given beside.

## What each product stored, and how each failure came about

- **`memoryking`**: two observations from its session-end hook after every session and one from the agent's own `remember` in sessions 1 and 3 (4 of 4 runs): 3, 5, 8 and 10 observations after the four sessions. The correction was stored and used in all four; the agent read memory through the start briefing and the prompt hook (no `recall` call in session 4).
- **`notes`**: the agent edited `NOTES.md` once, in session 3 (the correction), in all four runs, and read it in session 4. All four passed.
- **`mcp_memory`** (Knowledge Graph Memory server): **the agent wrote nothing in any of its 16 sessions** (it read the graph in each session, which was empty); the two kept runs failed as `missing` (the delimiter task used `,` and `ref`, a default and a guess; the retry task used 3 attempts, not 4). Never written.
- **`basic_memory`**: the agent wrote nothing, and the plugin's start brief said "No active tasks, open decisions, or recent sessions" in every session after the first; its kept runs failed `missing` (`export-delimiter`: the module was left without a value; `retry-policy`: 3 attempts, not 4). Never written. (The two excluded runs had `stale` results taken from the bytecode, not from memory.)
- **`mcp_memory_service`**: the agent wrote nothing; the plugin's own hooks stored a few memories (its start hook reported 1 memory after session 3 in `export-delimiter`, 2 after session 1 in `id-format`, 2 then 3 in `rate-limit`, none in `retry-policy`). **Written, then stale or not found:** the two `stale` runs (`id-format`, `rate-limit`) used the first value, not the correction; in `id-format` the hook stored nothing after session 3 (the count stayed at 2), in `rate-limit` it stored one more memory after session 3 (2 to 3) and the code still used the first value, so the correction was either not what it stored or not what the agent was shown (the stores were not kept, so this is not settled). In the other two (`export-delimiter`, `retry-policy`) little or nothing was stored and the code failed as `missing`.
- Stores of the other products were removed with the working directories (not kept), so the counts above are what the hooks and tool calls showed, not a read of the final stores.

## Tokens and seconds

Per run (four sessions), means: see the table above. `memoryking` and `notes` used the least input (about 384,000 and 381,000 tokens), the other three 390,000 to 413,000; Basic Memory took the longest (56 seconds a run). No paired test was declared for cost in this stage.

## What reached the model in the `memoryking` arm

The start hook and the prompt-time hook fired in all 16 sessions of the arm; no `recall` call was made by an agent in session 4 (its needed facts arrived through the hooks); the agent saved the fact and the correction itself with `remember` in sessions 1 and 3 of every run, which is what the start briefing tells it to do.

## Limits

One agent, one model, one repetition, **4 tasks**: it can show that a product that passed seeded tasks fails to carry its own memory (or does not), and how, and nothing about the size of a difference. Three of the products (the Knowledge Graph Memory server, Basic Memory, MCP Memory Service) were not told to save and, with this agent and these prompts, did not save; a differently prompted agent might. That the agent saved with `memoryking` and with `notes` is partly because the start briefing and the prompt sentence ask for it. `memoryking`'s hooks record the day of a capture, so the fact and its correction carry the same date in one run; every `memoryking` run passed, so this stage did not need a date to order them. Not run: the other tracks' lived counterparts, a second repetition.
