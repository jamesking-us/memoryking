# Long-history benchmark: question answering on 120 LongMemEval `_s` questions nobody had used, four arms (2026-11-28, Claude Sonnet via the Claude Code CLI, MemoryKing at commit 83f6ff9)

Stage T6: 120 questions stratified by type from `longmemeval_s_cleaned.json` (SHA-256 `d6f21ea9d60a0d56f34a05b609c79c88a451d2ae03597821ea3d5a9678c3a442`), drawn only from the 232 questions that were in neither the development draws nor the stage T5 draw (draw seed 21; SHA-256 of the sorted ids of the draw `fe2b8db982720bde482edbee818929a7110bbeeba192fc2c3adf299d0094c473`), four arms, one reader call and one judge call per question per arm: **960 model calls (480 reader, 480 judge), none repeated, none lost, none unparsed, no question excluded, no harness fault.** Aggregates only; nothing from the dataset beyond question ids and scores is kept here, and streams, stores and answers stayed outside the repository.

**The reading, in one paragraph.** The current MemoryKing code answered the most questions correctly of the four arms (103 of 120, 85.8%). Its lead over the released MemoryKing 0.2.0 (97 of 120, 80.8%: 5 points, 7 questions gained and 1 lost) points the right way, but **it is not established at the declared threshold with 120 questions** (p 0.070, 0.141 after correction); this was the primary comparison. It is **not distinguishable from Basic Memory 1.0.0** (100 of 120; 10 questions to 7). It is **ahead of MCP Memory Service 13.0.0** (87 of 120; 22 questions to 6) beyond chance after correction. Nothing more is claimed.

**What this is, and is not.** Each system ingests a question's haystack (about 46 to 50 sessions, about 500,000 characters) into an empty instance, returns a retrieved context for the question under one budget of 12,000 characters, a fixed reader answers from that context alone, and a fixed judge grades; this is stages [T5](2026-11-23-t5-99b1410.md) and [T5b](2026-11-23-t5b-semantic-c79e1a1.md) again, with the same reader, judge, prompts and budget. The retrieval function of each arm is the harness's construction of "what this system returns for a question" (`context_for` of each adapter: no query is written by hand and no model retrieves); it is not an agent searching with several queries, so this says nothing about the products used as their documentation tells a Claude Code user. **The questions were chosen so that none had been used for tuning** (MemoryKing's retrieval was tuned on 226 development questions, roadmap item P7-2) **and none had been published in an earlier record**, which is what makes the pair against 0.2.0 a test and not a fit. The other two arms were never tuned for or against. The protocol is [stage T6 of `RUNNING.md`](../RUNNING.md#stage-t6-track-t5-again-on-questions-nobody-has-used-four-arms-including-the-released-020), fixed before the first call.

## The arms

Reader and judge for all 960 calls: Claude Sonnet through the Claude Code CLI (`claude -p --model sonnet`, no tools, an empty neutral directory, a fresh home and a scrubbed environment), the prompts of `benchmarks/longhaul/prompts/`. Four arms at a time on one four-core host.

- **MemoryKing at commit 83f6ff9** (`memoryking_semantic`). Fed every chat turn as one observation at its session's date through its capture path; the daemon takes over on the installed, verified `bge-small-en-v1-5-onnx` model, indexes the haystack in the background (counted as ingest), and each briefing's receipt must show the semantic channel. **It contributed in 120 of 120 questions.** Its version string is `0.2.0` too, because the package number had not moved since the release, so this record names it by commit.
- **MemoryKing 0.2.0 as released** (`memoryking_020`, the package from PyPI, wheel SHA-256 `2a52f9f61aef24d356e0eed409cc587b08911dfffd4fd4a9451cfd19a34deddd`, its dependencies pinned by hash in `benchmarks/longhaul/tools/locks/memoryking-0.2.0.lock`). It runs none of this checkout's product code: a worker under its own virtualenv refuses to go on unless the package is 0.2.0, and the store, capture path, daemon and receipt are 0.2.0's. It is fed and asked exactly as the current arm is, with the same model directory. The semantic channel contributed in 120 of 120 questions.
- **Basic Memory 1.0.0** and **MCP Memory Service 13.0.0**: as in stage T5 (Basic Memory one note per session with every turn whole, then a reindex and a ten-result search; MCP Memory Service one stored session with every turn whole and the sessions' own dates, searched under the project tag).

## Paired tests

The commit against each of the three other arms, exact two-sided sign test by question (the exact binomial test with probability one half on the questions the two arms answered differently; 120 questions each, none dropped), **Holm over three**, as declared:

| Against | Commit only right (wins) | Other only right (losses) | Both or neither | p | p (Holm over 3) |
| --- | ---: | ---: | ---: | ---: | ---: |
| MemoryKing 0.2.0 (primary) | 7 | 1 | 112 | 0.070 | 0.141 |
| Basic Memory 1.0.0 | 10 | 7 | 103 | 0.63 | 0.63 |
| MCP Memory Service 13.0.0 | 22 | 6 | 92 | 0.0037 | **0.011** |

**What is and is not established.** The only difference beyond chance after correction is the lead over MCP Memory Service 13.0.0. **The primary comparison, the commit against 0.2.0, is not established at the declared threshold**: with one loss the declared design needed 10 wins to pass after correction (7 to 0 was the least with none), and it had 7. The direction is the expected one and the net gain is 6 questions, but 120 questions cannot tell a gain of 5 points from chance, and this record does not claim it. Against Basic Memory 1.0.0, 10 questions to 7 is a lead of 3 questions, well within what 120 questions cannot separate.

**By type, the primary comparison.** The 7 questions the commit gained are 4 multi-session, 1 knowledge-update, 1 temporal-reasoning and 1 single-session-preference; the 1 it lost is a single-session-assistant question. The gain is concentrated where the change was aimed (an answer spread over several sessions): multi-session 21 of 32 against 17 of 32, with every needed turn shown for 20 of 31 questions against 15 of 31. Per-type counts of 6 to 33 questions are descriptive.

## Cost

Timings are with four arms sharing four cores, which is not how stage T5 and T5b ran, and **are not comparable with those timings; they are reported, not tested.** Indexing dominates ingest for the two MemoryKing arms: 95.0 s a haystack for the commit (84.0 s waiting for the index, about 495 vectors) against 115.7 s for 0.2.0 (101.9 s); Basic Memory took 168.6 s and MCP Memory Service 40.3 s. Retrieval took 0.36 s for the commit, 0.28 s for 0.2.0, 6.12 s for Basic Memory and 2.18 s for MCP Memory Service. The retrieved context averaged 11,898 characters for the commit (99% of the 12,000), against 10,973 for 0.2.0.

## What was not shown

- That the retrieval change helps answers by a margin 120 questions can see: the lead over 0.2.0 is 5 points and not established.
- That MemoryKing is better than Basic Memory 1.0.0: 3 questions apart.
- Anything about a coding session. The retrieval is the harness's construction, not an agent searching with several queries.
- That the figures transfer to other readers, judges or budgets. Reader and judge are both Claude Sonnet (a self-grading effect is possible and not measured).
- Anything about timings as products would run alone: four arms shared four cores.

## Limits

One draw of 120 questions, one reader, one judge, one budget, one repetition. Wilson intervals are about 13 to 16 points wide; three of the six types have fewer than 17 questions. The reader and the judge are both Claude Sonnet. The retrieval of each arm is the harness's construction, not an agent searching, and says nothing about the products in a coding session. The result is comparable in kind, not in number, to what other products publish (a different subset, reader, judge and budget). The commit under test reports version 0.2.0, so it is named by commit; the other MemoryKing arm is the published 0.2.0 package. Not run: other budgets or readers, other embedding models, the raw-transcript arm and the Knowledge Graph Memory server (not asked for in this stage).
