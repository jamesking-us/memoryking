# Long-history benchmark: question answering on LongMemEval `_s`, MemoryKing with semantic search on (2026-11-23, Claude Sonnet via the Claude Code CLI, commit c79e1a1)

Stage T5b: one arm, `memoryking_semantic`, on the same 60 questions as [stage T5](2026-11-23-t5-99b1410.md) (draw seed 20), the same budget, reader, judge and prompts: **120 model calls (60 reader, 60 judge), none repeated, none lost, none excluded, no harness fault.** Aggregates only; nothing from the dataset beyond question ids and scores is kept here.

**What this is, and is not.** In stage T5 the `memoryking` arm searched by keywords only: the environment had neither the embeddings libraries nor the model, so the semantic channel never ran, while Basic Memory and MCP Memory Service ran with their embedding search. The owner decided that semantic search becomes part of the default install and asked for the test to be run again. **This is one arm run a second time after a declared change of configuration, not a correction of the first run: the keyword-only result of stage T5 stands, and the five rows of stage T5 are shown here as measured there.** The other four arms were not run again; their stage T5 answers on the same 60 questions are the pairs. The questions had been seen once before (by the keyword-only arm, in a record that is public); nothing was tuned on them: the configuration is the product's default with the model on, at the same 12,000-character budget. The retrieval of each arm is the harness's construction of "what the system returns for a question", not an agent's search. The protocol is [stage T5b of `RUNNING.md`](../RUNNING.md#stage-t5b-track-t5-again-for-memoryking-with-semantic-search-on), fixed before the first call.

## What the arm is

`memoryking` fed the haystack as in stage T5 (every chat turn one observation at its session's date through its capture path), then the daemon takes over on the installed model directory: it loads the installed, verified `bge-small-en-v1-5-onnx` by itself, enables a partition for the project and indexes it in the background, as `memoryking setup` leaves a store once the libraries and the model are present. The harness waited until the index was complete (mean 76.8 s a haystack, 62 to 85 s, about 489 vectors; counted as ingest) and then asked the same `recall` as in stage T5 at 12,000 characters. **Each briefing's receipt was read back and had to show the semantic channel; the arm would have stopped otherwise. It contributed in 60 of 60 questions** (the dense stage available with 256 candidates each time, fused with the keyword channel by the convex method). Claude Code 2.1.330, `--model sonnet` for all 120 calls; MemoryKing 0.1.0 at commit c79e1a1.

## Paired tests

`memoryking_semantic` against each of the five rows, exact two-sided McNemar by question (60 questions each, none dropped), **Holm over five**:

| Against | `memoryking_semantic` only right | Other only right | Both or neither | p | p (Holm over 5) |
| --- | ---: | ---: | ---: | ---: | ---: |
| `memoryking`, keyword only (stage T5) | 9 | 1 | 50 | 0.0215 | 0.0645 |
| `mcp_memory` (stage T5) | 42 | 0 | 18 | 4.5e-13 | 2.3e-12 |
| `basic_memory` (stage T5) | 6 | 4 | 50 | 0.754 | 0.848 |
| `mcp_memory_service` (stage T5) | 9 | 5 | 46 | 0.424 | 0.848 |
| `log` (stage T5) | 16 | 3 | 41 | 0.0044 | **0.0177** |

**What is and is not distinguishable.** After Holm correction over five, `memoryking_semantic` is ahead of the raw transcripts (16 questions to 3) and of the Knowledge Graph Memory server's harness search (42 to 0). **It is not distinguishable from keyword-only `memoryking`: 9 questions to 1 is p 0.0215 before correction and 0.0645 after**, so with the declared correction the rise from 43 to 51 correct is not established by this test, though the net gain sits in multi-session (6 more correct) and preference questions (2 more), and nowhere else. It is level with Basic Memory (6 to 4) and MCP Memory Service (9 to 5): the lead of two and four questions is within what 60 questions cannot separate. Where the evidence was in the context the reader was right in 46 of 52 questions (88%); where it was not, in 3 of 6; so most of the remaining misses are reading, not retrieval, for this arm.

## Cost

Indexing dominates ingest: 83.6 s a haystack (76.8 s waiting for the single-threaded index), about 1.3 hours for the 60, against 12.9 s for the keyword-only arm and 149.6 s for Basic Memory; retrieval 0.20 s. The retrieved context averaged 11,012 characters, 8% of the 12,000 left unused.

## Harness faults, exclusions and regrades

None during the run; no call repeated, lost or excluded; no question regraded. A fault found while preparing the stage (a haystack that repeats a session id with another date made the product refuse a capture) was fixed before it (T5b-2); stage T5's draw ingested without it. **Calls used: 120 of 120** (60 reader, 60 judge). Model `sonnet` only.

## Limits

**One arm run a second time after a declared change of configuration; the same 60 questions had been seen once before by the keyword-only arm; nothing was tuned on them.** The reader and the judge are both Claude Sonnet (a self-grading effect is possible and not measured). 60 questions separate only large differences: the intervals are about 18 to 22 points wide and the pair against keyword-only `memoryking` did not pass the declared correction. The other four rows were measured earlier in a different run (same questions, reader, judge and budget, different time), so the pairs are not simultaneous. The retrieval of each arm is the harness's construction, not an agent searching with several queries, and says nothing about the products in a coding session. Two things differ between the keyword-only and the semantic arm besides the channel: the semantic arm is asked through the daemon on the real clock (a development check on draws 1 to 5 found the keyword channel's evidence recall moves by under a point when asked that way), and it waits for an index. Not run: other budgets or readers, other embedding models.
