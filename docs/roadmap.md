# Roadmap

This page lists the planned improvements to MemoryKing and where each one stands. It is a plan, not a development log: an item states the problem, the change and how to tell it is done, and nothing else.

Status: `[ ]` planned · `[~]` in progress · `[x]` done. A done item names the release that carries it. Items inside a phase are in priority order, and phases are worked top to bottom unless an item says otherwise.

Every change keeps the existing invariants: observations stay verbatim evidence, nothing becomes accepted knowledge without an authorized decision, every delivery has a receipt, purge follows dependencies, and a restore creates a new history. A change that needs one of these relaxed is out of scope until this page says so.

| Phase | Goal | State |
| --- | --- | --- |
| 0 | Remove the defects that stop normal use at modest size | done, 0.2.0 |
| 1 | Harden credentials, delegation and the control journal | done, 0.2.0 |
| 2 | Find the right memory: ranking, word forms, passages, semantic search | done, 0.2.0 |
| 3 | Turn evidence into knowledge without a reviewer always present | done, 0.2.0 |
| 4 | Make it easy for agents and developers to adopt | done, 0.2.0 |
| 5 | Scale and operate it for a team | done, 0.2.0 |
| 6 | Prove it on recall and on real task outcomes | done, 0.2.0 |
| 7 | Index faster, find every piece of an answer, and carry preferences between projects | in progress |

## Phase 0: remove the cliffs

- [x] **P0-1 Backups work at any store size.** The signed backup manifest lists every blob, so it exceeds the 1 MiB canonical limit at roughly 13,000 observations and the backup fails after copying everything; the scheduled backup then leaves a partial directory each minute (`adapters/local_store.py` `backup`, `adapters/postgres_recovery.py`, `backups.py` `Policy.run`, `contracts/canonical.py`). *Change:* sign a small manifest that carries the hash of a separate blob-index file; verify the index on restore; remove the partial directory and record the failure on any exception; correct the manifest bound in the deployment guide. Existing backups must still restore. *Done when:* a backup and restore round-trips at 20,000 observations in a test, and a failed scheduled backup leaves no directory behind. *Done: 0.2.0.*
- [x] **P0-2 Captures do not slow down or stall as the store grows.** Advancing the job frontier looks jobs up by position with no index that can serve it (`application/store_core.py` `_advance`), so a drain of 200 jobs takes about 0.1 s at 2,000 observations, 1.1 s at 12,000 and passes the five-second deadline near 29,000, after which captures are refused with `queue_full`. A `reindex` or restore re-queues every job and has the same effect at once. *Change:* add `jobs(tenant,position)` on both backends through the normal migration chain; give the idle probe a tenant predicate; make drain work in batches that each fit the deadline; do not let a reindex backlog refuse captures. *Done when:* a test captures and drains 30,000 observations with drain time per job flat, and a capture straight after `reindex` on 2,000 observations succeeds. *Done: 0.2.0.*
- [x] **P0-3 Accepted knowledge stays in briefings however many proposals exist.** The registry query takes the first 257 revisions of any state and blocks above 256 (`adapters/knowledge_store.py` `query`), so 17 daily `draft-proposals` runs remove all accepted knowledge from briefings, and the same count of constraint revisions blocks every briefing. *Change:* bound the registry by live accepted revisions (and reviewer-visible diagnostics separately), selected in SQL; rejected, superseded and unreviewed revisions never count toward the bound. *Done when:* a test with 300 unreviewed drafts and 3 accepted claims still returns the 3 claims, and 300 retired constraint revisions do not block. *Done: 0.2.0.*
- [x] **P0-4 A long task can always be resumed.** Operation listing raises `operation_limit` above 32 operations of any state (`adapters/working.py` `_operations`), so a task's 33rd recorded tool effect makes `resume`, `summarize`, hand-off and the execution snapshot fail. *Change:* return every open operation plus the newest resolved ones up to the bound, with a truncation flag; never raise for resolved history. *Done when:* a test records 40 succeeded operations and resume, summary and hand-off all work and report truncation. *Done: 0.2.0.*
- [x] **P0-5 `draft-proposals` works through the daemon.** The CLI command returns `invalid_request` because the socket contract does not admit the `draft` action; the tests call the store directly. *Change:* admit the action in the authoritative schema and regenerate; add a socket-level test for every CLI command that lacks one. *Done when:* `memoryking draft-proposals --project P` files drafts against a running daemon in a test. *Done: 0.2.0.*
- [x] **P0-6 The lean `save_progress` and `resume` tools behave as described.** A save with `findings` always fails (`lean.py` sends a kind the schema refuses); a second save erases next actions, failed attempts, blockers and constraints the caller did not repeat; every resume of a lean checkpoint reads "Blocked: recovery_reconciliation_required" because defaulted sections count as a recovery gap (`adapters/working.py`). *Change:* send a valid kind; merge omitted sections from the previous revision and say so in the tool description; report defaulted sections as a note, keeping the blocked status for real reconciliation gaps. *Done when:* tests cover all three, including `findings`, through the stdio bridge. *Done: 0.2.0.*
- [x] **P0-7 Session hooks save what matters and nothing secret.** The hooks keep assistant text only, including file bodies passed to write tools, with no redaction; they drop user turns and tool errors; the checkpoint they write replaces the agent's own with the oldest part of the transcript tail; pre-compact followed by session-end fails with `idempotency_conflict` (`host_hooks.py`). *Change:* capture user turns and tool errors, exclude tool inputs, scrub common secret shapes before capture, keep the newest part of the tail, write hook state to its own stream instead of the agent's, key the checkpoint by hook kind. *Done when:* tests show a planted key is not stored, a user instruction is recalled, and an agent-authored checkpoint survives a hook run. *Done: 0.2.0.*
- [x] **P0-8 Every per-tenant bound has a release path.** Checkpoints, hand-offs and hand-off views (4,096 each) and experience records (10,000) count rows of every state for the life of the tenant, and nothing deletes them; none appears under `status` capacity. *Change:* count live rows; add retention that keeps what history verification needs and removes the rest; report all four under capacity; correct the hints and the reference table. *Done when:* a test saves 5,000 checkpoints across tasks without refusal and plan history still verifies. *Done: 0.2.0.*
- [x] **P0-9 A scoped constraint does not lock out simple readers.** The lean tools, CLI and hooks always send empty bindings, so one accepted constraint scoped to an environment blocks every recall and resume with `applicability_unknown`, without saying which field is missing. *Change:* let the bridge, CLI and hooks carry session bindings; name the unbound field in the reply; do not let briefing-policy uncertainty block reading a checkpoint the caller wrote, or saving one (the lean save reads the latest checkpoint first, so today a blocked read also refuses the save). *Done when:* tests cover recall, resume and save with and without the binding. *Done: 0.2.0.*
- [x] **P0-10 The check is deterministic.** One reranker test (`test_rerank_reorders_only_the_fused_window_and_only_when_asked`) and the knowledge demo run by the docs check (`tools/knowledge_demo.py`, `denied` on its first namespace request) each fail intermittently on an unchanged checkout. *Change:* find and remove the nondeterminism in each, in the product if that is where it is. *Done when:* each passes 30 consecutive runs. *Done: 0.2.0.*
- [x] **P0-11 Small defects found while fixing the above.** `memoryking trust set` without `--key` fails for a glob source because the default key contains `*`; the lean `resume` tool advertises a larger budget than the resume contract accepts; a reviewer cannot list proposals once a project holds more than 256 revisions of any state, because the diagnostic query keeps the unfiltered bound; the changelog lacks entries for P0-3 to P0-7. *Done when:* each has a test or an entry. *Done: 0.2.0, except the lean `resume` budget, moved to P0-12.*
- [x] **P0-12 Follow-ups from Phase 0.** The lean `resume` tool advertises a larger budget than the resume contract accepts. The reviewer listing of procedures still blocks above 256 revisions, as the knowledge listing did. A resume that returns the caller's own checkpoint while constraints are unresolved omits open operations and the summary, so an uncertain operation is not shown there. `hooks install` does not write session bindings into the installed command. *Done when:* each has a test. *Done: 0.2.0.*

## Phase 1: credentials, delegation and the journal

- [x] **P1-1 Credentials can be rotated.** A credential is derived only from the store, tenant and principal, so re-issuing after a revoke yields the same token. *Change:* a per-grant generation stored with the grant, checked at authorization, advanced by `credential issue --rotate` and by revoke; optional expiry enforced server-side. *Done when:* a revoked-then-reissued credential differs and the old one is refused. *Done: 0.2.0, for both profiles, including owner rotation. Revoking one of several grants does not rotate; recovering a lost shared owner credential file is not covered.*
- [x] **P1-2 A delegated token acts for its issuer.** Delegation returns a token whose acting principal is the named subject. *Change:* decide and document the intended model, then keep the delegator as the actor with "on behalf of" recorded, so reader lists, writer ownership and the event actor are evaluated against who really acted. *Done when:* a test shows a delegated token cannot read what only the subject may read. *Done: 0.2.0. The token is the issuer with a narrower scope; old delegated tokens are refused. "On behalf of" was first only in the signed token; event and receipt rows now carry a nullable `on_behalf_of` for writes made with a delegated token (events on both backends, receipts on the shared one, where delegation exists), shown in team activity, the timeline and the audit export. The dashboard pages do not draw it yet.*
- [x] **P1-3 The journal and the database cannot disagree silently.** *Change:* at open, fail closed when the database's journal position is ahead of the journal; use full-fsync semantics for control files where the platform has them; an instance lease in the database. *Done: 0.2.0, except the instance lease, moved to P1-4; full-fsync selection is tested but real macOS flush behavior is not.*
- [x] **P1-4 Journal cost stays flat.** The shared profile verifies the whole control journal on every transaction, and every operation intent appends to it. *Change:* cache verified state per tenant; move operation intents to their own compactable log; an instance lease in the database, so a second process with a copied control tree cannot serve the same store. *Done: 0.2.0. Verified journal state is cached per tenant (a request costs under a millisecond at 100,000 records instead of seconds). New operation records go to a separate hash-chained operations log, checked against the anchor, compacted only for segments every operation in which is resolved and which the oldest retained backup holds, with consumed identities kept for ever in a hash-committed index; 1,000 tool operations add 3.9 MB to the journal before and 0 now. The lease co-holds per control tree, refuses another holder for 60 seconds (`control_lease_held`) and guards against accidents, not against someone holding the copy and its key; multi-host deployments must set `--instance-id`. Decided against: signed journal checkpoints so that a cold start verifies only the tail (the cache already made requests cheap, and trading early detection of damage for a three-second cold start is not worth it). Not measured on a production-size store; compaction in the shared profile is an operator command, not a scheduler.*
- [x] **P1-5 A failing journal record can be repaired.** *Change:* apply journal records outside the request deadline; an operator command to inspect and resolve a record that cannot apply. *Done: 0.2.0. Records apply outside the request budget and `journal pending` lists what is stuck; there is deliberately no way to skip a record, which stays a decision for the owner and was decided against: skipping is a security decision (a skipped record may be a revocation or a purge), and restore remains the repair.*
- [x] **P1-6 Smaller hardening.** Restore checks role attributes, not only the role name; a missing tenant and a bad token answer alike; lock and statement timeouts map to `service_busy`; every statement that relies on row-level security also carries a tenant predicate. *Done: 0.2.0. The local daemon also no longer blocks its accept thread while connections wait, and `doctor` explains a clock that was set ahead.*

## Phase 2: find the right memory

- [x] **P2-1 Rank by how informative a match is.** Scoring is the share of query terms present, and each term contributes only its 256 newest matches, so a rare word counts like a common one and an older record matching every term can be crowded out. *Change:* BM25-style scoring with term rarity and length normalisation, driven from the full-text index on both backends; candidate windows chosen by score, not recency. *Done when:* the benchmark includes the crowded-out case and the rare-versus-common case and both pass. *Done: 0.2.0, as configuration `lexical-v2`; existing stores stay on `lexical-v1` until reindexed. Measured on the pooled LongMemEval oracle set (500 questions, 10,866 observations, asked as of each question's date, top eight, no model): session recall 0.556 to 0.770, answer-turn recall 0.564 to 0.782, MRR 0.468 to 0.665.*
- [x] **P2-2 Match word forms.** "retry" does not find "retries". *Change:* stemming applied identically at index and query time on both backends and in the pure scorer; a real stop list. *Done: 0.2.0.*
- [x] **P2-3 Index and quote passages.** A long observation is embedded by its first 256 tokens and excerpted from its first matching word. *Change:* split captures into passages for both the lexical and semantic indexes; return the best passage; keep the observation as the unit of evidence and authorization. *Quoting and long-capture ranking done: 0.2.0 (rule `passages-v1`, computed at query time; ranking stays `lexical-v2`, no schema change, no reindex). The embedding index still embeds an observation's first 256 tokens; `domain.passages.split` exposes the boundaries for P2-5 to reuse.* *Closed: 0.2.0. Passage vectors were then built and measured in P2-5 and scored lower than embedding the opening (session recall at five 0.844 against 0.850), so they stay off by default behind one switch; passages are used for quoting and for rescuing long captures only.*
- [x] **P2-4 One answer per fact.** *Change:* collapse exact and near duplicates and superseded versions at render time; break ties by authority, then recency; show accepted knowledge and unreviewed observations as separate sections with the recorded time. *Done: 0.2.0. A constraint's cited evidence is not folded into it, and an old version that matches while the newest does not is shown as it is.*
- [x] **P2-5 Semantic search on by default and at any size.** The scan is pure Python, takes over a second at 10,000 vectors and is refused above that. *Change:* vectorised exact scan; approximate index on PostgreSQL; a current small local embedder chosen by measurement; enable with one command. *Done: 0.2.0. Measured and chosen: bge-small-en-v1.5 over five other models, a convex combination over reciprocal-rank fusion, a numpy scan bounded at 200,000 vectors with the truncation named, binary vectors through the migration chain, claims embedded, `memoryking semantic enable` and `setup` as the one command (the runtime is still a separate install, by design). Session recall at five 0.820 to 0.850 and preference 0.233 to 0.433 on the pooled oracle set. Not as asked: observations are embedded from their opening, not by passage, because passage vectors measured lower (the passage path is built and tested behind one switch); the PostgreSQL HNSW path was exercised on pgvector 0.6.0, not the pinned 0.8.7, so iterative-scan settings are untested; latency figures come from a loaded shared host.*
- [x] **P2-6 Reranking chosen by measurement.** *Change:* a wider window and a current small cross-encoder if the recall harness shows a gain within the deadline. *Done: 0.2.0. Windows of 16, 32 and 64 and four cross-encoders measured; none earns a change: widening adds at most 0.014 MRR for up to 1.8 s more and worsens preference questions, and the three newer models take 10 to 28 s a window on one loaded thread. The window stays 16 and reranking stays opt-in; the docs' old numbers are replaced. Whether to turn it on by default when installed is left to the owner (the reference gives the measured gain, +0.03 MRR for about a second).*
- [x] **P2-7 Budgets count what the model receives.** *Change:* budget the rendered text; a characters-per-token estimate when no tokenizer is installed; say how many items were left out and the minimum budget. *Done: 0.2.0. A text briefing (and a text resume) is packed against its rendered Markdown; the receipt records `rendered_text`; the default estimate is `chars-estimate-v1` (three ASCII characters a token, conservative for English and code); matches left out and the minimum are named in the text; 256 tokens works for an empty and a small briefing. Measured on the pooled LongMemEval oracle set with the harness's new `--text` option: recall unchanged (session recall at eight 0.812); an exact-tokenizer briefing falls from 14,711 tokens (JSON) to 11,737 (text) and recalled text per real token rises from 3.1 to 3.9 characters. Unverified: the 256-token minimum through the MCP stdio bridge itself (tested through the store and the CLI).*
- [x] **P2-8 Understand time in a question.** *Change:* resolve relative dates in a query to a range and prefer records in it. *Done: 0.2.0. English only, UTC, no model; the boost is 25% of the best score, never a filter except for the new explicit `time_range` (`recall --from/--to`). Same oracle set: `temporal-reasoning` session recall at eight 0.729 to 0.774, overall 0.812 to 0.824; turn-level figures dipped slightly (turn MRR 0.480 to 0.473, turn recall any@5 0.618 to 0.616) because the boost raises every turn of a matching session. Not done: a `time_range` argument on the lean `recall` tool.*
- [x] **P2-9 Reindex for operators.** A shared tenant has no command to start the rebuild into `lexical-v2`, and the local CLI reaches it only through a raw `request`. *Change:* `memoryking reindex` and a shared equivalent, with progress in `status`. *Done: 0.2.0. The call was slow because it reset every projection job in one transaction and then worked for three seconds itself; it now moves the generation on and the jobs are reset in the batches of the rebuild (31 ms at 100,000 observations, 29 ms at 1,000,000, built by direct insert; it was 4.5 s). Found and not fixed: each rewrite batch scans the whole full-text table to delete the rows it replaces (about 0.4 s a batch of 64 at 300,000 observations), so the whole rebuild of a very large store is slow; and `status` right after building the 1,000,000-observation test store exceeded the five-second deadline (not investigated). The estimate in `status` uses the daemon's measured rate, else about 400 observations a second.*
- [x] **P2-10 Briefings that cover what was asked.** The long-history pilot showed one broad `recall` returning 8 items using 3,300 characters of a 6,000-token budget, about half of them one session twice, with the sentence that held the fact missing. *Change:* fold an excerpt that lies inside another (a hook's user-turn capture inside its session capture) into one item at render time; a text briefing holds as many distinct items as fit the budget (up to 32) and the lean `recall` takes `limit`; near-identical statements are capped so different ones still fit; a `UserPromptSubmit` hook recalls for each prompt (bounded, with a deadline and a relevance floor, off with `--no-prompt-hook` or `MEMORYKING_PROMPT_HOOK=off`). *Done: 0.2.0. Offline, seed 7, one broad query, 12 tasks: needles found 14 to 22 of 24 at 200 sessions and 9 to 20 of 24 at 2,000; context cost three to six times higher; recall latency about +12 to +17 ms median; no evidence-recall metric falls. Folding is at render time, not capture time, so both records stay verbatim and stores that already hold both are fixed too. The relevance floor (300,000 of 1,000,000) was set on the LongMemEval sample, not on the benchmark, and is a small synthetic check; no real agent session, so how a model uses the prompt-time briefing is unmeasured. The benchmark's `memoryking` arm is left without the prompt hook (its protocol was fixed without it); whether S1 gets a variant with it is the owner's decision.*

- [x] **P2-11 What the hooks show an agent at 200 and 2,000 sessions.** *Problem:* in the long-history record (seed 11, real agents) the prompt-time hook carried the needed sentence for 20 of 24 needles at 20 sessions but 2 at 200 and 1 at 2,000, the start briefing 9 of 72, and 16 of MemoryKing's 18 failures were "never surfaced"; the injection read as a complete answer and agents called `recall` in 10 of 36 runs. *Change:* an offline measure (`tools/longhaul_benchmark.py hookprobe`: needle sentences carried by the prompt hook, the start briefing, one `recall` for the prompt and one for a careful agent's query, with characters and hook time); the mechanism read from failing cases; a prompt named a file and every record that mentioned it tied on the anchor score, newest first, and the harness's scope sentence lowered every score under the floor; so anchors now combine with the word score (ties by word score), words nothing in the project holds no longer count against a match, the hook fills 2,000 tokens with the closest 32 records cut to their particular sentences, shows a session once, and says how many more matched and to call `recall` with specific words. *Done: 0.2.0, offline only.* Needles carried by the prompt hook on development seeds 1 to 5: 14% to 100% at 200 sessions, 0% to 41% at 2,000, 89% to 100% at 20; seed 11 (seen): 12% to 100%, 0% to 54%; seed 12 (held out, scored once): 8% to 100%, 0% to 42% ([record](../benchmarks/longhaul/results/2026-11-22-offline-hook-p2-11.md)). Cost: up to about 1,900 tokens on each prompt that finds something (about 830 before) and about 0.1 s more hook time (0.28 to 0.38 s at 2,000 sessions; deadline 1.5 s); at 1,200 tokens it carries 82% and 20%. Whether the hook stays on by default is the owner's decision: with it the agents at 200 sessions in the real run passed 1 of 6, without it 4 of 6 in the pilot, because they called `recall` themselves; the new text is honest about being partial and asks for `recall`, but nothing measures that an agent now does. Not done: a start briefing chosen by anything but recency (the store keeps no kind of statement to prefer, and selection by text is ruled out). *Real-agent re-run (seed 13, 96 sessions; [record](../benchmarks/longhaul/results/2026-11-22-t1-remeasure-033a9f0.md)):* MemoryKing passed 12 of 12 at 200 sessions (3 of 12 before, on another seed) and 4 of 12 at 2,000 (4 before), against `log` 11 and 8, the notes file 12 and 0 and the no-hook variant 12 and 2; the hook carried 24 of 24 needles at 200 sessions and 5 of 24 at 2,000 as predicted, but the no-hook variant also passed 12 of 12 at 200, no paired comparison is distinguishable after correction (hook against no hook 2 tasks to 0, p 0.50), and the 2,000-session weakness remains.

- [x] **P2-13 Finding and presenting the right record in a very large history.** *Problem:* in the real-agent re-measure (seed 13) MemoryKing passed 12 of 12 tasks with 200 seeded sessions of history and 4 of 12 with 2,000, where a grep-able raw log passed 8;
