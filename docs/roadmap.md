# Roadmap

This page lists the planned improvements to MemoryKing and where each one stands. It is a plan, not a development log: an item states the problem, the change and how to tell it is done, and nothing else.

Status: `[ ]` planned · `[~]` in progress · `[x]` done. A done item names the release that carries it. Items inside a phase are in priority order, and phases are worked top to bottom unless an item says otherwise.

Every change keeps the existing invariants: observations stay verbatim evidence, nothing becomes accepted knowledge without an authorized decision, every delivery has a receipt, purge follows dependencies, and a restore creates a new history. A change that needs one of these relaxed is out of scope until this page says so.

| Phase | Goal | State |
| --- | --- | --- |
| 0 | Remove the defects that stop normal use at modest size | done, unreleased |
| 1 | Harden credentials, delegation and the control journal | in progress |
| 2 | Find the right memory: ranking, word forms, passages, semantic search | in progress |
| 3 | Turn evidence into knowledge without a reviewer always present | planned |
| 4 | Make it easy for agents and developers to adopt | planned |
| 5 | Scale and operate it for a team | planned |
| 6 | Prove it on recall and on real task outcomes | planned |

## Phase 0: remove the cliffs

- [x] **P0-1 Backups work at any store size.** The signed backup manifest lists every blob, so it exceeds the 1 MiB canonical limit at roughly 13,000 observations and the backup fails after copying everything; the scheduled backup then leaves a partial directory each minute (`adapters/local_store.py` `backup`, `adapters/postgres_recovery.py`, `backups.py` `Policy.run`, `contracts/canonical.py`). *Change:* sign a small manifest that carries the hash of a separate blob-index file; verify the index on restore; remove the partial directory and record the failure on any exception; correct the manifest bound in the deployment guide. Existing backups must still restore. *Done when:* a backup and restore round-trips at 20,000 observations in a test, and a failed scheduled backup leaves no directory behind. *Done: unreleased.*
- [x] **P0-2 Captures do not slow down or stall as the store grows.** Advancing the job frontier looks jobs up by position with no index that can serve it (`application/store_core.py` `_advance`), so a drain of 200 jobs takes about 0.1 s at 2,000 observations, 1.1 s at 12,000 and passes the five-second deadline near 29,000, after which captures are refused with `queue_full`. A `reindex` or restore re-queues every job and has the same effect at once. *Change:* add `jobs(tenant,position)` on both backends through the normal migration chain; give the idle probe a tenant predicate; make drain work in batches that each fit the deadline; do not let a reindex backlog refuse captures. *Done when:* a test captures and drains 30,000 observations with drain time per job flat, and a capture straight after `reindex` on 2,000 observations succeeds. *Done: unreleased.*
- [x] **P0-3 Accepted knowledge stays in briefings however many proposals exist.** The registry query takes the first 257 revisions of any state and blocks above 256 (`adapters/knowledge_store.py` `query`), so 17 daily `draft-proposals` runs remove all accepted knowledge from briefings, and the same count of constraint revisions blocks every briefing. *Change:* bound the registry by live accepted revisions (and reviewer-visible diagnostics separately), selected in SQL; rejected, superseded and unreviewed revisions never count toward the bound. *Done when:* a test with 300 unreviewed drafts and 3 accepted claims still returns the 3 claims, and 300 retired constraint revisions do not block. *Done: unreleased.*
- [x] **P0-4 A long task can always be resumed.** Operation listing raises `operation_limit` above 32 operations of any state (`adapters/working.py` `_operations`), so a task's 33rd recorded tool effect makes `resume`, `summarize`, hand-off and the execution snapshot fail. *Change:* return every open operation plus the newest resolved ones up to the bound, with a truncation flag; never raise for resolved history. *Done when:* a test records 40 succeeded operations and resume, summary and hand-off all work and report truncation. *Done: unreleased.*
- [x] **P0-5 `draft-proposals` works through the daemon.** The CLI command returns `invalid_request` because the socket contract does not admit the `draft` action; the tests call the store directly. *Change:* admit the action in the authoritative schema and regenerate; add a socket-level test for every CLI command that lacks one. *Done when:* `memoryking draft-proposals --project P` files drafts against a running daemon in a test. *Done: unreleased.*
- [x] **P0-6 The lean `save_progress` and `resume` tools behave as described.** A save with `findings` always fails (`lean.py` sends a kind the schema refuses); a second save erases next actions, failed attempts, blockers and constraints the caller did not repeat; every resume of a lean checkpoint reads "Blocked: recovery_reconciliation_required" because defaulted sections count as a recovery gap (`adapters/working.py`). *Change:* send a valid kind; merge omitted sections from the previous revision and say so in the tool description; report defaulted sections as a note, keeping the blocked status for real reconciliation gaps. *Done when:* tests cover all three, including `findings`, through the stdio bridge. *Done: unreleased.*
- [x] **P0-7 Session hooks save what matters and nothing secret.** The hooks keep assistant text only, including file bodies passed to write tools, with no redaction; they drop user turns and tool errors; the checkpoint they write replaces the agent's own with the oldest part of the transcript tail; pre-compact followed by session-end fails with `idempotency_conflict` (`host_hooks.py`). *Change:* capture user turns and tool errors, exclude tool inputs, scrub common secret shapes before capture, keep the newest part of the tail, write hook state to its own stream instead of the agent's, key the checkpoint by hook kind. *Done when:* tests show a planted key is not stored, a user instruction is recalled, and an agent-authored checkpoint survives a hook run. *Done: unreleased.*
- [x] **P0-8 Every per-tenant bound has a release path.** Checkpoints, hand-offs and hand-off views (4,096 each) and experience records (10,000) count rows of every state for the life of the tenant, and nothing deletes them; none appears under `status` capacity. *Change:* count live rows; add retention that keeps what history verification needs and removes the rest; report all four under capacity; correct the hints and the reference table. *Done when:* a test saves 5,000 checkpoints across tasks without refusal and plan history still verifies. *Done: unreleased.*
- [x] **P0-9 A scoped constraint does not lock out simple readers.** The lean tools, CLI and hooks always send empty bindings, so one accepted constraint scoped to an environment blocks every recall and resume with `applicability_unknown`, without saying which field is missing. *Change:* let the bridge, CLI and hooks carry session bindings; name the unbound field in the reply; do not let briefing-policy uncertainty block reading a checkpoint the caller wrote, or saving one (the lean save reads the latest checkpoint first, so today a blocked read also refuses the save). *Done when:* tests cover recall, resume and save with and without the binding. *Done: unreleased.*
- [x] **P0-10 The check is deterministic.** One reranker test (`test_rerank_reorders_only_the_fused_window_and_only_when_asked`) and the knowledge demo run by the docs check (`tools/knowledge_demo.py`, `denied` on its first namespace request) each fail intermittently on an unchanged checkout. *Change:* find and remove the nondeterminism in each, in the product if that is where it is. *Done when:* each passes 30 consecutive runs. *Done: unreleased.*
- [x] **P0-11 Small defects found while fixing the above.** `memoryking trust set` without `--key` fails for a glob source because the default key contains `*`; the lean `resume` tool advertises a larger budget than the resume contract accepts; a reviewer cannot list proposals once a project holds more than 256 revisions of any state, because the diagnostic query keeps the unfiltered bound; the changelog lacks entries for P0-3 to P0-7. *Done when:* each has a test or an entry. *Done: unreleased, except the lean `resume` budget, moved to P0-12.*
- [x] **P0-12 Follow-ups from Phase 0.** The lean `resume` tool advertises a larger budget than the resume contract accepts. The reviewer listing of procedures still blocks above 256 revisions, as the knowledge listing did. A resume that returns the caller's own checkpoint while constraints are unresolved omits open operations and the summary, so an uncertain operation is not shown there. `hooks install` does not write session bindings into the installed command. *Done when:* each has a test. *Done: unreleased.*

## Phase 1: credentials, delegation and the journal

- [x] **P1-1 Credentials can be rotated.** A credential is derived only from the store, tenant and principal, so re-issuing after a revoke yields the same token. *Change:* a per-grant generation stored with the grant, checked at authorization, advanced by `credential issue --rotate` and by revoke; optional expiry enforced server-side. *Done when:* a revoked-then-reissued credential differs and the old one is refused. *Done: unreleased, for both profiles, including owner rotation. Revoking one of several grants does not rotate; recovering a lost shared owner credential file is not covered.*
- [x] **P1-2 A delegated token acts for its issuer.** Delegation returns a token whose acting principal is the named subject. *Change:* decide and document the intended model, then keep the delegator as the actor with "on behalf of" recorded, so reader lists, writer ownership and the event actor are evaluated against who really acted. *Done when:* a test shows a delegated token cannot read what only the subject may read. *Done: unreleased. The token is the issuer with a narrower scope; old delegated tokens are refused. "On behalf of" was first only in the signed token; event and receipt rows now carry a nullable `on_behalf_of` for writes made with a delegated token (events on both backends, receipts on the shared one, where delegation exists), shown in team activity, the timeline and the audit export. The dashboard pages do not draw it yet.*
- [x] **P1-3 The journal and the database cannot disagree silently.** *Change:* at open, fail closed when the database's journal position is ahead of the journal; use full-fsync semantics for control files where the platform has them; an instance lease in the database. *Done: unreleased, except the instance lease, moved to P1-4; full-fsync selection is tested but real macOS flush behavior is not.*
- [x] **P1-4 Journal cost stays flat.** The shared profile verifies the whole control journal on every transaction, and every operation intent appends to it. *Change:* cache verified state per tenant; move operation intents to their own compactable log; an instance lease in the database, so a second process with a copied control tree cannot serve the same store. *Done: unreleased. Verified journal state is cached per tenant (a request costs under a millisecond at 100,000 records instead of seconds). New operation records go to a separate hash-chained operations log, checked against the anchor, compacted only for segments every operation in which is resolved and which the oldest retained backup holds, with consumed identities kept for ever in a hash-committed index; 1,000 tool operations add 3.9 MB to the journal before and 0 now. The lease co-holds per control tree, refuses another holder for 60 seconds (`control_lease_held`) and guards against accidents, not against someone holding the copy and its key; multi-host deployments must set `--instance-id`. Decided against: signed journal checkpoints so that a cold start verifies only the tail (the cache already made requests cheap, and trading early detection of damage for a three-second cold start is not worth it). Not measured on a production-size store; compaction in the shared profile is an operator command, not a scheduler.*
- [x] **P1-5 A failing journal record can be repaired.** *Change:* apply journal records outside the request deadline; an operator command to inspect and resolve a record that cannot apply. *Done: unreleased. Records apply outside the request budget and `journal pending` lists what is stuck; there is deliberately no way to skip a record, which stays a decision for the owner and was decided against: skipping is a security decision (a skipped record may be a revocation or a purge), and restore remains the repair.*
- [x] **P1-6 Smaller hardening.** Restore checks role attributes, not only the role name; a missing tenant and a bad token answer alike; lock and statement timeouts map to `service_busy`; every statement that relies on row-level security also carries a tenant predicate. *Done: unreleased. The local daemon also no longer blocks its accept thread while connections wait, and `doctor` explains a clock that was set ahead.*

## Phase 2: find the right memory

- [x] **P2-1 Rank by how informative a match is.** Scoring is the share of query terms present, and each term contributes only its 256 newest matches, so a rare word counts like a common one and an older record matching every term can be crowded out. *Change:* BM25-style scoring with term rarity and length normalisation, driven from the full-text index on both backends; candidate windows chosen by score, not recency. *Done when:* the benchmark includes the crowded-out case and the rare-versus-common case and both pass. *Done: unreleased, as configuration `lexical-v2`; existing stores stay on `lexical-v1` until reindexed. Measured on the pooled LongMemEval oracle set (500 questions, 10,866 observations, asked as of each question's date, top eight, no model): session recall 0.556 to 0.770, answer-turn recall 0.564 to 0.782, MRR 0.468 to 0.665.*
- [x] **P2-2 Match word forms.** "retry" does not find "retries". *Change:* stemming applied identically at index and query time on both backends and in the pure scorer; a real stop list. *Done: unreleased.*
- [~] **P2-3 Index and quote passages.** A long observation is embedded by its first 256 tokens and excerpted from its first matching word. *Change:* split captures into passages for both the lexical and semantic indexes; return the best passage; keep the observation as the unit of evidence and authorization. *Quoting and long-capture ranking done: unreleased (rule `passages-v1`, computed at query time; ranking stays `lexical-v2`, no schema change, no reindex). The embedding index still embeds an observation's first 256 tokens; `domain.passages.split` exposes the boundaries for P2-5 to reuse.*
- [x] **P2-4 One answer per fact.** *Change:* collapse exact and near duplicates and superseded versions at render time; break ties by authority, then recency; show accepted knowledge and unreviewed observations as separate sections with the recorded time. *Done: unreleased. A constraint's cited evidence is not folded into it, and an old version that matches while the newest does not is shown as it is.*
- [ ] **P2-5 Semantic search on by default and at any size.** The scan is pure Python, takes over a second at 10,000 vectors and is refused above that. *Change:* vectorised exact scan; approximate index on PostgreSQL; a current small local embedder chosen by measurement; enable with one command.
- [ ] **P2-6 Reranking chosen by measurement.** *Change:* a wider window and a current small cross-encoder if the recall harness shows a gain within the deadline.
- [x] **P2-7 Budgets count what the model receives.** *Change:* budget the rendered text; a characters-per-token estimate when no tokenizer is installed; say how many items were left out and the minimum budget. *Done: unreleased. A text briefing (and a text resume) is packed against its rendered Markdown; the receipt records `rendered_text`; the default estimate is `chars-estimate-v1` (three ASCII characters a token, conservative for English and code); matches left out and the minimum are named in the text; 256 tokens works for an empty and a small briefing. Measured on the pooled LongMemEval oracle set with the harness's new `--text` option: recall unchanged (session recall at eight 0.812); an exact-tokenizer briefing falls from 14,711 tokens (JSON) to 11,737 (text) and recalled text per real token rises from 3.1 to 3.9 characters. Unverified: the 256-token minimum through the MCP stdio bridge itself (tested through the store and the CLI).*
- [x] **P2-8 Understand time in a question.** *Change:* resolve relative dates in a query to a range and prefer records in it. *Done: unreleased. English only, UTC, no model; the boost is 25% of the best score, never a filter except for the new explicit `time_range` (`recall --from/--to`). Same oracle set: `temporal-reasoning` session recall at eight 0.729 to 0.774, overall 0.812 to 0.824; turn-level figures dipped slightly (turn MRR 0.480 to 0.473, turn recall any@5 0.618 to 0.616) because the boost raises every turn of a matching session. Not done: a `time_range` argument on the lean `recall` tool.*
- [x] **P2-9 Reindex for operators.** A shared tenant has no command to start the rebuild into `lexical-v2`, and the local CLI reaches it only through a raw `request`. *Change:* `memoryking reindex` and a shared equivalent, with progress in `status`. *Done: unreleased. The call was slow because it reset every projection job in one transaction and then worked for three seconds itself; it now moves the generation on and the jobs are reset in the batches of the rebuild (31 ms at 100,000 observations, 29 ms at 1,000,000, built by direct insert; it was 4.5 s). Found and not fixed: each rewrite batch scans the whole full-text table to delete the rows it replaces (about 0.4 s a batch of 64 at 300,000 observations), so the whole rebuild of a very large store is slow; and `status` right after building the 1,000,000-observation test store exceeded the five-second deadline (not investigated). The estimate in `status` uses the daemon's measured rate, else about 400 observations a second.*

## Phase 3: evidence into knowledge

- [x] **P3-1 Review from the terminal and from chat.** *Change:* `memoryking review list|accept|reject`; a lean tool that lets an agent present a proposal for the user to confirm. *Done: unreleased.* `review list|show|accept|reject` (plus `--as constraint`, `retire-approve`, `retire-dismiss`) and the lean `propose` and `confirm` tools; `confirm` is off unless the bridge starts with `--allow-chat-review`. Not done: a TTY prompt or interactive review loop.
- [x] **P3-2 A labelled tier between raw notes and accepted knowledge.** *Change:* agent-extracted facts that briefings may include, always marked unreviewed, never as constraints, on by policy per project. *Done: unreleased.* `memoryking unreviewed on|off|show` (journaled admin policy, default off); drafts appear in query briefings only, at most three, never in the session start or a historical or attested briefing. Eligibility is a whitelist of provenance methods (consolidation, `propose`, repeated evidence); a hand-written proposal without a method is not shown. Not measured: whether agents act better or worse with the section present.
- [x] **P3-3 Background consolidation that drafts, never accepts.** *Change:* an opt-in pass, under the egress policy, in which a model drafts claims from recent evidence; every claim must cite spans that exist verbatim; drafts enter the existing proposal lifecycle; contradictions with accepted claims are filed as conflicts. *Done: unreleased.* `memoryking consolidate` (one pass, or `--watch`) and the opt-in `serve --consolidate-every`; knowledge actions `consolidate_prepare` and `consolidate_admit`; `memoryking health` counts drafts by method. Left out: checkpoints are not fed to the model (a claim must quote an observation, and a checkpoint is not one); the pass runs as the consolidating principal, so a record visible only to another principal is passed over. Unverified: draft quality against any real model, since no model was called; the injection defence is structural and tested with a scripted adapter only.
- [x] **P3-4 Corrections.** *Change:* `supersedes` on capture; lean `correct` and `forget` that file a retirement with the usual authority; a superseded record stops appearing beside its replacement. *Done: unreleased.* `supersedes` on capture and lean `remember`, lean `correct` and `forget`; retirement is a request that only an admin approves (a reviewer can dismiss). A superseded record is hidden only from briefings; catalog, graph, fetch and resume still show it.
- [x] **P3-5 A session start that needs no query.** *Change:* constraints, pinned items, the latest checkpoint and recent decisions, within a budget. *Done: unreleased.* `recall --start`, the hook default and `pin add|remove|list`. Decisions are recognised by source name (`decision`, `instruction`, `user`, with an optional `-` or `_` suffix), not inferred from text; quality on real sessions is unmeasured beyond a 50-session synthetic test.
- [x] **P3-6 Procedures learned from outcomes.** *Change:* draft procedures from repeated successful and failed attempts recorded in checkpoints, into the same review lifecycle. *Done: unreleased.* The deterministic drafter (`repeated_outcome_v1`) runs inside `draft-proposals`. Left out: the optional model drafting of procedures in consolidation. Limits: a checkpoint's `failed_attempts` carry no evidence of their own, so the proposal cites the observations the checkpoints reference, and an avoid procedure needs success evidence from a recorded successful outcome in the same tasks (a procedure cannot be filed without it), so a project that records no outcomes gets no procedure drafts. Draft quality on real work is unmeasured.

## Phase 4: adoption

- [x] **P4-1 One command to connect a host.** *Change:* `memoryking setup <host> --project P` creates the store if needed, starts the daemon, issues a credential with the capabilities the tools need, registers the lean MCP profile and installs hooks under the same principal; the bridge starts the daemon when it is not running. *Done: unreleased. For Claude Code the registration command is printed, not written, because its MCP file format is not documented in this repository; Codex's `config.toml` block and both hosts' hook files are written. Tested on Linux with real processes; not exercised on macOS or against the real hosts.*
- [x] **P4-2 A small, standard MCP surface.** *Change:* lean is the default profile; unused schema definitions are pruned from the full catalog; replies return Markdown as content with the envelope as structured content; lean is served over HTTP; current protocol revisions are accepted; server instructions say when to recall and remember. *Done: unreleased. The full profile's text block stays canonical JSON (replay is byte-exact on it) and gains no `structuredContent`; only lean changed shape. The stateless `2026-07-28` revision is served over shared HTTP (tested against the pinned `mcp` 2.3.0) but not by the hand-written stdio bridge, which negotiates the four handshake revisions; stdio support for the stateless revision is not done.*
- [x] **P4-3 Lean tools to follow up.** *Change:* `fetch` a cited source, give `feedback`, list recent memory. *Done: unreleased. `confirm` is omitted from the catalog unless chat review is enabled; `propose` stays. Tested over the local bridge and shared HTTP, not against a real host.*
- [x] **P4-4 Errors a model can recover from.** *Change:* validation failures name the failing field and the allowed values as tool results; denials name the missing capability. *Done: unreleased. Covers the bridge, the wire and the CLI; the shared HTTP operations endpoint's own error bodies were not changed.*
- [x] **P4-5 Client libraries.** *Change:* `client.remember()` and `client.recall()`; an async Python client; a TypeScript client published with the contracts. *Done: unreleased. The Python methods wrap the lean tools' shared implementation and the async clients run the sync client on worker threads (no native asyncio transport); `@memoryking/client` (`packages/client`) is ready to publish but not published, and `supersedes` on `remember` waits for P3-4. The local daemon's loopback endpoint serves retrieval only, so the TypeScript client can `recall` there but writes need the shared service or the MCP bridge; a local write endpoint would be a bearer `POST` on the dashboard listener that reuses the socket's operation table (`context`, `capture`, `working`, `handoff`) with the same bounds, host, origin and cookie refusals and tests for each, after which the TypeScript local client could drop its history-id option. The TypeScript write operations are tested against a real shared service only where PostgreSQL is available.*
- [x] **P4-6 Memory about the user, across projects.** *Change:* a user scope readable from every project the user's agents work in, with the same review and receipt rules. *Done: unreleased. The scope is the reserved project `_user_<principal>` and "agent A acts for user U" is a journaled grant on it, so no schema change or migration was needed; `*` grants never match it. Not done: the unreviewed tier can be switched on for a user scope by its user but its drafts are not yet carried into other projects' briefings, and PostgreSQL row-level security cannot enforce the per-user rule (it is per tenant). Decision for the owner: administrators cannot read user scopes; letting them would be a one-line change in the authorization query.*
- [x] **P4-7 Framework adapters.** *Change:* thin adapters for the common agent frameworks, each with a runnable example. *Done: unreleased. Adapters for the Claude Agent SDK, the OpenAI Agents SDK, LangChain/LangGraph, LlamaIndex and plain function calling, in `memoryking.integrations`, each with an example that needs no model. Exercised against the real framework classes and a real store (no model called) with `claude-agent-sdk` 0.2.187, `openai-agents` 0.25.0, `langchain-core` 1.8.4, `langgraph` 1.2.24 and `llama-index-core` 0.14.26; the function-calling helper is in the main suite and the rest skip when their framework is absent. Left out: pinned optional extras and locks (frameworks are installed by the user), an Agents `Session` (MemoryKing is not a transcript store), and a live-session test of the Claude Agent SDK `SessionStart` hook. No real model has driven any adapter.*
- [~] **P4-8 Wider runtime support.** *Change:* newer Python versions; Windows after a qualification pass. *Python 3.13 done: unreleased. The hash-pinned lock files already installed on it; the only code blocker was the `doctor` version check. The full suite (690 tests, 78 PostgreSQL cases skipped in that run) and the PostgreSQL suites passed on 3.13 in a scratch environment; `tools/local_ci.py` has no version matrix and still runs the pinned 3.12 only. Python 3.14 was not run (no interpreter available) and is not claimed. Remaining: Windows. The qualification pass is written up in the reference; a port needs a platform lock and fsync module so the code imports without `fcntl`, a named-pipe or loopback-with-secret transport in place of the Unix socket, an ACL-based owner-only check in place of modes and `getuid`, a decision on directory-fsync durability, retries for `os.replace` and unlink of open files, handle-based symlink-safe reads in place of `O_NOFOLLOW` and `dir_fd`, a stop mechanism in place of SIGTERM, `encoding="utf-8"` on text files, Windows hook quoting, and a Windows machine to test on.*
- [x] **P4-9 Hosts use memory without being told how.** *Problem:* in the first real run of the task-outcome benchmark the MCP arm saved nothing in 10 of 10 sessions (the host lists tools by name and loads a schema only when the model fetches it) and the one failure of the CLI arm never saved what it was told; the run also had no hooks, though the intended setup installs them. *Change:* tools that stay loaded in Claude Code, a start briefing that names the tools and carries the user's recent words and how the last session ended, a note for command-line agents that says to save as you go, and a benchmark arm that installs what `setup` installs. *Done: unreleased, offline only.* `alwaysLoad` (server option and per-tool `_meta`), the start note, the `user-<host>` capture and the new start-briefing items are built and tested (a deterministic replay of synthetic Claude-Code-shaped sessions through the hooks shows each of the four knowledge kinds in the next session's start text; before the change it showed none), arm `setup` and `report --rep` are in the harness and its stub pipeline. *Measured: unreleased.* The second real run (Claude Code 2.1.330, model `sonnet`, 5 arms x 10 tasks x 3 repetitions, commit 2954501, `benchmarks/outcomes/results/2026-11-21-claude-sonnet-5-5-2954501.md`) shows that installed as `setup` installs it the hooks fire and their briefing is injected, the tools are in the tool list with no search step, and something is saved in every run; with no mention of memory in the prompt, `setup` passed 27 of 30 runs (10 of 12 on the four knowledge tasks) against 16 of 30 (0 of 12) with memory off, though a notes file did as well (26 of 30, 11 of 12) and tokens rose by about 109,000 per run. Fixed after that run: a lean reply is its text alone (no `structuredContent`, no `outputSchema`): a `recall` or `resume` is the briefing plus one trailer line (receipt, status, warnings, how to `fetch`), so every host shows it once; `capture` also takes `--file`, and the command-line note shows the file form first because the host refused a heredoc with braces and quotes in a one-session probe; the start briefing and the lean briefing reproduce code-like literals exactly (checked on the `staging-collector` runs, so that failure was the agent's choice, and nothing was changed). A follow-up check of 4 runs (arm `mcp`, the four knowledge tasks, one repetition) passed 4 of 4 with the briefing in the text block the model received; that confirms the mechanism, not an effect size. Left out and unverified: the CLI arm and the file-form note were not re-run with a real agent, and Codex and Grok have no verified way to keep tools loaded. *Done: unreleased.*

## Phase 5: scale and operations

- [~] **P5-1 Briefings do not serialise a tenant.** *Change:* retrieval under the shared gate; embedding and reranking outside the lock with a short re-validation; batched visibility checks. *Done: unreleased: PostgreSQL gate sharing, models outside the gate, batched visibility. The rerank re-validation is a whole fresh decision after the model returns (a second pass over the candidates, only for briefings that ask for a model), not a short re-check. Blob reads stay per candidate because scoring needs the text. Not done: a separate read connection for the local profile. A local briefing is CPU-bound Python that also writes a receipt, so a reader would overlap only fsyncs while adding a second connection under the single-owner and anchor rules. Measured on a shared development machine, not a production envelope; PostgreSQL 16, not 18.*
- [~] **P5-2 Reads are not durable writes.** *Change:* group commit; persist the anchor on position change and on a timer; connection checks once per pooled connection. *Done: unreleased: a request that committed nothing writes no anchor and takes no commit serial; writers share one anchor write; connection checks are cached for five seconds; an MCP request makes one context decision. Every committing request is still anchored before release (strict by default); the timer is the opt-in `--anchor-interval-ms`, off by default, with its two costs documented. Not done: group commit of the SQLite commit itself. Each local commit still fsyncs under `synchronous=FULL` inside the store lock; sharing one WAL fsync between writers needs `synchronous=NORMAL` plus an external fsync before acknowledging, which changes the durability contract and needs fault-injection evidence for the WAL.*
- [x] **P5-3 Retention for tables that only grow, and the indexes their scans need.** Two bounds still release only by purge: structured-plan revisions and long ordinary streams count toward the 4,096 checkpoints (shrinking the per-stream window needs an explicit history-incomplete marker), and the latest revision of each experience record never expires by age. *Change:* decide both, then implement. *Done: unreleased. Both decisions implemented: above 80 percent of the checkpoint bound an ordinary stream keeps its newest 32 revisions and reports `history_complete: false` (plans keep everything); feedback and shadow records older than 365 days that nothing names lose their bodies (other kinds never expire). Events, idempotency tombstones and operation intents are kept on purpose and only indexed. Measured on SQLite synthetic rows, not under production load; the shared migration was exercised on PostgreSQL 16, not 18.*
- [x] **P5-4 Backups without stopping the service.** *Change:* incremental, content-addressed backups taken without the store lock; a sharded blob directory; reindex in batches outside the deadline. *Done: unreleased. Reindex in batches was already done under P2-1. - [x] **P6-2 Task outcomes with memory on and off.** *Change:* an executable coding-task benchmark run with and without MemoryKing, reporting success, tokens and time. *Harness built: unreleased.* Ten two-session tasks with hidden checks, `tools/outcome_benchmark.py`, a stub agent for offline pipeline tests and the run protocol in `benchmarks/outcomes/RUNNING.md` are in place and validated without a model.
