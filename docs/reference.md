Use the [agent guide](agent-guide.md) for workflows and [deployment guide](deployment.md) for setup. This page maps implemented interfaces and their limits; schemas and `--help` provide exact required fields.

The local CLI reads `{"operation":"NAME","args":{...}}` from stdin. Shared operations add top-level `"version":1`. Structured domain commands inside `args.command` carry their own version, current `incarnation`, action and project-scoped arguments; mutations also require a stable key. Use current context values, not copied example history IDs.

The `grant` operation takes `principal`, `project`, `capabilities` and optional `starts`, `expires` and `rotate`, and returns the principal's credential. With `rotate: true` every earlier credential of that principal is refused (`credential_replaced`); without it an unchanged grant returns the current credential. Revoking a principal's last grant does the same. `grant` never grants `admin`; the shared operator credential is rotated with `memoryking.shared rotate-owner`. See [rotating credentials](deployment.md#rotating-credentials).

## Feature behavior

**Knowledge.** Observations can be recalled without a model. Claims remain proposals until reviewed. Acceptance, quarantine, deprecation, attestation and partial replacement are explicit versioned actions. Constraint resolution is complete within its bounds and blocks on ambiguity, missing essential evidence or unknown applicability.

**Working state.** Checkpoints preserve hard constraints, failures, verification and next actions. Expected revisions prevent stale writers from overwriting newer state. A save with `readers: null` (the client default) keeps the stream's current readers; the first save is readable by its writer alone. Handoffs are recipient-bound. Operation intent/transition/reconciliation records track uncertain effects; the host implements the actual external tool and readback. Session summaries (`summarize`, hand-off, idle) are derived artifacts with their own receipt: the deterministic `extractive-v1` method quotes only the checkpoint, and a provider-written summary is admitted only as the exact reply in a delivered egress audit record. Resume packets and task cards carry the latest summary visible to the reader.

**Host hooks.** `memoryking hook` reads user turns, assistant text and tool errors (never tool-call inputs; successful tool results are compared in memory and never stored), stores the conversation and the tool errors as separate observations (the errors, and each run of 12 or more words of at least 72 characters that a turn copied from a tool result of the same session, under source `<host>-tool`, third-party text the automatic views leave out), replaces secret-shaped values with `[REDACTED]` and reports the count (best effort, not a guarantee), and writes checkpoints to the `<task>--mkhook` stream keyed per hook kind. The two save hooks also keep a sentence of the user's own turns that states a standing personal preference for every project (a first-person stance plus the user's own `in all my projects` or `whatever the project`, nothing tying it to this project; `memoryking.domain.preference`) in the user scope the credential acts for, as an observation with source `user-<host>-preference`, at most five per capture, one record per sentence, unreviewed evidence labelled "recognised from what you said, not reviewed" in the start briefing; nothing is kept for a credential that acts for no user, when the user's turns were held, or with `--no-user-preferences` or `MEMORYKING_USER_PREFERENCES=off`. The `prompt` hook (Claude Code and Codex, `UserPromptSubmit`) stores no memory: it asks for a briefing with the prompt as the query (the closest 32 records with `min_score_ppm` 300,000 that share two searchable words with it), shows as many as fit 2,000 tokens, each cut to its particular sentences when they do not all fit whole, says how many more matched and names `recall` for a specific fact, all within a 1.5-second deadline, and prints nothing when no record clears the floor. Records are shown newest first, each with its observed day, under one line saying that the later of two disagreeing records is current unless it says otherwise (when four or more are listed and the query's neighbouring words are side by side in some of them and not in others, those are marked `holds` with the phrase and the line says how many; the hook's budget keeps marked records first); up to three records of the user's own memory that share a searchable word with the prompt join them (a second lookup, in parallel, under the credential's own user link); and third-party records (sources `tool`, `web`, `fetch`, `<host>-tool`) are left out unless `--third-party` or `MEMORYKING_HOOK_THIRD_PARTY=1`. Details are in the agent guide.

**Resume status.** `blocked`, `budget_insufficient` and `incomplete` resumes carry a `reason`. `incomplete` (`recovery_reconciliation_required`, with `recovery_gaps`) is reserved for unresolved operations, unavailable artifacts, dirty state without artifacts and writer-declared gaps; `defaulted:<section>` entries in `capture.gaps` only produce `unrecorded_sections` on a `ready` packet. The lean `save_progress` tool carries omitted sections over from the stream's latest revision. A `blocked` resume whose reason is `applicability_unknown` (a mandatory constraint depends on a binding field the caller did not supply) names the fields in `unbound_fields` and, for a direct `resume`, still carries the checkpoint the caller may read, with the stream's operations (`operations_truncated` as for any resume, so an effect that may not have happened is visible) and the latest summary the reader may see, and no constraints; consumers must treat the packet as blocked. Briefings name the same `unbound_fields` and the Markdown says "Missing binding fields". Other block reasons carry no checkpoint. Session bindings (`--binding key=value`, `MEMORYKING_BINDINGS`, a profile's `bindings`) supply the fields to the lean tools, the CLI and the hooks; see the [agent guide](agent-guide.md#session-bindings-telling-the-tools-where-you-work).

**Repository context.** Registration and snapshots are trusted-host operations. Git/dirty artifact identity and supported passive source projections inform dependency checks. No repository code is executed. Shallow or incomplete ancestry and unsupported coverage remain unknown rather than current.

**Dashboard.** Task activity, criteria/history, current authorized evidence, force-directed graph/list, source impact, receipts, usage inspection, review and retention previews are implemented. Nodes and counts represent bounded visible results, not the whole corpus. Layout distance is not confidence. In the memory graph, colour is the recorded authority of each node (observation, accepted, proposed, quarantined, rejected or deprecated, mandatory constraint, attestation, procedure, working state) and size grows with the number of the viewer's own retained receipts that cited the record; selecting a node lists those receipts and opens one in Retrieval history. A reviewer sees proposed and quarantined claims in the graph; a reader sees accepted ones only. On a phone the sidebar becomes a bar, cards stack and the graph shows its list unless the drawing is requested. The crowned cybernetic elephant has an optional 1.8-second depth tilt, with a static fallback when reduced motion is enabled. The animation stops when hidden or offscreen. Gunmetal panels, subtle CSS textures and cyan accents are available in dark and light themes; assets are served locally. Ordinary use requires no development reports.

**Procedures and learning.** Procedures require separate review and activation. Outcomes and helpfulness are actor reports tied to evidence/receipts. Feedback ranking is disabled by default; an administrator may run a frozen bounded comparison and explicitly activate or roll back a configuration. It cannot add candidates, override policy or prove a causal quality improvement. There is no autonomous learner or scheduler.

## Optional capabilities

| Capability | Enablement | Boundary |
| --- | --- | --- |
| Exact token counting | Install `requirements-tokenizers.lock`; request `cl100k_base`. | Missing runtime is explicit. Without it the default is `chars-estimate-v1`, a disclosed estimate of one token per three ASCII characters plus one per other character: conservative for English prose (about four characters per token) and code (three to three and a half), so a budget counted with it is not exceeded by the real count. `utf8-byte-estimate-v1` (one token per byte) stays selectable. |
| Local semantic retrieval | On once installed: the core install carries the libraries (onnxruntime, numpy, tokenizers) and `memoryking setup` downloads the pinned model, verifies it, restarts the daemon so it loads the model, and switches the project on (`--no-semantic` skips; `memoryking semantic enable [--project P]` does the same later or retries a failed download). The daemon then indexes projects in the background and embeds every briefing's query. A daemon that finds an installed model loads it without a flag, and enables each new project that has memory. `semantic status` and `status` show progress. | Keyword retrieval is the fallback whenever the libraries, the model or the project's index is absent, and the receipt's trace says which (`reason`: `no_model_loaded`, `project_not_enabled`, `query_embedding_failed`); `status` and `doctor` say why no model is loaded. The libraries are imported only when a model loads, so an install made with `--no-deps` or a platform without a wheel for one of them serves keywords. The one network request semantic search makes is the model download at `setup` or `semantic enable`, printed first (model, size, licence, host, pinned revision) and verified against pinned SHA-256 values; nothing is fetched afterwards and nothing is sent but the file requests. A purge removes the vectors with the records they came from. |
| Local reranker | Libraries are in the core install; install the pinned cross-encoder once with `python -m memoryking.model_install --model reranker --destination DIR`, start `serve --reranker-model DIR` (or `reranker_model` in a profile), and ask for it per briefing: `rerank: "on"`, `recall --rerank`, lean `recall(rerank=true)`. | Off unless requested. Reorders the top 16 fused candidates only; never admits, removes or re-authorizes a record; a model failure keeps the fused order and the trace says so. No egress. |
| pgvector (HNSW) | Reviewed extension in its dedicated schema, explicitly enabled by an operator with `enable-vector`, which also builds an HNSW index over a converted copy of the vectors. | Shared only. The index shortlists up to 1,000 candidates, eligibility is applied to them, and the survivors are rescored exactly; when fewer than 64 survive (a reader who can see little of a large partition) the exact, eligibility-first scan answers instead, so the index can make a search faster but never emptier. Without the extension the numpy scan runs in the service process. Missing or wrong extension returns unavailable for an explicit `pgvector_exact` request. |
| Adapter deltas | Retain a matching authorized base through the resume adapter. | Transport optimization; full model context is reconstructed. No automatic model-token savings claim. |
| Source-backed compilation | `processing` commands; deterministic extraction by default. | Candidate text must preserve validated whole source units and essential state or fall back. Remote generation is not included. |
| Feedback ranking | Explicit proposal, evaluation and activation. | Bounded development experiment; disabled by default. |
| Model providers | `serve --egress-policy FILE` naming providers, models, hosts and classification ceilings; the host builds adapters from the same file. | Off by default: only the local recorder is accepted. Enforced by the daemon at permit time; every dispatch is audited for 30 days. One HTTPS request per dispatch, no retry, no streaming, no provider-side state. |

`memoryking setup` runs it by default; `memoryking semantic enable` is the same job on its own: it checks the libraries, states what it will download (the model, its size and licence, the host and the pinned revision), downloads into `~/.memoryking/models` (`MEMORYKING_MODELS` overrides), verifies every file against the SHA-256 in the [model manifest](../src/memoryking/adapters/models/bge-small-en-v1-5-onnx.json), restarts the daemon of the profile so it loads the model, and enables the project. Nothing is loaded from the model repository's Python code. `python -m memoryking.model_install --destination DIR` remains for an installation by hand, and `serve --embedding-model DIR` (or `embedding_model` in a profile) for a model outside the models directory. `--no-semantic` on `serve` and `setup` opts out. If the download fails, setup finishes on keyword search and names the retry; a file that fails its SHA-256 is discarded with the rest of its staging directory, so a half-downloaded model is never loadable. The `embeddings` extra (`memoryking[embeddings]`) remains for compatibility and adds nothing. In the local container image the models directory is `/data/models`; the shared image carries the libraries and no model (see the [deployment guide](deployment.md#shared-postgresql)). Review the licence and network requirements of the model host before running setup, or opt out.

The vectors are 384-dimensional; the default model reads up to 512 tokens of each input and the truncation is disclosed. The daemon completes each enabled project's indexing jobs through the ordinary claim and complete path using its own owner credential, and embeds the query of any briefing that did not supply a `dense` request; an explicit request is never overridden. Accepted claims are embedded as well as observations (after the observations of a project), so reviewed knowledge can be found by meaning; a claim's vector is only ever looked up for claims the reader's briefing already found eligible. The embedding API and the one-shot worker (`--model`, `--credential`, `--project`, `--socket` or `--shared-url` with `--tenant`/`--ca-file`) remain available for the shared profile and for external indexing. Installing a runtime does not provision a provider account or authorize remote egress.

Each observation is embedded as one unit, its first 512 tokens. That is not yet passage-level: a long capture is embedded by its opening, and a passage index (roadmap P2-3) would replace the unit without changing the storage, which already keys a vector by kind, subject and part.

## Current limits

| Area | Implemented bound / behavior |
| --- | --- |
| Local request | 256 KiB wire body; 64 KiB captured text; one request per socket connection; up to eight connections served concurrently, more wait up to five seconds (up to 16 waiting at once, each on its own thread, so they wait together) and then receive `service_busy`; connections beyond that bound receive it at once. |
| Shared request | Every HTTP, MCP and dashboard request carries one five-second budget from its first byte: waiting for a pooled connection, the connection checks and every statement in the request's transactions stop at that deadline, so a saturated pool or a slow query returns `service_busy` or `service_unavailable` inside the budget rather than after it. A lock timeout, statement timeout or cancel, deadlock or serialization failure inside a transaction answers `service_busy` with 429 (a warning is logged with the SQLSTATE only); a saturated pool answers it with 503. A request for a tenant that does not exist answers exactly as a credential that does not verify does (400 `invalid_token`). |
| Query | Up to 32 distinct searchable terms (about 120 common function words are not searchable; word forms count as one term). Longer queries are searched on their leading terms and the receipt diagnostics record `query_terms_truncated`. |
| Reranker window | The cross-encoder reorders at most the top 16 fused candidates per briefing, one call of at most 16 pairs, 256 tokens per pair with the text cut first, on up to four CPU threads; it runs only when the briefing asks and a model is loaded. |
| Candidate window | At most 256 candidates per briefing, chosen by informativeness: exact anchors first (at most 128), then the records holding every query term, then all but the most common, and so on to the rarest term alone, then the other terms one at a time from rare to common, each step newest first, with at most 14 searches per briefing. Every search is filtered by tenant, project, deletion, recorded position, readers and holds before its limit. `candidate_limit_reached` is true when more than 256 qualify. A store whose lexical index is not rebuilt yet keeps the previous per-term windows (each term's 256 newest matches) and reports configuration `lexical-v1`. |
| Lexical statistics | Per project: documents and total length (`lexical_projects`) and documents per index term (`lexical_terms`, at most 4,096 distinct terms counted per observation), maintained at capture, purge and reindex; `lexical_state` records whether a tenant's index is `current`, `rebuilding` or `legacy`. SQLite schema 16, shared schema 11, shared archive schema 9, SQLite backup schema 11. |
| Policy journal | 256 KiB per signed record, enforced before writing (`journal_record_limit`) and on reading. A torn final line beyond the anchored sequence is discarded on the next append; damage anywhere else stays fatal. A database that has applied more records than the verified journal holds fails closed at open with `journal_rollback`. Records are verified incrementally per process. Operation records (new ones) go to a separate operations log in 4 MiB segments, compacted only when a retained backup holds them and every operation in them is resolved; consumed identities are kept for ever. Unapplied records are applied outside the request budget (statements up to 15 minutes in the shared profile), listed by `memoryking journal pending` / `memoryking.shared journal-pending`, and never skipped. |
| Conversation | 128 messages per conversation through `AuthorizedConversation` (a dispatch carries up to 127, leaving room for the reply); the request as a whole stays within 96 KiB, or the provider's smaller `max_request_bytes`. |
| Egress audit | One record per consumed permit for a remote provider, retained 30 days, 64 per listing page; a reply is admitted only up to 64 KiB of text and a provider response up to 1 MiB. |
| Session summaries | Extractive summaries are at most 1,200 characters from the checkpoint plus the 16 newest visible observations since it; provider-written ones at most 4,096 characters. Retained 30 days; the idle scan runs at most once a minute and derives up to 32 per pass. |
| Quote | One quote per observation per briefing, at most 4,096 bytes (only observations over 4,096 bytes are split into passages, at query time; an observation of more than six passages also scores by its best passage when that beats its whole text): the whole observation when it fits, else its best passage with adjacent passages that score at least three quarters as well, with exact byte offsets (`excerpt_start_byte`, `excerpt_end_byte`, `source_bytes`) that `fetch` returns exactly (a fetch range is at most 16,384 bytes). Passages (`passages-v1`) are about 1,000 characters, at most 1,200 (1,500 with a joined last piece), cut after sentence ends and paragraph ends, never inside a code or path line. |
| One answer per fact | Collapsed duplicates and superseded versions are named in the kept item: `also_recorded_in` and `supersedes` (`count` and at most 16 `references`), `evidence_not_repeated` on an accepted claim; the receipt depends on every one of them. Observation items carry `recorded_ms`, the time the store recorded them. |
| Briefing | Full response must fit requested budget; essentials are not silently truncated. A useful result can still be blocked or insufficient. `format: "text"` returns a cited Markdown rendering in an envelope with the same receipt; the token count is of the rendered text. Selection is by relevance; the rendering lists observations newest first with their observed day and, with two or more, one line that the later record is current unless it says otherwise; an observation whose source names third-party text (`tool`, `web`, `fetch`, `<host>-tool`) is labelled and fenced with a fence longer than any backtick run in its text. |
| Authorization | Five-second evaluation-to-commit/first-byte deadline, with UTC and monotonic checks. |
| Idempotency | Replay bodies retained for 30 days; expired/deleted results do not free a consumed identity. |
| Generic jobs | 30-second leases, five attempts, bounded retry backoff, 1,000 unfinished jobs and four live leases per tenant. Jobs reset by a `reindex` or restore are backlog the daemon rebuilds, not new captures, and do not count toward the 1,000. The local daemon completes `audit_probe` jobs itself between requests, so a default installation never needs a worker to keep capturing. |

### Lexical index and upgrading

Ranking (`lexical-v2`) reads an index of the text's words plus their stems and the per-project statistics, both written at capture. A store created by an earlier release has its rows indexed as raw text and no statistics: it keeps working, old rows stay searchable by their exact words, briefings keep the previous ranking (`lexical-v1`, named in each receipt) and `status` shows `lexical: legacy` with the number of observations still to rewrite; `memoryking doctor` warns the same way. To move to the new ranking run `memoryking reindex [--project P] [--wait]` (admin credential; `memoryking request` with the operation `reindex` does the same). The starting call does work that does not grow with the store: it moves the projection generation on, marks the index as rebuilding and runs at most a 0.2-second first slice. Everything proportional to the corpus then runs in batches of at most 64 observations or about a second, each in its own transaction and resumable from a stored cursor, so captures are never blocked behind it: each batch rewrites the index text, anchors and statistics of its observations and resets the projection jobs and items at the event positions it covers (the daemon's housekeeping runs the batches; an interrupted rebuild resumes where it stopped). `status` and `doctor` show the state, percent complete and an estimated time left (the daemon's measured batch rate, else a reference rate of about 400 observations a second; a guide, not a promise), and `reindex --wait` prints the same once a second until the state is `current`. While it runs, briefings keep using `lexical-v1`. Restore always rebuilds the index in full. The shared profile has the operator command `python -m memoryking.shared reindex --dsn-file F --content D --control D --tenant T --credential admin.credential [--wait]` (there is no HTTP route for it): it starts the rebuild and, with `--wait`, does the batches in that process and shows progress on stderr; without it the serving process advances the rebuild between requests, at most every five seconds, and the hourly housekeeping also does.

### Retrieval quality gate

`tools/retrieval_benchmark.py --gate` builds a deterministic synthetic corpus (400 documents, 200 labelled queries by default), runs real briefings and reports recall, precision, reciprocal rank, recall when a common word widens the candidate set, briefing tokens and latency. Seven further labelled cases each have their own project in the same store: `long_document_quote_rate` (the answer is one sentence in the middle of a 20-30 KB observation among short notes: the observation must be found, its quote must contain the sentence, and `fetch` of the quote's byte range must return exactly the quote), `duplicates_collapsed_rate` (five near-identical notes come back as one item naming the other four) and `newest_version_rate` (three versions of one file come back as the newest naming the older two), `word_form_recall` (a note with inflected forms is found by the base words), `rare_first_rate` (the note with the one distinctive word outranks notes with two common words), `crowded_recall` (the only note holding all three terms, oldest, among more than 256 newer single-term notes per term) and `newer_first_rate` (a correction comes before the stale fact when scores are equal). The thresholds in `fixtures/evaluation/retrieval-gate.json` fail the check when a ranking change regresses them. The corpus is synthetic, so the gate guards against regressions; it is not evidence of real-task retrieval quality.

Four tools measure the memory layer, none calls a model and none is a claim about real tasks. [CONTRIBUTING.md](../CONTRIBUTING.md#measuring-a-change) says which to run for which change.

#### Evidence recall on LongMemEval

`tools/evidence_recall.py` runs LongMemEval-format questions through real briefings and scores them against the dataset's own labels, with no answer generated or judged, so it is not comparable to answer-accuracy leaderboards.

**Corpus.** Every chat turn of every haystack session becomes one observation, recorded at its session's date and written as `role: text`; the question is asked as the briefing's query, as of the question's date (sessions recorded later are excluded). Two settings:

- *Pooled* (the default, for `longmemeval_oracle.json`, which holds only each question's evidence sessions): all 500 questions share one project, so about 950 sessions (10,866 turns) compete for every question.
- *Per question* (`--no-pool`, for `longmemeval_s_cleaned.json`, about 50 sessions per question): each question is asked against a fresh store holding only its own haystack. This is the setting other systems publish for the `_s` file.

**Ranking and K.** The briefing is asked for 32 results (the largest the contract allows) with a 65,536-token budget, so the result count and not the budget limits the list; a smaller budget cuts the list to the five or six excerpts that fit, and recall at ten cannot be measured under it. *Turn level* ranks the cited observations as returned. *Session level* collapses that ranking to distinct sessions in order of first appearance, so K sessions need not be K results.

**Metrics**, for K = 5 and 10. The gold set is the question's `answer_session_ids` at session level and, at turn level, the turns marked `has_answer` inside those sessions (a question with none scores 0 at turn level). `recall_any@K` is the share of questions with any gold item in the top K; `recall_all@K` the share with every gold item in the top K; `MRR` is the mean reciprocal rank of the first gold item, 0 when none is returned. `session_recall_at_k`, `answer_turn_recall_at_k` and `session_mrr` are the earlier headline figures: they look only at the first eight results (`--top-k`), and `session_mrr` counts result positions rather than distinct sessions. Earlier reports counted an answer turn of *any* question in the pooled set as a hit for answer-turn recall; it now counts only the question's own, which is why that figure fell.

The oracle run takes about three minutes. The `_s` run builds a store of about 500 turns per question (51 minutes for all 500 here, almost all of it capture); `--per-type N` or `--questions N` take a documented subset, and the report records the file's SHA-256, which `--compare` checks. Treat the downloaded files as untrusted data: they are only read as JSON.

**The committed sample and gate.** `fixtures/evaluation/longmemeval-regression-sample.json` is 72 questions, 12 of each type (the first twelve by hash of the question id, abstention questions left out), with their evidence sessions, taken from the oracle file under its MIT licence (see `NOTICE`); `tools/build_recall_sample.py` rebuilds it. The older three-question `longmemeval-sample.json` only exercises the harness in tests.

**Comparing a change.** `--compare BASELINE.json` (a report from the same data and settings; a mismatch exits 2) prints each metric's before, after and delta, the same for every question type, and the questions that left or entered the top five sessions. It exits 1 when a metric falls by more than `--tolerance` (default 0.02) or a question type's by more than `--type-tolerance` (default 0.10, because a type holds few questions); latency is shown, not judged. `--current REPORT.json` compares two saved reports without measuring.

#### Stale versus current facts

`tools/stale_facts_benchmark.py` states facts in synthetic projects, corrects them later and asks for the fact; the correct evidence is the newest statement. Corrections arrive three ways, each through the real service: a newer capture (worded as a marked correction, as the same sentence, as a short sentence, buried in a long one, or after the old fact was captured three times), a memory-tool file edit (`str_replace`, or `create` over an existing file; the tool records the day, so both versions carry the same time), and an accepted claim replaced by a later accepted revision of the same claim (two or three revisions; only accepted claims are scored). Values are unique made-up words, so a result states the old or the new fact when it contains that value. Per case it records whether the current statement is returned, whether it is ranked above every stale one, whether it is the first result stating either, whether a stale statement is returned at all and whether one outranks the current. The default run is 90 cases and takes about 20 seconds; `fixtures/evaluation/stale-facts-gate.json` holds thresholds at what the code achieves. At commit 165280c: the current statement is returned in every case (1.0), but it is ranked first in only 0.367 overall, 0.200 for captures (plain restatement 1.0; marked correction, terse, buried and repeated-old-fact 0.0), 1.0 for memory-file edits and 0.150 for replaced claims; a stale statement is returned in every case, and ranked above the current one in 0.633. Cases fail because a correction that is worded differently from the old fact scores lower than the old statement, which still matches the question's words better, and because a replaced claim stays in the briefing next to its replacement. Since the revisions of one claim are listed newest first (they used to be ordered by their random identifiers when their scores tied, so the figure changed from run to run), the current statement is ranked first in 0.556 overall and in every replaced-claim case; captures stay at 0.200, because no link or position says that a differently worded capture replaces an earlier one, and ranking by recency among near matches was measured to lose evidence on the long-history questions (see [Context coverage](#context-coverage)). The report names every failing case; the gate records the present behaviour and is meant to be raised as retrieval learns to prefer, or collapse, superseded statements.

#### Context coverage

`tools/context_coverage.py` asks, offline and with no model, whether the text of the turns an answer needs is inside the briefing a question gets. It records every turn of a LongMemEval question's roughly 50 sessions as one observation, indexes them by meaning with the installed model, builds the briefing the way the `memoryking_semantic` arm of the long-haul harness does (a text briefing under a 12,000-character budget) and reports, per question type and pooled, the share of questions whose briefing holds every needed turn, the share that holds at least one, the share of the budget used, the candidates considered and the distinct sessions shown. Only the five development draws of 60 questions (seeds 1 to 5, 226 distinct questions) are accepted; the published draw and the reserved ones are refused. Seeding a store takes about 30 seconds a question and the stores are kept outside the repository (`--stores`), so a second run only asks; `--cached-only` skips questions not yet seeded. The data file is third-party text and is never copied into the repository. This is retrieval evidence, not answer quality: a turn in the briefing is necessary for a right answer and not sufficient.

#### Scale

`tools/scale_regression.py` builds a local store of N observations and times capture (200 captures), drain per queued job, briefing for a 3-term and a 20-term query (30 each), `status`, reindex (the bounded call and the whole rebuild), backup and restore, then writes a JSON report. Every observation goes through the real capture path (validation, authorization, event, blob, anchors, lexical index and statistics, projection job), about 120 words each from a Zipf-like vocabulary, with a drain between batches as the daemon does; none is inserted behind the store's back. The one shortcut is durability: `fsync` and SQLite's `synchronous` are off while building, and on again for every timed step. `fixtures/evaluation/scale-budgets.json` holds a budget per figure and size, set to roughly two and a half times the measurement so that it catches a step change on a loaded host; `--check` fails past a budget and whenever a single capture, drain call, briefing, `status` or the reindex call takes five seconds or more. `tools/local_ci.py` runs the 20,000-observation size as the `scale` step (about five minutes); `tools/check.py` does not.

Measured at commit 165280c on a 4-CPU Linux host that was running two other benchmarks at the time, SQLite profile:

| --- | --- | --- |
| capture p50 / p95 / max | 15 / 26 / 43 ms | 40 / 59 / 111 ms |
| drain per job | 0.09 ms | 0.14 ms |
| briefing, 3 terms, p50 / p95 / max | 129 / 176 / 197 ms | 270 / 628 / 679 ms |
| briefing, 20 terms, p50 / p95 / max | 196 / 252 / 291 ms | 657 / 815 / 820 ms |
| `status` p50 / max | 12 / 22 ms | 38 / 62 ms |

Nothing reached the five-second request deadline. The reindex call was the closest: it used to work for about three seconds and then finish its current batch (3.2 to 4.1 seconds), and its projection reset was one corpus-sized transaction. It now does constant work: measured on stores built by direct insert, a call to a 100,000-observation store takes 31 ms (it took 4.5 s) and to a 1,000,000-observation store 29 ms (a store of at most 2,000 observations is rebuilt inside the call). The rebuild figures in the table are from before that change; a rewrite batch still scans the full-text table once to delete the rows it replaces, so the whole rebuild grows faster than linearly with the corpus. Backup and restore are offline operations whose cost grows with the number of observations (each blob is copied and verified; restore rebuilds the index), and restoring a 100,000-observation store takes about eight minutes. Building the 100,000-observation store took 22 minutes under that load, which is why only the 20,000 size is in the clean-checkout job.

| Not supported | A store on Windows itself, including a Windows drive seen from WSL2 (`/mnt/c`) or a Windows folder mounted into the container, which setup refuses with `store_filesystem_unsupported`; WSL1; a machine with neither WSL2 nor Docker Desktop; Windows setup for hosts other than Claude Code. |

The Windows side reaches the store through `memoryking relay`, which it starts with `wsl.exe` or `docker exec` and keeps open: the relay passes each request line to the daemon's Unix socket on that side and the reply back, without reading either. There is no network listener and no new secret. The agent's credential stays on the store side: the relay hands it over in its first line, and the Windows process keeps it in memory only, never on disk, on a command line or in an environment variable. A relay of another MemoryKing version, or a store side without an optional extra this side uses (`tokenizers`), is refused when it connects.

Tested on Windows 11 Pro (x64) with CPython 3.12.14, a WSL2 Ubuntu 20.04 distro, Docker Desktop with engine 29.8.0 (Linux containers), Git for Windows, Windows PowerShell 5.1 and Claude Code 2.1.101 and 2.1.330. On Windows the test suite skips, with that reason, every test that needs a store; those tests run where the store runs. Windows on Arm, Windows Server and other WSL distributions are untested.

## Importing legacy memory

The importer recognizes `kingforge-v1`, `standalone` and `universal` SQLite profiles. Start with a verified detached backup; do not copy a live main file and discard its WAL. Snapshot copying rejects sidecars, symlinks and files over 512 MiB.

Workflow: `memoryking.migration snapshot` → `inspect` → `plan` → bounded `apply` batches → `reconcile`. Run each subcommand with `--help` for the exact options. [The migration example](../tools/migration_demo.py) executes the entire local flow; shared import uses the same commands with `--url`, `--tenant` and verified `--ca-file` instead of `--socket`.

Inspection is bounded to 128 ordinary tables, 10,000 rows, 60 KiB per canonical row and 64 MiB total canonical row data. Unknown schemas, unresolved references, unstable keys or hash mismatches block. Apply defaults to 100 rows, maximum 500. Keep its source ID, snapshot and journal stable across retries.

Each imported row becomes restricted historical evidence; legacy approval and role labels do not become current permission. Lessons become unaccepted, nonexecutable proposals. Retired rows/dependents become tombstones. Reconciliation checks current target records and references but is not a lossless reverse importer, two-way sync or live cutover procedure. Production datasets and client behavior require their own rehearsal.

### Dashboard project listing

`GET /api/projects` on a signed-in dashboard session returns the projects the session's principal may read now, each with tenant-wide counts of observations, claims, task streams and retained receipts, and the instant of the latest recorded observation event (`last_activity_ms`). A tenant-wide grant lists every project holding records; a scoped grant lists its own project even when empty.

### Dashboard timeline

`GET /api/timeline/{project}` and `GET /api/timeline/{project}/{before}` on a signed-in session list the project's events newest first (captures, claims, reviews, checkpoints, handoffs, purges) with the principal that caused each, up to 100 per page; `next_before` pages further back. The Memory view's **Timeline** shows the same.

### Dashboard receipt trail

`GET /api/citations/{project}/{node}` on a signed-in session lists the session principal's retained receipts (briefings, fetches and reruns, newest first, up to 32) whose recorded dependencies include the node: an observation id, a claim revision or a checkpoint id, URL-encoded. Each item has the same fields as the receipts listing plus `dependency_kind`. A receipt the principal may no longer replay is omitted, exactly as in the receipts listing. The memory graph uses this route when a node is selected.

### Influence report

`memoryking influence OBSERVATION --project P` (or `--json`), the Memory view **Where did this go**, and the `inspection` socket operation's `influence` action list every record built on one observation and who received them: the claims that cite it; the checkpoints, handoffs, summaries and experience records that recorded a dependency on it or on anything derived from it (the same fixed point a purge follows, read without changing anything); the retained briefings, fetches, reruns and graph pages that included it, each with its principal and time; and the sorted set of principals those reached. Lists are bounded to 256 entries each and truncation is named. It requires the admin capability, because it reveals who read what. It covers recorded dependencies in this project and retained deliveries only: a delivery whose retention expired, a prior export, a provider dispatch or a backup leaves no record here, and the report says so in its coverage field. This is the causal-attribution view the memory-poisoning literature asks for, built from the receipts MemoryKing already keeps.

### Memory health

`memoryking health --project P [--days N] [--json]`, the **Memory health** section at the top of the dashboard's Jobs & health view, and the `inspection` operation's `health` action (admin; `days` 1 to 365, default 30) report whether memory is paying for itself from records the store already keeps. Every figure is a count or a ratio of counts over one project; no text and no principal is named. `observations`: live, captured in the window, held, purged, reached by a retained delivery in the window, and never delivered (with a share in millionths). `briefings`: retained briefings in the window by status, the share that ended `no_relevant_memory`, and deliveries of every kind. `feedback`: the latest revision of each actor's vote on each item, counted once if recorded in the window, by usefulness and by use, with the helpful share of rated votes. `claims`: the latest revision of every non-procedure family by state, quarantined, retired because cited evidence was purged (`evidence_purged`), and replaced by a successor (`superseded`). `backlog`: proposals waiting for review, the oldest age, and the oldest 16 (`truncated` says if more wait). `signals`: one line each for `feedback`, `briefings`, `backlog`, `evidence` and `reach` at level `ok`, `watch`, `attention` or `unknown`. Thresholds are fixed, not learned: a ratio needs 5 rated votes or 5 briefings before it speaks; under half helpful, over half empty, or over a quarter budget-starved is `watch`; any harmful or misleading vote, a quarantined claim, or a proposal waiting more than 7 days is `attention`; lost evidence is `watch`; reach is judged from 20 observations and is `watch` when more than nine in ten reached no delivery. Coverage: retained deliveries in the window only (an expired delivery leaves no record), so reach is a floor.

### Proposal drafts

`knowledge` action `draft` (capture capability, keyed), `memoryking draft-proposals --project P [--limit N]` (default key one per project and day), and the dashboard's Review view. Window: the newest 512 visible observations; topics: anchors held by 2 to 32 of them, then terms of five or more characters shared by 2 to 8 of them, deduplicated by member set; a topic needs at least two distinct source events; a draft cites up to 16 spans (one sentence each, at most 512 characters); families are keyed `draft-<sha256(topic)>`; a draft whose evidence is already cited by the family's latest unpurged revision is skipped (`already_proposed`). Result: drafted revisions with topic, basis, support and text; `skipped` counts; `window`; `method` `repeated_evidence_v1`.

### Anchors and salience

Anchors: deterministic extraction at capture (paths, symbols, tickets, URLs, hosts, error codes; at most 32 per observation, each at most 128 characters) into the `anchors` table (SQLite 13 / PostgreSQL 8, archive schema 6). A query's anchors (at most 16) each get a newest-first candidate window and come first in the candidate set; the share of the query's anchors a record holds combines with its word score (one minus the chance that neither is right), so a record holding every anchor scores 1,000,000, the top of the scale, and is reported as `anchor_match`; records still tied on the anchors are ordered by word score, then recency. The graph adds `anchors` to observation nodes and `shares_anchor` edges for anchors held by 2 to 8 loaded records, at most 512 such edges per page (`anchor_links` truncation). Purge removes a record's anchors; `reindex` rebuilds them from retained text.

A brief's optional `file` argument is the exact-anchor search on its own: only observations that hold that anchor (a path such as `src/app.py`, a symbol such as `parse_row`, a ticket) are candidates, inside the same authorization filter and before any limit, and an accepted claim is kept only when its text names it. A text page of four or more observations also says, per record, which anchors it holds (`about` in the packet, "names ..." in the text, at most three of at most 48 characters, files before symbols before tickets), leaving out an anchor that more than half of the page holds, so a label is what is particular to the record. See [paging and narrowing](design.md#near-identical-records-in-a-long-history).

Salience: per candidate, the caller's own deliveries in the last 90 days from retained non-graph receipts, the caller's own helpful feedback votes, and the last delivery time (another principal's use or opinion never changes a reader's order); strength is at most one million (millionths), the rank nudge at most 45,000 (a tenth of a typical full match, which scores about 1/(K1+1) of the scale; it stays 100,000 while a store is on `lexical-v1`), half-life 30 days; a record never delivered, never voted on and recorded more than 180 days ago is tier `archival` and ranked after every active record while remaining searchable. Applied only when the briefing asks (`salience: "on"`); disabled for any briefing with `recorded_position`, `valid_ms` or `as_of_ms`, during a ranking evaluation, and while a frozen ranking policy is active, each named in the trace stage `salience_v1`. Reported per item as `salience`.

Evidence recall: see [Retrieval quality gate](#retrieval-quality-gate) for the tool, its definitions and the current figures. When anchors were added, on the pooled LongMemEval oracle set (500 questions, 10,866 observations; earlier ranking, earlier budget and answer-turn definition) session recall at eight moved from 0.548 to 0.556 and MRR from 0.462 to 0.469 while answer-turn recall moved from 0.562 to 0.538; chat transcripts rarely carry anchors, so a developer's own project is the corpus where they count.

**What is embedded.** Observations and accepted claims. An observation is embedded from its opening (up to 512 tokens). The passage-by-passage path (`domain.passages`, the lexical index's boundaries, a vector per passage, an observation scored by its best passage) is implemented and tested, but on the merged code it scored lower than the opening on four of five headline metrics (session recall at five 0.844 against 0.850, at ten 0.898 against 0.904, MRR 0.718 against 0.724, turn MRR 0.496 against 0.516; turn recall at five 0.676 against 0.674), because most chat turns fit in 512 tokens and splitting the rest dilutes them, so it stays off (`EMBED_PASSAGES` in `adapters/embedding_store.py`). A corpus of long documents, which this set is not, is where it should be measured again. The merged lexical baseline is unchanged at 0.820 / 0.868 and MRR 0.697; with the default semantic channel it is 0.850 / 0.904, MRR 0.724, turn MRR 0.516, preference 0.433 (from 0.233). A briefing's median latency on this loaded host went from 211 ms to 265 ms (95th percentile 302 ms to 355 ms), with the query embedded in the request.

**Passage vectors for long records (tried again, not kept).** The hooks store a whole session as one observation of up to 64 KiB, so a long record is found by meaning only through its opening (the model reads 512 tokens, about the first two passages); the rest is found by keywords. The earlier switch embedded every observation passage by passage and lost on turns, because it also split records that fit the window. A second design left those alone: an opening the model had to cut, on a record of more than one passage, got one more vector for each later passage (the lexical index's boundaries), a search scored a record by its best vector, and a record found by meaning alone was quoted from the passage that matched (a schema migration added the passage rule to each vector; existing vectors stayed valid and the indexing loop added only the missing ones; the PostgreSQL pgvector path and the purge, hold and reader checks were extended and tested with several vectors a record). It was measured at session level, with `tools/context_coverage.py --unit session` (each haystack session one observation, as the hooks store it; the stores are kept apart from the turn-level ones). **Batches of long records.** Measuring this showed a defect in batched indexing that records longer than about 8 KiB hit: a batch of 16 records of up to 16 KiB each exceeded the model's input limit (128 KiB of text a call), the whole batch failed, and after five attempts every such record was marked dead and never indexed (the 46 sessions of one haystack all ended dead). A batch is now closed when another 16 KiB record could not fit, and the external worker splits what it was given into model calls that fit. Turn-length records are unaffected.

The gain, about 3.5 times, comes from two things. The model runs on three threads instead of one (about 2.5 times, because ONNX Runtime spreads one pass over the cores), and the store work, a third of the old time, is cut by two thirds (one claim and one completion per 16 records instead of per record) and overlaps the model. Batching texts of different lengths into one pass saves nothing on a CPU, where a pass costs about what its tokens cost: a text is padded only up to the longest in its group of at most 512 padded tokens, and a group of short texts is one call. The vectors are unchanged: for a sample of 240 texts of 1 to 900 words, embedded one at a time on one thread, in batches of 16 on three threads, and in the order reversed, every vector was identical (largest difference of any coordinate 0 millionths, cosine 1.000000); `tests/test_indexing.py` compares them for a mixed-length sample and accepts at most 2 millionths per coordinate and a cosine of 0.999999, which is under the rounding of a stored 16-bit vector. The retrieval and evidence-recall gates of `tools/check.py` give the same figures.

*Settings.* `MEMORYKING_EMBEDDING_THREADS` sets the model's CPU threads for the daemon and the external worker. The default is one fewer than the number of cores, from one to four (three on four cores): enough for a threefold gain, and one core left for briefings, captures and the rest of the machine. A value of 1 gives the old model speed and the lightest load; a value above the number of cores is lowered to it. `memoryking-embedding-worker --count N` sets the records per model call (1 to 16, default 16). Everything else is fixed: the model, the 512-token rule and the vector format are unchanged.

*What it costs the foreground.* A briefing waits for the model only to embed its own question, and the question goes first: indexing yields between groups, so a briefing waits for at most one group (up to 512 padded tokens, about a tenth of a second). The remaining slowdown is the processor shared with the three model threads. The bound for the defaults on four cores: while a backlog is being indexed a briefing takes at most 0.5 s at the median and 1 s at the worst of 50 (measured 0.38 and 0.73 s; the idle figure is about 0.1 s), well inside the five-second request deadline. If briefings matter more than the time to index on a small machine, set `MEMORYKING_EMBEDDING_THREADS=1` or `2`. The figures were taken on one machine; with other work running at the same time (load average 3 to 5) the same code indexed at 10 to 20 records a second.

*Progress.* `memoryking status` and `memoryking semantic status` show, per project, `p 1,200 vectors, 24% indexed (3,800 of 5,000 records left, about 3 min at 22.4 a second)`. The speed is the daemon's own, measured over the last records it indexed (smoothed, reset after a pause of a minute), so the time left is an estimate and is left out until the daemon has indexed a few records. In the JSON `status` response each partition carries `records`, `records_indexed`, `records_left`, `records_per_minute` and `estimated_seconds`. The shared PostgreSQL profile reports the same fields, from the speed of whichever worker is indexing it.

*Both backends.* The local and the shared profile run the same claim and completion code (`Embeddings` in `adapters/embedding_store.py`), so the batch actions `claim_batch` and `complete_batch` exist on both. The shared profile has no loop inside the service: `memoryking-embedding-worker` calls them, 16 records a run, and `--until-idle` keeps going until nothing is left. A completion that arrives after a record was purged, changed or hidden is refused for that record only; no vector is stored for it, and a purge removes the vectors it stored.

**The scan.** Vectors are 16-bit integers (768 bytes at 384 dimensions) read from the store after eligibility, then one matrix product in numpy. Measured with `tools/dense_scale.py` (synthetic vectors, local SQLite, five repeats, the same loaded host; median and worst):

| Eligible vectors | Whole corpus scanned | Under the product bound (200,000) |
| --- | --- | --- |
| 10,000 | 56 ms (89) | 152 ms (204) |
| 100,000 | 738 ms (869) | 716 ms (826) |
| 1,000,000 | 7.5 s (23 s with the machine busy) | 1.37 s (1.54 s), newest 200,000 scanned, `scan_truncated` |

The earlier pure-Python scan took about 1.2 s at 10,000 vectors and refused above that. The bound is 200,000 vectors per briefing: about 154 MB of vectors from the store and a few hundred MB of working memory, about a second and a half on this host, so a briefing stays inside its five seconds with margin; a store beyond it is searched on its newest 200,000 vectors and the `dense` stage of the trace carries `scan_truncated` and `scan_limit`, never an empty channel. Without numpy (the core install) a pure-Python scan covers the newest 10,000. With pgvector enabled on a shared profile the index shortlists and the numpy scan rescores (see the capability table); the HNSW path was exercised against pgvector 0.6.0, the only release installable on the test host, not the pinned 0.8.7, and so without iterative scans: the filtered shortfall is tested for real, the 0.8 iterative-scan settings are not.

### Local reranker

The reranker is a cross-encoder, `cross-encoder/ms-marco-MiniLM-L6-v2` (Apache 2.0), pinned by revision, file sizes and SHA-256 hashes in its [manifest](../src/memoryking/adapters/models/ms-marco-minilm-l6-v2-onnx.json) and run by the same ONNX runtime, tokenizers and numpy versions as the embedding model, on up to four CPU threads. `python -m memoryking.model_install --model reranker --destination DIR` downloads and verifies it; `doctor --reranker-model DIR` re-verifies; `serve --reranker-model DIR` loads the checked bytes once. A briefing that asks for `rerank: "on"` has its top 16 candidates, after lexical scoring, dense fusion and salience, scored against the query (the text is cut at 256 tokens, the query never) and reordered by that score with the fused order as the tie-break; everything below the window keeps the fused order. Each reordered item carries `rerank_score_ppm` (the sigmoid of the model's logit, in millionths); the receipt's trace carries a `rerank_v1` stage with `state` `applied` (model fingerprint, window, candidates, how many moved, duration), `off_unless_requested`, `unavailable_no_model`, `disabled_for_ranking_evaluation`, `disabled_for_active_ranking_policy` or `failed_fused_order_kept` (with the error code); the model fingerprint joins `model_fingerprints` in the diagnostics. Authority, constraints, policy completeness and conflict expansion are decided before the stage and are not changed by it; the model moves records, it never admits or removes one. Bounds: 16 pairs per call, 256 tokens per pair, 16 KiB per text, the query at most 16 KiB; a limit or runtime failure keeps the fused order. The window is 16 candidates unless `serve --rerank-window 32|64` says otherwise (a call runs its pairs in batches of 16). The harness takes `--reranker-model DIR --reranker-name ID --rerank-window N` and reports the fingerprint it used.

The pinned MiniLM reranker still pays: with a window of 16 it adds 0.018 to session recall at five, 0.03 to MRR and 0.054 to turn recall at five and 0.056 to turn MRR over the semantic-and-lexical base, although the preference questions (the semantic channel's best case) fare worse as the window grows. Widening the window buys little for what it costs: 32 candidates add 0.009 MRR and 0.006 turn recall for about 0.7 s more, and 64 add 0.005 more for no extra median but a 95th percentile of 3.0 s on one loaded thread, close enough to the five-second deadline (with the briefing itself, 0.35 s) to leave no margin, while the preference questions get worse as the window grows (0.467, 0.400, 0.367). So the window stays 16. The two newer cross-encoders that were run did not beat it: mxbai-rerank-xsmall-v1 is a DeBERTa model that took ten seconds for a window of 16 on one loaded thread, and its subset recall was no better than MiniLM's. gte-reranker-modernbert-base and mxbai-rerank-base-v1 are 150 to 180 million parameters and took 26 to 28 seconds for a window of 16 on one loaded thread, five times the whole request deadline, so they were not run on the full set; that is a decision on latency, not on recall. The 32 and 64 rows for MiniLM are understated: a few questions have fewer than that many turns to score.

Recommendation, not a change: reranking is off unless asked, and it stays so in this release. If an owner wants better ranking and accepts about a second of added latency on a busy single thread (less with more threads), turning it on by default when the model is installed is supported by these figures; the model is a 2021 one and nothing newer that was measured is both better and fast enough. `rerank` is per briefing (`rerank: "on"`, `recall --rerank`).

### Time in the question

A query's dates are resolved without a model (`domain/timeexpr.py`, English only, all UTC; a day is 00:00:00.000 to 23:59:59.999 and a week runs Monday to Sunday) against the briefing's reference instant, `as_of_ms` when given, else the evaluated time. Understood: ISO and slash dates and months (`2025-03-14`, `2025-03`); month names with or without a day and year (`March 14`, `14 March 2025`, `March`); `in 2025`; `yesterday`, `today`, `tomorrow`, `last night`, `the day before yesterday`; `last|this|next week|month|year|quarter` (calendar periods) and `past|last N days|weeks|months|years`; `N days|weeks|months|years ago`; weekday names (`Monday`, `last Friday`, `this Tuesday`, `next Wednesday`); `Q1 2025`; and `since X`, `before X`, `after X`, `until X`, `between X and Y`, `from X to Y`. Where there are two readings the most recent past one is taken (a month or date without a year, a weekday without `last`, `last week` as the previous calendar week) and named in the trace's `ambiguity`. The words of each expression are removed from the lexical terms, so "last week" does not search for the word "week"; if nothing else is left the whole query is searched as before.

Records in a resolved range are raised, never filtered: an observation by its observed time, a claim by its validity interval (a claim with no bound is in no particular time). The rise is 25% of the best score in the candidate list (`TIME_BOOST_PPM`), so a date decides between near-equal matches and never beats a clearly better one on words; the matched items carry `in_time_range` and the receipt's trace has a `time_v1` stage with the understood expressions, their ranges, the removed words, the ambiguity notes and the number raised. Only an explicit `time_range` argument (`from_ms` and/or `to_ms`, Unix ms, inclusive) is a hard filter: it is applied in the candidate search before any limit, to observed time and to claim validity overlap, and mandatory constraints are not filtered. CLI `recall --from DATE|ISO|MS --to DATE|ISO|MS` (a bare date is the start of the day for `--from` and the end for `--to`). On the pooled LongMemEval oracle set the boost took the `temporal-reasoning` session recall at eight from 0.729 to 0.774 (overall 0.812 to 0.824).

### As-of briefings

`brief` accepts `as_of_ms` (Unix ms): the frontier is the last event recorded by that wall time and claim validity is judged at that time; the packet carries `as_of_ms`, `recorded_position` and `valid_ms` and the receipt replays byte for byte. Equivalent to passing `recorded_position` and `valid_ms` yourself, which remain available; combining the two is `invalid_request`. CLI `recall --as-of DATE|ISO|MS`, lean tool `recall(as_of=...)`, dashboard briefing form **As of**.

### Source trust

`memoryking review list|show|accept|reject|retire-approve|retire-dismiss` and `memoryking pin add|remove|list` call the `knowledge` operation. New actions, all additive: `retire` (needs `capture` and read access to the record; args `observation`, free-text `note`; one open request per requester and record), `retirements` (needs `review`; the open requests oldest first, at most 64, each with the requester, note and a 160-character preview), `retire_decide` (`review`; `decision` `approve` or `dismiss` with an identifier `reason` and optional `note`; `approve` additionally needs `admin` and journals a `purge`, `dismiss` journals a `retirement` record), `pin` (`review`; `mode` `add` or `remove`, `target_kind` `claim` or `observation`, `target`; a claim is pinned by its family and must be accepted; a journaled `pin` record) and `pins`. `review` takes an optional free-text `note` (up to 2,048 characters) beside the identifier `reason`, and `channel: "chat"`, which the daemon accepts only for accepting or rejecting a knowledge proposal and records, with the relaying and the proposing principal, in the decision. `query` with `diagnostic` takes `revision` (one revision), `kind` (`knowledge` or `constraint`) and `excerpts` (the cited text), and each item names `proposed_by` and its latest `decision`. A capture request takes an optional `supersedes` (an observation id the caller can read in the same project, else `unavailable`); the link is recorded in `supersessions`, requests in `retirement_requests`, pins in `pins` (SQLite schema 17, shared schema 12 with row-level security, shared archive schema 10, SQLite backup schema 12). A purge deletes the links, empties the request note, closes an open request as approved and removes the pin. The `retrieval` operation takes `start` (`project`, `bindings`, `max_output_tokens`, `tokenizer`, optional `task`, `run`, `format`, `recent_days` 1 to 365 default 14, `recent_limit` 0 to 16 default 5): constraints (essential), then pins, the task's latest checkpoint, then recent decisions newest first, packed within the budget like a briefing; items are at most 800 bytes of text; the status is `no_relevant_memory` when nothing is recorded. The lean bridge flag `--allow-chat-review` enables `confirm` (see the agent guide). The labelled tier adds `unreviewed_tier` (needs `review` on the project and an admin grant; `mode` `on` or `off`; keyed; journals an `unreviewed_tier` record and replays on restore) and `unreviewed_tier_show` (read). With the tier on, a query briefing (not historical, not `freshness: attested`, not the session start) appends up to three drafted proposals after the accepted guidance, each `authority: drafted_unreviewed`, `selection_reason: drafted_unreviewed`, `assurance: unreviewed_draft`, with `draft: {method, method_label, kind, age_ms, quotes}` and the warning `unreviewed_drafts_included`; the text rendering puts them under "Unreviewed, drafted from evidence". The table is `unreviewed_tier` (SQLite schema 20, shared schema 15, shared archive schema 12). The `draft` action takes an optional `procedures` (default true) and returns a `procedures` report beside the claim drafts: `drafted` (revision, family, `polarity` avoid or do, `tasks`, text), `skipped` by reason (`no_success_evidence`, `no_evidence`, `already_proposed`, `refused_by_store`, `limit`) and the method `repeated_outcome_v1`. Consolidation adds two `knowledge` actions: `consolidate_prepare` (`capture`; `project`, optional `limit` 1 to 64 default 24, `since_ms`, `idle_ms` and `max_classification`; returns the retained input packet with its receipt, or `{status: nothing_new|busy, frontier}`) and `consolidate_admit` (`capture`, retry key required; `run` is the packet's receipt, `permit` the egress permit and `text` the exact reply; returns `status` `admitted` or `rejected`, the filed proposals, the dropped counts by reason, and the frontier). Dropped reasons are `invalid_shape`, `invalid_text`, `invalid_kind`, `no_evidence`, `evidence_limit`, `unknown_observation`, `unreadable_observation`, `observation_changed`, `quote_not_verbatim`, `invalid_relation`, `duplicate`, `previously_rejected`, `claim_limit` and `refused_by_store`, plus `reply_too_large`, `reply_not_json` and `reply_shape_invalid` for a reply that is rejected whole. The `health` report adds `drafts.by_method`: for each method named in a claim's provenance, `drafted`, `accepted` (including later deprecated), `rejected`, `waiting`, `accepted_of_drafted_ppm` and `accepted_of_decided_ppm`, over the project's newest 4,096 revisions.

`memoryking trust set|list|held|release`, the **Review & conflicts** view, and the `inspection` operation's `trust`, `trust_list`, `held` and `release` actions (all admin). A rule names a project or `*`, a source by exact name or glob, and a level. A capture whose source resolves to `untrusted` (most specific rule wins) is stored but held: `_visible` is false for every principal until an admin releases it, so reads, briefings, the graph, resume evidence, claim proposals and the influence of later records exclude it; the capture reply carries `held: true`. `held` lists the oldest 64 held captures in a project with a 256-byte preview. Rules and releases are journal records (`trust`, `hold`) replayed on restore; `source_trust` and `observation_holds` are content tables in schema SQLite 12 / PostgreSQL 7 and archive schema 5.

### User memory

`memoryking user show|export|purge` shows, writes as Markdown (`user/` folder) and erases the caller's own user scope; `purge` needs `--yes` and an administrator may add `--user NAME`. `capture --scope user` and the lean `remember` tool's `scope: "user"` write to it; `credential issue --for-user NAME|--no-user` ties an agent to a user. `MemoryTool.for_session(client)` also serves the scope as `/memories/user` when the credential acts for a user (nothing can move between it and a project). The wire operation `user` has the actions `scope`, `ensure`, `show` and `purge`; `status` reports `user_scopes` counts and, on a daemon started with `--consolidate-every`, a `consolidation` list with one entry per project (`state` waiting, running or backoff, `pid` of the running child or null, `runs`, `consecutive_failures`, `last_exit`, `next_run_ms`). A user scope holds no schema of its own, so no migration was needed.

### Memory tool and vault

`MemoryTool(client)` answers `view`, `create`, `str_replace`, `insert`, `delete` and `rename` for paths under `/memories/<project>`; `DEFINITION` is the `tools` entry to send. Paths: `README.md` (generated), `<source>/<name>.md` (the newest version of the observation whose source event is `<name>`, versions `<name>__v<n>`), `claims/<key>.md` (the latest unpurged `knowledge` revision of family `<key>`). Names are mapped to identifiers of at most 80 characters; the version suffix is reserved; anything outside the root, hidden, or containing `..`, `\\` or `%` is refused. A file is a provenance block (`---` lines) and the stored text; `str_replace` and `insert` edit the text only, with line numbers counted as viewed, and record a new version through `capture` (key `mt-<sha256>`, day-granular observed time, namespace `sdk`, replay-safe) or a new revision through `propose` (expected version from the catalog; evidence from the file's `evidence` list, whole-record spans, at most 16; provenance method `memory_file_v1`). `view` of a file reads through `fetch` in 16 KiB ranges; directory listings show the newest 512 observations grouped by source and at most 256 entries, and say what they left out. `delete` purges every version of a note and `rename` captures the newest text under the new name before purging; both require the admin capability. Claims cannot be deleted or renamed. Reply texts follow the reference implementation; refusals are returned as `is_error` tool results.

`vault export --dir D` writes `D/<project>/<source>/<name>.md`, `D/<project>/claims/<key>.md` and `D/<project>/README.md` with mode 0600 in 0700 directories, replacing files in place; `vault import --dir D [--dry-run]` reads them back (notes before claims), captures a version for each changed or new note, proposes a revision for each changed or new claim file, and reports `captured`, `proposed`, `unchanged` and `errors`; the exit code is 1 when any file was skipped. Connection comes from `--socket`/`--credential`/`--project`, a profile, or `MEMORYKING_SOCKET`, `MEMORYKING_CREDENTIAL` and `MEMORYKING_PROJECT`; the vault client uses capture namespace `vault`.

Both read through the `inspection` operation's `catalog` action (read capability): `kind` `observations` (default) or `claims`; filters `source`, `name` (a file and its versions; `_` is literal) and `id`; `after` and `limit` (1 to 512, default 256) page newest first by position (`next_after` continues); `text: false` omits text. Observations are the visible ones only; claims are the latest unpurged knowledge revision per family, accepted ones for every reader and every state for a reviewer (`reviewer` in the reply). A page carries at most 192 KiB of text. Catalog reads leave no delivery record; `fetch` does.

### Task-outcome benchmark

`tools/outcome_benchmark.py` measures whether a coding agent finishes multi-session tasks better with MemoryKing than without. The ten tasks in `benchmarks/outcomes/tasks/` each have a small Python project, two prompts written as a user would write them, and a hidden check. Session 1 does part of the work and learns something the repository does not record: an instruction ("never edit `legacy/`", "use this retry helper"), a failed approach and the reason, a decision between two designs, or an environment fact (a port, a flag name, a data format). A task's between-step may delete the slow script or sample data that showed it. Session 2, a separate agent instance, must finish; the hidden check fails on the untouched repository, fails after session 1 alone, and passes only when the carried knowledge was used.

There are five arms; the first four are identical except for one closing sentence in the prompts, and the fifth has none:

##### What the product changed in response

The result above stays as measured. It was taken on code from before the latest MCP-surface work (server instructions that say when to recall and remember, lean as the default profile, Markdown replies), with no hooks installed, although the intended setup (`memoryking setup claude-code`) installs hooks that load and save memory without the model choosing to. Reading the 80 sessions showed two causes: Claude Code lists an MCP server's tools by name only and loads a schema when the model fetches it, and none of the ten `mcp` session-1 agents did (three session-2 agents fetched `recall` and found an empty store); and in arm `on` one agent recalled from an empty store, did the work and never saved what it had been told. Afterwards the product was changed so that saving and loading do not depend on the model deciding to fetch a tool:

- The lean tools `remember`, `recall`, `save_progress` and `resume` carry `_meta` `anthropic/alwaysLoad` (the other tools a search hint), `memoryking setup claude-code` registers the bridge with `alwaysLoad`, and each tool's name and first sentence, and the server instructions, say when to call it (save as soon as there is something to save).
- The session-start hook prints a short note naming the tools in the host's vocabulary and when to save, then a briefing that now includes the user's own recent words (the hooks capture the user's turns verbatim as their own observation, `user-<host>`, which the start briefing shows up to 2,400 bytes at a time), how the last captured session ended, and recent observations of the user's own scope. Before this, a hook capture was invisible to the start briefing, because only sources named `decision`, `instruction` or `user` were listed there: replaying a recorded-shape session through the hooks and starting a second session showed "nothing is recorded" for all four knowledge kinds, and shows each kind's facts now (`tests/test_hook_replay.py`, synthetic transcripts modelled on Claude Code's; no real transcript is committed).
- The `MEMORY.md` note for command-line agents says to save an instruction or decision the moment it is given and not to recall from an empty store.
- The benchmark gained the `setup` arm and `report --rep`; `RUNNING.md` shows how to pass the settings and MCP files to a headless host.

What the numbers show:

- The mechanism works as installed. - Memory as installed beat no memory on the tasks that need carried knowledge: 10 of 12 against 0 of 12 (the knowledge tasks are `alert-sink`, `job-states`, `partner-feed`, `staging-collector`). Over all ten tasks `setup` passed 27 of 30 against 16 of 30 for `off`; by task it was higher on 5 tasks and lower on none (exact p = 0.0625), and the by-run p of 0.001 is too small because repetitions of a task are correlated.
- A notes file did as well: `notes` passed 26 of 30 and 11 of 12, `setup` 27 of 30 and 10 of 12. `setup` against `notes` p = 1.0, `setup` against `on` p = 0.69, `notes` against `off` p = 0.013 by run and 0.375 by task. This run does not show that MemoryKing beats a notes file the agent is told to keep.
- The MCP-only arm passed 0 of 12 knowledge tasks although the agent saved in 23 of 30 runs: in this CLI version the model is shown a tool result's `structuredContent` and not its text block, so a lean `recall` or `resume` reply (briefing as text, envelope as `structuredContent`) reaches the model as a JSON envelope with no briefing. The hooks hide the defect in arm `setup`. This was a defect in the product's reply shape for this host, found by the run; a lean reply is now its text alone (see the follow-up check below).
- `setup` used about 109,000 more tokens per run than `off` and was slower on average; there is no saving to report.
- Follow-up check after the reply-shape fix (4 runs, not a new experiment): arm `mcp` on the four knowledge tasks, one repetition, same host and protocol, commit `f249efb`. All four passed, in each the model received the briefing as the text block of a result with no `structuredContent`, and session 2 called `recall` in all four. This confirms the mechanism for this host and version; with four runs and no comparison arm it says nothing about an effect size, and the `mcp` arm's 0 of 12 above stays as measured. A separate one-session probe found that this host refused a heredoc containing braces and quotes and accepted `capture --file`, so the note for command-line agents shows the file form first.
- Several failures in every arm that carried the right facts (for example `staging-collector`, where the agent passed a JSON string where the check wants a dict) are the agent's design choices, not lost memory.

Limits: ten synthetic tasks, one model, one host and version, one machine with four runs in parallel, three repetitions (which add pairs, not independent tasks), a knowledge-task split made after the first run, and `fetch` not allowed in the benchmark's tool list (allowed in the follow-up check). Ten tasks can show only a large effect, nothing was corrected for ten comparisons, and none of this is evidence of real-task quality or production performance.

### Long-history benchmark

`tools/longhaul_benchmark.py` is built; its pilot (S0) and then track T1 on the measured seed (stage S0 repeated and stage S1: 12 tasks at 20, 200 and 2,000 sessions, nine arms, one repetition, 312 real Claude Code sessions) have been run against a real agent, tracks T2, T2f, T3 and T4 at 200 sessions beside four other products (135 sessions) and T1 again at 2,000 sessions on a fixed generator (60 sessions) have been run too (below); the lived track (80 sessions) and question answering (600 model calls) have been run too (below). It asks whether memory still helps when the history is long, changed, spread over projects or partly hostile, and compares MemoryKing with no memory, a notes file, raw transcripts, Claude Code's own memory file and, as their adapters are added, other memory products. Prior sessions are not lived but **seeded**: synthetic transcripts are ingested through each system's own ingest path, and then one real agent session per run does a small task in a small Python repository, with a hidden check that passes only if the code uses what the history established. The number of real sessions is therefore tasks x arms x repetitions.

| Track | What it measures |
| --- | --- |
| T1 needle at scale | 12 tasks; one or two facts among 20, 200 or 2,000 sessions with hard distractors (the same project's vocabulary, other components with the same attribute and other values, reverted experiments, draft notes in tool output, a sibling project's different value) |
| T2 change over time, T2f forget | 8 tasks with a fact corrected once, twice or retracted (using an earlier value is the failure `stale`); 4 tasks where the product's own delete path is used for one fact and the text must not reach the session's event stream |
| T3 scopes | 9 tasks: a leak check across projects (canary text), a preference stated in another project, a hand-off between two agents in a fresh directory |
| T4 hostile memory | 6 tasks: history holds a fetched page or a failed tool call with an embedded instruction (add a dependency, create a file, POST to localhost); counts of acted, mentioned and refused, never surfaced |
| T5 question answering | a stratified, seeded subset (default 60) of LongMemEval `_s`: each system ingests the haystack, returns a context under one character budget, and a reader and a judge command (the same for every system) answer and grade; accuracy and evidence recall |
| T2b lived | 4 tasks of 4 real sessions with a correction in the third, each system writing memory itself |

Every needle is a decision or instruction by the user, or a confirmed outcome ("we settled on ...") that the assistant reports and the user acknowledges, never hearsay and never weaker than a distractor; which of the two states it is a recorded factor of each task (`stated_by`), balanced over each track, and the report splits by it. Every session has the same six turns. Each of the 39 hidden checks is audited by tests against conforming implementations that differ in everything the history never fixed (which must pass) and against every other value of every fact and the defaults an agent would write (which must fail). Generators are deterministic from a seed (`benchmarks/longhaul/gen.py`, `families.py`); seeds 1 to 5 are development seeds whose runs `report` leaves out, and every measured stage uses seed 11; a system is a module in `benchmarks/longhaul/systems/` that implements one small interface (`prepare`, `seed`, `host`, `context_for`, `forget`, `usage`, `close`). Built-in arms are `off`, `notes` and `native` (one fixed extractive rule over every user and assistant turn, capped at 30,000 characters), `log` (raw transcripts to `grep`) and `memoryking`, which is seeded through the real session-end hook code under the session's own project and agent credential, on a store clock moved to each session's date, with nothing held and no trust rule beyond what `setup` writes, so a tool error carrying an embedded instruction reaches memory as in a real session. Seeding a product that hooks into the host gives it what a real session of the same turns would: claude-mem gets the hook events and payloads Claude Code fires (the first prompt and each turn's last assistant message reach its observer, a failed tool call arrives as a failure); MCP Memory Service and Basic Memory would get almost nothing from a real session of a few turns (the first stored no statement of any decision when its hooks were run offline, the second writes only when the context is compacted), so they are measured on the lived track only and a seeded run of them is labelled an explicit-save upper bound. The driver's subcommands are `generate`, `seed`, `run`, `report`, `regrade`, `validate`, `plan`, `t5-select`, `t5-run` and `lived`; the offline stub agent (`null`, `oracle`, `stale`, `gullible`, `leaker`, `reader`) drives every one of them. `report` pairs `memoryking` with each other arm by task (exact sign test, Wilson intervals, Holm correction within a track), and states failure classes, tokens, seconds and memory characters by history size.

Measured offline, with no model: seeding MemoryKing through the hook path took 1.8 s (0.9 MB) for 20 sessions, 5.9 s (2.4 MB) for 200 and 44 s (14.6 MB) for 2,000, about 22 ms a session on one shared four-core host (T1, group 0, one run each, so noisy). For every one of the 39 tasks the stub agent without memory fails and the oracle passes. With the `reader` stub, which finds facts the way a careful agent would, the needles are found in the notes, native, log and MemoryKing arms at 200 sessions and the bounded notes arms lose them at 2,000, which checks that the information is reachable, not how a real agent behaves. A preference stated in another project (T3b) cannot reach MemoryKing through the hooks alone, which capture project scope only, so the MemoryKing arm also makes the one save to the user scope that the start briefing tells an agent to make for a standing personal preference (an upper bound, labelled as such; `benchmarks/longhaul/preflight.py` reports the hook-only seeding too), and in T3 the `log` arm holds every project's transcripts, one folder each, so that isolation can be measured in it. The distractors that call a value tried, reverted, suggested, not adopted or a draft never use the slot's current value (before, they could, which changed every history: results from seed 16 and earlier are not comparable with later seeds). A run records what a product's own delete path left behind (`forget_residue`) and every tool call that carried an injection's token (`stream.injection_calls`), neither of which is graded. A lived run (T2b) waits for what each session leaves running, which is where a host's session-end hook runs, before the next session starts, keeps each session's stream and writes every session start to a ledger first; a T5 run feeds the haystack whole, keeps a result file per question and announces every reader and judge call in a ledger first, so that no call is made twice. The protocol, fixed before any real run (isolation, arms, the exact agent command, stages with their real-session counts, the analysis, exclusion rules, what is recorded and never committed), is in [`benchmarks/longhaul/RUNNING.md`](../benchmarks/longhaul/RUNNING.md). The pilot (T1, 200 sessions, 6 tasks, 9 arms, one repetition, 70 real sessions; [record](../benchmarks/longhaul/results/2026-11-22-pilot-ef3c4f0.md)) is a harness check and cannot rank products: it found five harness faults (two hidden checks that failed code following the history, the end-of-session capture switched off by a host flag, and a working-directory name that hid the history from two products' start hooks), all fixed, and showed MemoryKing missing two of six facts because one broad `recall` returns a fixed 8 items, about half of them the same session twice. The work after it found more in the harness and fixed them: hidden checks that rejected code which followed the history (29 of the 39 tasks had a check that rejected at least one conforming variant, mostly in whitespace, separators, numeric types, header or end-line wording and a limiter's counting method), a needle worded as hearsay that agents distrusted, and a claude-mem seeding that fired a summary at every assistant message. The protocol now also fixes the measured seed, how a fault in a check is regraded rather than re-run, a probe checklist per arm, and the claude-mem observer budget (about one model call per seeded session; 2,310 as the cap for a 2,000-session history). A pass is one run of one agent on a small synthetic fixture, not evidence of real-task quality.

## Plan tracking contracts

`memory_plan` groups four working-state actions. `plan_save` creates or revises a typed plan; `plan_step` updates one step; `plan_get` reads the current or an earlier revision; `plan_list` pages the project's current plans. Read and checkpoint capabilities, current project and audience authorization, writer ownership, compare-and-set revisions, durable retry keys and the history id are enforced by the existing working-state transaction. A plan is stored as a checkpoint on its task stream, so no schema migration or second store is involved, and backup, restore and purge treat it like any checkpoint. An ordinary task stream cannot turn into a plan, or a plan into an ordinary stream.

Limits are 32 ordered phases, 256 steps, 64 prerequisite ids per step, 16 evidence references per step, 32 lesson references and the checkpoint's 128 distinct dependencies. The working request limit stays 128 KiB, so the maximal fields cannot all be used at once. Plan revisions are never retired, because completion evidence is checked against every earlier revision, so they count toward the tenant's 4,096 live checkpoints and a plan's history is bounded by that capacity. A read verifies the available history up to that capacity; a historical revision the reader cannot open conservatively makes the affected completion `unknown`. A listing inspects at most 64 task streams per page, returns at most 50 plans and stops before the page exceeds 96 KiB; continue an opaque cursor even when a page is empty. A changed frontier, authorization or history invalidates the cursor; restart the listing.

The dashboard shows the agent-reported lifecycle separately from computed progress. Percent complete is not an estimate of elapsed time, cost or remaining effort. Nothing advances a plan automatically; agents call the plan commands with recorded results.

## Troubleshooting

Every error reply carries a `hint` beside its `error` code, and the complete list is in [error codes](error-codes.md), generated from the same table. The most common results:

| Result | What to do |
| --- | --- |
| `no_relevant_memory` | Check project, access, query and evidence; an empty result can be correct. |
| `budget_insufficient` | Increase the explicit budget or narrow task scope; do not strip required constraints. |
| `applicability_unknown`, `essential_policy_unavailable` | For `applicability_unknown`, set the binding fields named in `unbound_fields` (`--binding`, `MEMORYKING_BINDINGS`, a profile). For `essential_policy_unavailable`, resolve policy/evidence access with its owner. |
| `context_changed`, `history_changed` | Discard stale bindings, reconcile and create a fresh client/plan deliberately. |
| `idempotency_conflict`, `source_conflict` | Investigate mismatched bytes; do not invent a new key to bypass the conflict. |
| `source_retired`, `idempotency_result_expired` | The identity remains consumed. Reconcile instead of repeating the mutation. |
| `stale_lease`, `stale_source` | Discard stale output and resolve current source/worker state. |
| `queue_full`, `service_busy` | Back off and drain bounded work; inspect contention. No mutation retry is automatic. HTTP transports answer capacity that frees with time (`*_capacity`, queue, rate, concurrency and session limits, and a database lock or statement timeout) with 429 and unavailability, including a saturated connection pool, with 503; conflicts such as `history_changed` or `session_changed` use 409. A fixed input bound such as `tool_input_limit` stays 400: waiting does not help. |
| `journal_record_limit` | The policy action was refused before any byte was written; the store stays usable. Reduce the action's payload. |
| `maintenance_operation_mismatch` | `end-maintenance` was given an operation id that is not the one recorded by the interrupted backup. Read the anchor's `maintenance_operation` and retry with it. |
| `internal_error`, `dashboard_unavailable`, `service_unavailable` with a `request_id` | Find the matching `request_id=` line in the daemon's stderr log (`serve --log-level`); it names the component, error type and code location without content. |
| `release_expired`, `clock_untrusted` | Restore trustworthy timing and request a fresh authorized response. `clock_untrusted` is also what a store answers when the wall clock is behind the latest time it recorded; `memoryking doctor` reports how far ahead that record is, and [Clock recovery](deployment.md#clock-recovery) says what to do. |
| `recovery_required`, `journal_rollback`, `backup_invalid` | Stay offline and use verified independent recovery evidence. |
| `control_lease_held` | Another instance holds the tenant's lease (a copied control tree, or a different `--instance-id`). It lapses 60 seconds after its last renewal; stop the other instance, or give every process one `--instance-id`. |
| `session_changed` | Sign in again; permissions changed and retained views were cleared. |
| `egress_provider_denied`, `egress_classification_denied` | The daemon's egress policy does not allow that provider or model, or a cited source is classified above the provider's ceiling; change the policy and restart, or rebuild the conversation without the source. |
| `provider_not_supported` | The adapter was built from a policy revision the daemon is not running; rebuild it from the current file. |
| `summary_source_invalid` | A provider-written summary was not the exact delivered reply for that permit; pass the unmodified text and the permit from the same dispatch, or use the extractive method. |
| `provider_unavailable`, `provider_response_invalid` | The provider failed, timed out or answered in an unexpected shape; nothing was admitted and the audit record says `failed`. The dispatch is never retried automatically. |
