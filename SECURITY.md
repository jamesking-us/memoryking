# Security model

MemoryKing stores potentially sensitive agent observations. Run it inside a trusted operating environment and grant each agent only the projects and capabilities it needs.

- The local profile trusts one OS owner, private files and a local Unix socket. Another process with the same OS identity is inside that trust boundary.
- Shared deployments use explicit tenant/project identity, separate database roles, verified transport and bounded delegation. Browser cookies are separate from agent credentials.
- A credential can be retired without abandoning the principal or restoring the store: revoking a principal's last grant or rotating it (`credential issue --rotate`, `credential rotate-owner` for the owner, and `memoryking.shared rotate-owner` for the shared profile's operator credential) advances a per-principal generation that every authorization checks, through the signed control journal, so a restore keeps it retired and hands the recovery admin its current generation. Maintenance release and dashboard sign-in apply the same rule. Credentials issued before generations existed stay valid until then.
- Tool-operation records have their own signed, hash-chained log, checked against the anchor like the journal. It is compacted only for segments whose operations are all resolved and that the oldest retained backup already holds, and consumed operation identities are kept for ever, so a restore never lets an external action be authorized twice. A lease in the database refuses a second control tree that was copied by mistake (`control_lease_held`); it is an accident guard, not a defence against someone who holds the copy and its key.
- The anchor is written before any acknowledgment or watermark that names a new position, and on a timer (one second) for the commit serial and the clock's high-water mark. A database rolled back behind a position, journal record or operation is refused; a rollback that discards only receipts from the last second may not be detected, and a clock that went back by less than a second across a restart is not refused.
- Journal records are never skipped. A policy record that cannot be applied stays pending and is retried; `memoryking journal pending` and `memoryking.shared journal-pending` list it by sequence, kind, tenant and error code without its content. A running process verifies the control journal incrementally against the anchor, so damage inside an already verified prefix is found at the next start, by `doctor` and at restore rather than on each request.
- A model cannot accept its own proposal on its own authority. The lean `confirm` tool is off unless the operator starts the bridge with `--allow-chat-review`, needs the credential's own `review` capability, can decide only knowledge proposals, and records the decision as confirmed in chat with the relaying principal, the proposer and the quoted answer, so a reviewer can audit and revert it. A model's `forget` only files a retirement request: it hides the record from the requester's own briefings and marks it for others, and purging stays an admin action.
- Source text is evidence, not permission. Capturing a note cannot grant a role, accept a policy, run code or activate a procedure.
- Private reads recheck current permissions. The consuming host must use the authorized-conversation integration to rebuild retained model input after revocation; an ordinary memory API call cannot erase a host's old transcript.
- The shared service does not reveal which tenants exist: an unknown tenant and a bad credential get the same answer. Restore refuses a migration role that is a superuser or bypasses row-level security.
- Backups require independent current control information. Restoring content creates a new history and retires old retry namespaces, watermarks and handles.
- Revocation and purge control future access and implemented live copies. They do not promise erasure of previous deliveries, exports, backups or physical storage remnants.
- Nothing leaves the machine for a model provider unless the operator loads an egress policy. The service enforces that policy before issuing a permit (provider, model, host, byte count and the classification ceiling of every cited source) and records every dispatch in an audit that survives purge. Provider keys and tokens are read by the host process from private files, never by the service, and never appear in records or logs.

Do not expose the local dashboard remotely or disable TLS/Host/Origin checks to make a shared setup work. Keep credentials, DSNs, store/control files, migration snapshots and provider inputs out of Git and public issues.

Report a suspected vulnerability privately to the repository owner using an existing private channel. Include a minimal synthetic reproduction, affected revision and impact; do not include live secrets or customer data. No separate public security-reporting service is currently configured.
