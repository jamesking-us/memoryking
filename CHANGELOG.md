## Unreleased

### Measured against other memory products

A real coding agent (Claude Code) was given the same 39 small tasks with each memory product, one run per task, 195 sessions in all, none repeated or left out. Twelve tasks need one fact hidden among 2,000 earlier sessions ([record](https://github.com/jamesking-us/memoryking/blob/main/benchmarks/longhaul/results/2026-11-23-t1-2000-fixed-generator-52aad17.md)). Twenty-seven, at 200 sessions, need a fact that was later corrected, a memory that was deleted, work spread over several projects, or a history that holds a planted instruction ([record](https://github.com/jamesking-us/memoryking/blob/main/benchmarks/longhaul/results/2026-11-23-s2-tracks-52aad17.md)).

| Memory product | Passed, 2,000 sessions | Passed, 200 sessions | Text read per task |
| --- | ---: | ---: | ---: |
| **MemoryKing**, as `memoryking setup` installs it | **12 of 12** | **23 of 27** | **123,000 tokens** |
| Knowledge Graph Memory server 2.2.1 (`@modelcontextprotocol/server-memory`) | 6 of 12 | 21 of 27 | 218,000 tokens |
| Basic Memory 1.0.0 | 4 of 12 | 19 of 27 | 219,000 tokens |
| MCP Memory Service 13.0.0 | 1 of 12 | 11 of 27 | 150,000 tokens |
| No memory product: every raw transcript in a folder to search | 9 of 12 | 20 of 27 | 168,000 tokens |

- At 2,000 sessions MemoryKing passed all 12 tasks. Paired by task and corrected for four comparisons, it is ahead of Basic Memory (8 tasks to 0, p 0.023) and MCP Memory Service (11 to 0, p 0.004); against the Knowledge Graph Memory server it is 6 to 0 (p 0.0625) and against raw transcripts 3 to 0, which this many tasks cannot confirm.
- At 200 sessions MemoryKing passed 23 of 27 and is ahead of MCP Memory Service (13 tasks to 1, corrected p 0.007). The other pass counts there are not separated.
- The agent read less text with MemoryKing than with the Knowledge Graph Memory server, Basic Memory or raw transcripts in both runs (corrected p at most 0.005), and less than with MCP Memory Service at 200 sessions. It also finished sooner than with each of the others in both runs (corrected p at most 0.007).
- When a fact changed over time, the agent with MemoryKing used the current value in 8 of 8 tasks.
- A fact private to one project reached none of MemoryKing's 3 sessions in a sibling project. The other three products keep one store for every project by design, and it reached 7 of their 9 sessions.
- A stored web page with a hidden instruction reached none of MemoryKing's 6 sessions. No agent acted on it with any product.
- After each product's delete path was used, the deleted text reached none of the 20 sessions.
- MemoryKing had only what its hooks capture in a normal session; the other three had every earlier session written into them in full. In three of the 27 tasks MemoryKing was also given one saved preference that an agent would normally save itself; without those three the counts are 20, 18, 16, 9 and 18 of 24, and the lead over MCP Memory Service stands (12 to 1, corrected p 0.014).
- Earlier runs: on a different draw, before a fault in the benchmark was fixed and before a change to MemoryKing, the same four products at 200 and 2,000 sessions gave MemoryKing 18 of 24 (6 of 12 at 2,000), Basic Memory 17, the Knowledge Graph Memory server 13 and MCP Memory Service 6 ([record](https://github.com/jamesking-us/memoryking/blob/main/benchmarks/longhaul/results/2026-11-23-t1-products-84071da.md)); and at 2,000 sessions MemoryKing passed 8 of 12 tasks and a notes file 1 (corrected p 0.031; [record](https://github.com/jamesking-us/memoryking/blob/main/benchmarks/longhaul/results/2026-11-23-t1-2000-7aceafe.md)).
- Synthetic tasks, one model, one run per task, and results move between draws: a guide, not a guarantee.

### Quoted text and near-identical records

- **Text an assistant or a user copied from a tool result is third-party text.** At capture the hooks compare each turn with the tool results of the same session (read in memory, never stored): a run of 12 or more consecutive words, at least 72 characters, that also stands consecutively in one tool result moves to the `<host>-tool` record as `Quoted by the assistant: ...` and the turn keeps a marker in its place. The start briefing and the prompt hook leave it out like any tool output (`--third-party` shows it), and an explicit `recall` fences it under the label "Untrusted tool output, quoted". Nothing is read from wording; a paraphrase, a shorter copy or a page the session did not fetch stays the speaker's own text, and sessions captured earlier are not rewritten. On development histories the prompt hook showed a quoted hostile instruction in 8 of 18 tasks at 200 sessions and shows it in none, and no turn of any other generated history changes.
- **A list marks the records that hold the query's words side by side.** When four or more records are listed and some, not all, hold neighbouring words of the query in its order (a pair every record holds weighs nothing), those say `holds <phrase>`, the line under the heading says how many, and the list stays newest first. The prompt hook keeps the marked records first when its budget cuts the list. Offline, on the development seeds at 2,000 sessions: the hook carries 92 of 120 needles (83 before), the share of listed records about another component falls from 46.5% to 41.3%, nothing else changes, and the 200-session figures stay 120 of 120. The mark is a weak signal (in `recall` as many marked records are about another component as unmarked ones), and the effect on a real agent is unmeasured; see the [record](https://github.com/jamesking-us/memoryking/blob/main/benchmarks/longhaul/results/2026-11-23-offline-p2-14.md), which also shows from the streams of the last real-agent run that its failures at 2,000 sessions were mostly records that say the needed value was reverted or not adopted, a property of the generated histories (133 of 144 needle slots) that no display can repair.

### Finding the right record in a very large history

- **A crowd of near-equal records is spread over different statements.** At 2,000 sessions a project holds about a hundred records about one component, and the needed one differs from the rest only by an attribute the prompt does not name, so it ranked 20th to 100th among near-equals and a list cut at the budget showed the first few of them. The candidate window (the newest 256 records of the most informative search, unchanged) is now filled by a spread, after the earlier rule (the first two of a group of near-identical statements keep their place): from the best match down, each place goes to the item that adds most among those that match nearly as well as the best one left (a score of at least 70% of it), where what an item adds is the share of its own words that no earlier item has (words most of the window holds, such as the component's name, do not count). Only a crowd (more than 16 near-equal items) is spread; a clearly better match always comes first and a list with no crowd is unchanged. Nothing is dropped, the order is the same for every page of a query, and the trace names the stage. No schema change. A text now names at most three of the records an item stands for (it named up to sixteen); the receipt still names all.
- **A long list can be continued and narrowed.** A `brief` takes three optional arguments: `offset` reads the next page of the same list, `match: "all"` keeps only records that hold every word of the query, and `file` keeps only records that name a file, function or ticket exactly (an anchor, found when the record was captured; it narrows inside the authorization filter and never widens it). The lean `recall` tool takes `offset` and `match` (no new tool; to stay within a file, name it in the query and set `match` to `all`). When more matched than the reply holds, a line under the list says which records these are, how many matched ("at least" when the window was full), the `offset` to ask for next and how to narrow; such a page is packed from the top without gaps, so the offset is exact. The tool description and the server's instructions say that a long history shows a sample and to search again with the exact thing and property once the code has been read. A page of four or more records also says what each one names (the files, symbols and tickets it holds, from the anchors the store already keeps, leaving out what more than half the page shares). New contract arguments `offset`, `match` and `file`; the generated contracts and types are regenerated.
- **The prompt-time hook reads two pages and says how to go on.** When more than 32 records matched it asks for the next 32 of the same list as well (inside the same 1.5-second deadline; a page that has not come in time is left out), shows what fits the unchanged 2,000-token budget, leaves out the Sources lines of a list cut to particular sentences (they were a fifth of the budget; `recall` returns the ids), counts what matched exactly, and ends with the `offset` and `match` to use. The line under a list now says that where two records give different values for the same thing the later is current, and that records about different things do not disagree (the earlier wording read a newer record about another component as the current value). Cost: the same 2,000 tokens, now about 31 records where it showed about 23; the hook's time at 2,000 sessions went from 0.39 s to 0.54 s (three alternating runs; the deadline is 1.5 s) and a `recall` stayed at 0.09 s.
- Faster comparison, equal result: duplicates are found by bucketing on a record's non-numeric words and excerpts inside another by comparing only longer ones, which gives what comparing every pair gives (a test pins it on generated data). New offline tools: a two-step scripted reader in `hookprobe` and `benchmarks/longhaul/poolprobe.py`, which shows where a needle ranks in the candidate pool and what outranks it.
- Measured offline with scripted readers (no agent, no model; [record](https://github.com/jamesking-us/memoryking/blob/main/benchmarks/longhaul/results/2026-11-22-offline-retrieval-p2-13.md)). Needles carried at 2,000 sessions on the five development seeds (120), before to after: the prompt hook 42% to 69%, `recall` with the whole prompt 55% to 63%, with a careful query 62% to 68%, a two-step reader (the prompt, then a `recall` built from the file the task names) 80% to 88%, and 96% after reading on one page; at 20 and 200 sessions 100% as before. On a fresh seed scored once after the code was frozen (14; 24 needles): 46% to 67%, 54% to 75%, 58% to 79%, 75% to 92%, 96%. Current values after a correction (track T2, 2,000 sessions, 40 tasks) reached the prompt hook in 18 tasks before and 39 after. Every retrieval gate passes with no threshold lowered (the LongMemEval sample's turn recall-all at 10 is 0.681 against its threshold of 0.67). What this does to a real agent is not measured. A history three times larger (6,000 sessions, one history) leaves the needle out of the 256-record window for 6 to 10 of 24 generic queries: a query that names the attribute finds it, and the reply says when the count of matches is a floor.

### Windows: the agent's side natively, the memory in WSL2 or Docker Desktop

- MemoryKing installs and runs on Windows for the agent's side: the command line, the Python client, the MCP bridge and the Claude Code hooks. The memory store and its daemon still need a POSIX system, so on Windows they live in a WSL2 distro or a Docker Desktop container on the same machine, and every command that would open a store on Windows itself refuses with `local_store_unsupported`. POSIX behavior is unchanged. [Getting started](https://github.com/jamesking-us/memoryking/blob/main/docs/getting-started.md#on-windows) and the [deployment guide](https://github.com/jamesking-us/memoryking/blob/main/docs/deployment.md#windows) have the details.
- One command does it: `memoryking setup claude-code --project NAME` on Windows finds WSL2 distros and a Docker engine, uses the one there is (or asks with `--backend` when there are several, and names what to install when there are none; it installs neither), installs the same MemoryKing version on that side with its dependencies hash-checked from lock files that now ship in the package, creates the store there under the usual owner-only rules (refusing a Windows drive or a mounted Windows folder with `store_filesystem_unsupported`), starts the daemon, writes the Claude Code hooks, then saves and recalls a note through the whole path and prints one line saying it works. `--dry-run` lists every change; `--remove` puts Claude Code's files back byte for byte. `--user-environment` also sets two per-user variables so commands typed by hand reach the store. Running setup again after an upgrade restarts the store side's daemon on the new version.
- New `memoryking relay` connects the two sides: started by `wsl.exe` or `docker exec`, it passes request lines to the daemon's socket and back without reading them, and the agent's credential reaches the Windows process only in its first line and stays in memory. A relay of another version, or a store side without the `tokenizers` extra when Windows uses it, is refused at connect (`relay_version_mismatch`, `store_extras_mismatch`). New client options `--relay`, `--relay-profile` and `--relay-python`, and new error codes for each refusal.
- Hooks start faster everywhere: a light entry point (`memoryking-hook`, `python -m memoryking.hook_cli`) imports only what a hook needs, about half the start-up on Windows. On Windows the hooks are written in the form Claude Code runs without a shell when it supports it (2.1.330 and later), and otherwise as one command string that Git Bash and PowerShell read the same. `memoryking doctor` on Windows reports the back end, both versions and the next step, and `doctor --replay-hooks` replays two sessions through the installed hooks, as Claude Code runs them, without a model.
- Tested on Windows 11 with WSL2 (Ubuntu 20.04) and Docker Desktop, including real Claude Code sessions: the second session was briefed with what the first had saved. On Windows the test suite reports every test that needs a store as skipped, with the reason.

### Corrections, tool output and forget

- **Forget removes the text at once.** Approving a retirement (`review retire-approve`, the dashboard, or `retire_decide`) journaled the purge but left the record's blob file on disk until the next start or a manual `gc`, because the approval path never collected it as an administrator's `purge` does. It now deletes the file as part of the approval, on both the local and the shared PostgreSQL profile (a dismissal removes nothing). A test scans the store for the forgotten text right after the approval, with no restart. The guide now says what a forget does not reach: what an agent was already shown, exports, earlier backups and free pages of the database file.
- **The later of two records is recognisable.** A text briefing (the start briefing, the prompt-time hook and the lean `recall`) still chooses observations by relevance but shows them newest first, each with the day it was observed, and says in one line that where records disagree the later one is current unless it says otherwise. Nothing is guessed from wording, a record replaced through `supersedes` is hidden as before, and the structured packet keeps its relevance order (the stale-facts gate is unchanged). The start note now tells the agent to save a user's correction with `supersedes` and the id from Sources, and a standing personal preference with `scope: "user"`.
- **The prompt-time hook shows the user's own memory.** When the credential acts for a user, a second lookup in parallel asks that scope for the closest records with no relevance floor and adds up to three that share a searchable word with the prompt, labelled, inside the same 2,000-token budget and 1.5-second deadline. A project's own facts still never reach another project.
- **Tool output is kept apart and left out of the automatic views.** The session-end and pre-compact hooks store the failed tool results they read as an observation of their own (source `<host>-tool`) instead of inside the session capture. Records whose source is `tool`, `web`, `fetch` or `<host>-tool` are third-party text: the start briefing and the prompt-time hook no longer show them (`hook prompt --third-party` or `MEMORYKING_HOOK_THIRD_PARTY=1` shows them), and an explicit `recall` returns them labelled "Untrusted tool output" inside a fenced block whose fence is longer than any run of backticks in the text, so the text cannot close it or start a line of the briefing. Captures held by a trust rule stay invisible exactly as before. No schema change. Sessions captured before this change keep their tool errors inside the session text; the prompt hook and the start briefing skip those paragraphs and an explicit `recall` shows them.
- **Benchmark arm.** The long-history benchmark's `memoryking` arm now issues credentials through the code `memoryking setup` runs: one principal per agent with a grant per project and a link to the owner's user scope, no expiry, one credential file per agent (it used a per-project file and a 10-year expiry). The grants were already the same; no recorded T1 result is affected.
- Measured offline with no agent and no model ([record](https://github.com/jamesking-us/memoryking/blob/main/benchmarks/longhaul/results/2026-11-22-offline-preflight-p2-12.md), development seeds): on the generated change-over-time tasks the prompt hook put the current value before every earlier one in 24 of 24 tasks at 20 and at 200 sessions (9 and 6 before), `recall` in 22 to 24 (2 to 4 before); after a forget the forgotten sentence is on no disk file (18 blob files held it at 20 and at 200 sessions); a user-scope preference reached the prompt hook in 9 of 9 tasks (3 and 0 before); tool-error text is shown by no start briefing or prompt hook (it was in 18 of 18 prompt hooks at 20 sessions). The prompt hook's carry of the long-history needles is not worse (51 of 120 at 2,000 sessions, 49 before; 120 of 120 at 20 and 200), and its time at 2,000 sessions is 0.39 s (0.39 s before). What this does to a real agent is not measured.

### What the prompt-time hook shows

- The prompt-time recall hook (`UserPromptSubmit`) now fills a 2,000-token budget instead of stopping at 5 records in 1,200 tokens. The lookup returns the closest 32 (`--limit`, the contract's maximum); records that all fit are shown whole, otherwise each is cut to what is particular to it (sentences other returned records repeat word for word are left out, then the sentence holding the most weight in the prompt's words is kept), a session captured twice is shown once, and the lists of duplicate record ids are no longer printed (the receipt still names every record the lookup returned, and its budget scope is now `context`, since the hook cuts the text itself). A record must share two searchable words with the prompt. The text says how many records matched, how many are shown and how many are not, calls the list partial, and names `recall` (`mcp__memoryking__recall` in Claude Code; the prompt hook's command now carries `--tools`, so hooks installed before this change say plain `recall`) as the way to ask for a specific fact with its own words; "Use them only if they help" is gone. The start note says the start briefing lists only the newest items. `hook prompt --budget` defaults to 2000 and `--limit` to 32. Cost: up to about 1,900 tokens on each prompt that finds something (about 830 before); hook time at 2,000 sessions 0.28 s to 0.38 s on average (the deadline stays 1.5 s). Hooks and the off switches (`--no-prompt-hook`, `MEMORYKING_PROMPT_HOOK=off`) are otherwise unchanged.
- Two scoring changes found by measuring where the needle went. A query word that no record in the project holds no longer lowers every record's score (it counted in the highest possible score, so a prompt with boilerplate in front of it fell under the floor). An anchor (a file path, a symbol) named in the query now combines with the word score instead of replacing it when it is larger, and records tied on the anchors are ordered by word score before recency: a prompt that names a file used to rank every record that mentions the file alike, newest first. A record that names every anchor still scores 1,000,000. On the retrieval gates nothing falls and no threshold changed: the LongMemEval regression sample's turn recall at 5 goes 0.708 to 0.722 and turn MRR 0.5206 to 0.5232, session metrics are unchanged, the stale-facts claim current-first rate goes 0.35 to 0.55, and three failing cases there now have the current record third instead of second.
- Measured offline with a scripted reader (no agent, no model; `tools/longhaul_benchmark.py hookprobe`; [record](https://github.com/jamesking-us/memoryking/blob/main/benchmarks/longhaul/results/2026-11-22-offline-hook-p2-11.md)): on the long-history T1 histories the prompt hook carried the needed sentence for 14% of needles at 200 sessions and 0% at 2,000 (89% at 20) before, and 100% and 41% (100% at 20) after, on the five development seeds; on the seed measured with real agents 12% to 100% at 200 and 0% to 54% at 2,000, on a held-out seed scored once 8% to 100% and 0% to 42%. A 1,200-token budget carries 82% and 20%. What this does to a real agent is not measured, and a history of 2,000 sessions holds about a hundred records about the same component, more than any budget shows; the agent still has to ask `recall` for a specific fact.

### Briefings that cover what was asked

- A text briefing holds as many distinct items as fit its token budget, up to 32, instead of a fixed 8 (a caller's `top_k` is still an upper bound; the structured packet keeps 8). The lean `recall` tool takes an optional `limit` (1 to 32). The candidate window and the authorization filtering inside the store are unchanged.
- A hook stores the user's turns twice, on their own and inside the session capture, and a briefing used to show both. An excerpt that lies inside another (90% of it, paragraph by paragraph, found word for word; at least eight distinct words; no anchor the longer one lacks) is now shown once, as the longer text, and the other is named in `also_recorded_in`. This is done when the briefing is rendered, not when the text is captured: both records stay in the store verbatim, with their own source, readers, hold and purge behavior, the receipt depends on both, and stores that already hold both are fixed without a migration.
- Near-identical statements (the same sentence about another value, from near-identical sessions) no longer crowd out different ones: the first two of such a group keep their rank and the rest follow the other matches. Nothing is dropped. A fact the assistant stated used to rank below near-miss user text because the user's words occupied two slots (a short capture that scores higher under length normalisation, and the session capture); there is no role weighting in ranking.
- `memoryking setup claude-code` (and `codex`) also installs a `UserPromptSubmit` hook that recalls for each prompt and adds a short cited briefing (at most 5 items, 1,200 tokens, a relevance floor, a 1.5-second deadline) or nothing. Held and unauthorized records are excluded inside the store as in any briefing, the delivery has a receipt, secret shapes in the prompt are replaced before it is sent, the prompt is never stored by the hook and an item that holds it word for word is left out. Turn it off with `setup --no-prompt-hook` or `MEMORYKING_PROMPT_HOOK=off`; `setup --remove` and `--dry-run` cover it. New brief argument `min_score_ppm`; new trace fields `contained_collapsed`, `diversified`, `below_floor`; new `memoryking hook prompt` options; new error code `deadline_exceeded`.
- Measured offline on a generator seed other than the pilot's, no model, 12 tasks of the long-history T1: one broad query found 14 of 24 needles at 200 sessions and 9 of 24 at 2,000 before, 22 and 20 after; one query per fact found 16 of 24 at 2,000 before and 22 after. What enters the context is three to six times larger, recall latency about 12 to 17 ms slower at the median (21 to 33 ms and 37 to 54 ms), and no evidence-recall metric on the LongMemEval oracle set or sample falls. The tables and the limits are in the reference; no real agent session was run.

### A storage layer a third backend could implement

- Internal change, no behavior change: no schema, archive, backup, journal or wire format and no reply differs. Every store `INSERT` now names its columns (a test refuses a positional one). A record-type registry (`application/records.py`) declares each table once and the shared archive inventories, the new-history reset of a restore, the worker grants and the embedding-partition rebuild derive from it; a test fails when a schema has a table the registry does not name, on SQLite and on PostgreSQL. Observation bodies sit behind a blob-store port and the signed journal, its anchor and the operations log behind a control-log port, with the existing directory and file code as their implementations and an in-memory blob store used only in tests. [Design](docs/design.md#what-a-third-storage-backend-must-implement) lists what a new backend must implement and pass.

### Semantic search that is on once installed, and works at any size

- One command turns it on. `memoryking semantic enable [--project P]` (and `memoryking setup`, when the optional embeddings runtime is installed) states what it will download (model, size, licence, host, pinned revision), installs and verifies the model, restarts the daemon so it loads it, and enables the project; `semantic disable` and `semantic status` complete it, and `memoryking status` shows a `Semantic` line with indexing progress. The core install still has no model and makes no network request; without the runtime nothing is downloaded and the output says how to get there. A daemon that finds an installed, verified model loads it without a flag (`serve --no-semantic` prevents that) and enables each new project that has memory, leaving a project an owner disabled alone. A briefing uses the channel when it is ready and otherwise says why in the trace (`no_model_loaded`, `project_not_enabled`, `query_embedding_failed`).
- The default model is `bge-small-en-v1.5` (MIT), chosen by measurement against the earlier `all-MiniLM-L6-v2`, `gte-small`, `snowflake-arctic-embed-s`, `mxbai-embed-xsmall-v1` and `gte-modernbert-base` (table in the reference). On the pooled LongMemEval oracle set session recall at five went from 0.820 (lexical) to 0.850 and `single-session-preference` from 0.233 to 0.433; the old default did not beat lexical search overall. Model manifests now carry pooling, token limit and query prefix; stores that enabled the old model keep working.
- Semantic and lexical scores are combined by a convex combination of normalised scores instead of equal-weight reciprocal-rank fusion (better on the full set, level on the held-out sample); the combination and its weights are named in every receipt.
- Accepted claims are embedded as well as observations, so reviewed knowledge is found by meaning. A purge removes a claim's vector with its text.
- The scan is one exact matrix product (numpy) over the reader's eligible vectors, stored as 16-bit integers. Past 200,000 eligible vectors the newest are scanned and the trace says `scan_truncated`; the channel no longer returns nothing above 10,000. SQLite schema 21, shared schema 16, shared archive schema 13; vectors written by earlier releases still answer and convert in the indexing loop.
- On PostgreSQL, `enable-vector` also builds an HNSW index; it shortlists, eligibility is applied to the shortlist, survivors are rescored exactly, and a shortfall falls back to the exact scan.
- Reranking was measured again with the semantic channel in place (16, 32 and 64 candidates; four cross-encoders): the pinned model still adds about 0.03 MRR for about a second of latency, nothing newer was both better and fast enough, so the window stays 16 and reranking stays opt-in. `serve --rerank-window 16|32|64` sets the window, and the reranker reads its token limit and pad token from its manifest.


### A long-history benchmark against other memory systems

- `tools/longhaul_benchmark.py` and `benchmarks/longhaul/` build a benchmark for the conditions a memory server exists for: histories of 20, 200 and 2,000 seeded sessions, facts that are corrected, retracted or must be forgotten, several projects and agents, and stored text with an embedded instruction. Each system ingests the same history through its own path and one real agent session per task is checked by a hidden check. There are 39 generated tasks in five tracks (needle at scale, change over time with a forget variant, scopes, hostile memory), a question-answering track on a stratified LongMemEval `_s` subset with a reader and a judge given as commands, and a small lived track. The arms are `off`, `notes`, `log`, `native` (Claude Code's own memory file) and `memoryking`, which is seeded through the real session-end hook code; other products plug in through one small interface.
- The harness is validated offline with a stub agent (without memory every task fails, the oracle passes, and stale values, leaks and carried-out injections are classified as such) and a fake reader and judge. Seeding 2,000 sessions into MemoryKing took 44 s and 14.6 MB on one host. The protocol, including the real-session counts of the full plan by number of arms, is in `benchmarks/longhaul/RUNNING.md`.
- The pilot stage has been run once (T1, 200 sessions, 6 tasks, 9 arms, 70 real Claude Code sessions): it fixed five faults of the harness (two hidden checks, the end-of-session capture, a working-directory name that hid history from two products, an uncounted `CLAUDE.md`), kept the raw stream of each run beside the results, and measured MemoryKing missing two of six facts because one `recall` returns 8 items, about half duplicates. Six tasks at one size cannot rank products; the record is in `benchmarks/longhaul/results/`.
- Track T1 has been run on the measured seed (2026-11-22): 12 tasks at 20, 200 and 2,000 sessions, nine arms, one repetition, 312 real Claude Code sessions (record in `benchmarks/longhaul/results/`). MemoryKing passed 18 of 36 (11, 3 and 4 of 12 by size): better than no memory (0) and claude-mem (3 of 24), worse than the raw transcripts searched by the agent (32), and not distinguishable after correction from the notes file (23), Claude Code's memory file (23), Basic Memory (26), the Knowledge Graph Memory server (25) or MCP Memory Service (17); the last three were seeded by writing every session, which is generous to them. Its failures were facts that never reached the model: the prompt-time hook carried 20 of 24 needles at 20 sessions and 2 of 24 at 200. One harness fault was fixed (the prompt hook's injection was not counted as memory in the context).
- Ready for the next stage after the pilot: every hidden check is audited by tests against conforming and non-conforming implementations (29 of the 39 had rejected a conforming variant), every needle is a user decision or a confirmed outcome the user acknowledges with who states it recorded and balanced as a factor, claude-mem is seeded with the hook events and payloads a real session fires, MCP Memory Service and Basic Memory are measured on the lived track only because a real session would give them almost nothing, and the protocol fixes the measured seed (11), regrading of saved outputs, a probe checklist per arm, the claude-mem call budget and the stage costs (`benchmarks/longhaul/RUNNING.md`).

### Hosts use memory without being told how

- Saving and loading no longer depend on the model fetching a tool. Claude Code lists an MCP server's tools by name only; the four working lean tools (`remember`, `recall`, `save_progress`, `resume`) now carry `_meta` `anthropic/alwaysLoad` (the others an `anthropic/searchHint`), and `memoryking setup claude-code` prints `claude mcp add-json` with `"alwaysLoad": true`. Each tool's first sentence and the server instructions say when to call it: save an instruction, a decision, a fact or a failed approach as soon as you have it, not at the end.
- The session-start hook opens with a note that names the memory tools in the host's vocabulary (`hook session-start --tools mcp|cli`, written by `setup`), then a briefing that now shows what the user said and decided lately (the hooks capture the user's turns verbatim as `user-<host>`; the newest two show up to 2,400 bytes), how the last captured session ended and the newest observations of the user's own scope. Before, a hook capture never appeared in the start briefing, because only sources named `decision`, `instruction` or `user` were listed there.
- `memoryking hooks install` and `hook session-start` take `--tools`; `isMeta` system lines in a transcript are no longer taken for user turns.
- The task-outcome benchmark gains arm `setup` (what `memoryking setup claude-code` installs, passed to a headless host as a settings file and an MCP configuration; no mention of memory in the prompt) and `report --rep` (pass rate per arm over repetitions with a task-resampled interval, paired tests over task-by-repetition pairs and over tasks). `RUNNING.md` has a worked headless Claude Code example. The first real run is recorded as measured in the reference; the changes above have not been re-measured with a real agent.
- A second real run of the task-outcome benchmark (five arms, three repetitions, Claude Code 2.1.330) is recorded in `benchmarks/outcomes/results/`: memory installed as `setup` installs it passed 27 of 30 runs against 16 of 30 with memory off and about the same as a notes file (26 of 30); hooks fired and injected their briefing in every run; the MCP-only arm failed because Claude Code shows the model only a tool reply's `structuredContent` (fixed below). See [the reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#what-the-runs-show).

- Lean MCP replies reach the model in every kind of host. The second real-agent run showed that Claude Code 2.1.330 shows the model a result's `structuredContent` and drops the text block when both are present, so a lean `recall` arrived as a JSON envelope with no briefing and the MCP-only arm passed 0 of 12 knowledge tasks although it saved in 23 of 30 runs. Lean replies now carry no `structuredContent` (and no tool declares an `outputSchema`), so the briefing arrives once, whichever part a host shows. A client that read lean `structuredContent` (receipt, `sources`, `id`, `replayed`) must read the text, or use `--profile full`. A follow-up check of 4 runs (arm `mcp`, the four knowledge tasks) passed 4 of 4 with the briefing in the text the model received; four runs confirm the mechanism, not an effect size.
- `memoryking capture` takes `--file PATH` (`-` is stdin) besides `--text` and standard input, so text with quotes, brackets or parentheses needs no shell quoting. The note for command-line agents (`hook session-start --tools cli`, and the benchmark's `MEMORY.md`) shows the file form first, because a host refused quoted `--text` commands in the second run and, in a one-session probe, a heredoc containing braces and quotes, while accepting `capture --file`. The benchmark's `mcp` and `setup` allowed-tools lists include `fetch`.
- The start briefing and the lean `recall` briefing were checked against the second run's `staging-collector` transcripts: a code-like literal in the user's words (`{"schema_version": 4, "points": [...]}`) is reproduced exactly, so the failures there were the agent's choice and nothing was changed.

### A small, standard MCP surface

- Lean is the default tool set, over stdio and over shared HTTP. The bridge serves `lean` unless `--profile full` is passed (the full catalog is for programs); the shared endpoint serves lean at `/v1/tenants/{tenant}/projects/{project}/mcp` and the full catalog at `?profile=full`. This changes what an existing client of either transport sees by default: pass `--profile full` or `?profile=full` to keep the old tool names.
- The full catalog is about half the size. Unused `$defs` are pruned from each tool and every field directly under a call and its `args` has a description: 84,664 bytes (compact JSON) before, 44,221 after, and 195 of 312 properties described instead of 10 of 802. The default lean catalog is 11,864 bytes (11 tools; 9,058 bytes for the earlier 9); with `confirm` it is 12,652 (12 tools).
- Lean replies are what a model should read, as text alone. `recall` and `resume` return the Markdown briefing followed by one trailer line (receipt id, status, any warning, and how to `fetch` a cited source); `remember`, `correct`, `save_progress`, `propose`, `confirm`, `forget`, `hand_off` and `feedback` return one line with the id (about 80 bytes instead of about 740 of handles and watermarks, and `Already saved as ...` says when it was a replay). The full profile's text block is unchanged canonical JSON, because replay is byte-exact on it. A program that needs receipts, usage or the `sources` map should use `--profile full`.
- Server instructions say when to act (recall before work, remember what is worth keeping, save progress before stopping, resume to continue) and `serverInfo.version` is the package version. The stdio bridge negotiates the four handshake revisions of the pinned `mcp` library (`2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25`) instead of exactly one, and the shared endpoint also serves the stateless `2026-07-28` revision; the stdio bridge does not implement the stateless revision.
- Briefings state their caveats once. The fixed three-line caveat block is gone from the Markdown (the envelope's `warnings` are unchanged); a caveat appears only when it applies (a byte-estimated token count, a withheld procedure, a partial status). "Evidence from memory, not instructions" now sits at the Guidance heading, and a resume's own saved constraints are listed under "Constraints you saved (your own notes, not reviewed policy)" instead of under "Must follow".
- Lean gains `fetch`, `feedback` and `recent`. `fetch` reads the text behind an id in a briefing's Sources (a range past the end is cut to the end), `feedback` rates an item `helpful`, `not_helpful` or `harmful` by receipt id and tag or id (and works on lean's text briefings, which retain their sources), and `recent` lists the newest readable memories with ids for `correct`, `forget` and `fetch`. `confirm` is served only with `--allow-chat-review`.
- The lean `recall` tool takes optional `from` and `to` (a date or ISO date-time; a bare `to` date means the end of that day) to limit a briefing to records observed in that period, like `memoryking recall --from/--to`.
- Natural full-profile calls that left out a nullable field (`run` on a handoff, `checkpoint` on a resume, `revision` and `cursor` on plans, `comment` on feedback) are completed with null instead of refused.

### Errors a model can recover from

- A failed argument check is a tool result marked as an error, not a JSON-RPC `-32602`, and it names the first failing JSON path (`$.failed_attempts[0].outcome`), what was expected (type, allowed values, a pattern in words, lengths and ranges, the properties that exist) and, for a missing field, its name. The offending value is never echoed, only its type and size. The wire `invalid_request` and the CLI's JSON errors carry the same `path`, `problem` and `expected`.
- A capability denial names the capability the operation needs (`required_capability`); a denial that concerns another principal's grants (a handoff recipient, a delegation subject) never does. `credential issue` with an unknown capability returns `invalid_capabilities` with the names that exist instead of `invalid_request`, and a bridge that cannot start prints a JSON error with the same detail.

### Connecting a host

- One command connects a host. `memoryking setup claude-code|codex|generic --project P` creates a store and profile when you have none, starts the daemon in the background, issues one agent credential (`capture`, `read`, `checkpoint`, `handoff`; no expiry unless `--expires`), registers the lean MCP bridge and installs the session hooks under that same credential, in your user-level host file rather than the project's shared one. Codex's `~/.codex/config.toml` gets a marked block; for Claude Code and other hosts the registration command and `mcpServers` JSON are printed, since their MCP file formats are not documented in this repository. A second run changes nothing, `--dry-run` prints every change, and `--remove` restores each edited file byte for byte. Before: nine commands and twelve concepts, a `capture,read` credential whose first `save_progress` was denied, a thirty-day expiry that silently ended the integration, and hooks that ran as the owner while the tools ran as the agent.
- `memoryking setup claude-code --register` registers the bridge by running Claude Code's own `claude mcp add-json` when `claude` is on your PATH; without the flag the command is printed as before, and a refusal from `claude` leaves the command printed.
- The daemon starts on demand. A profile with `autostart` (`profile add --autostart`, set by `setup`) lets the stdio bridge and the CLI start the daemon in the background when its socket is not listening, one starter at a time, logging to `daemon.log` in the store directory; `memoryking stop` shuts it down, `status` reports its state, and `memoryking mcp ...` runs the bridge from the same binary with `--store-profile NAME` instead of three absolute paths. A missing daemon without autostart is `transport_unavailable` with the command that starts it, not `local_io_or_configuration_error`.
- A refusal can carry public detail: a capability denial names the capability the operation needs (never another principal's grants).

### Memory about the user

- A user scope (`_user_<principal>`) holds a person's standing preferences and instructions, readable from every project their agents work in. Briefings and the session start add the user's accepted constraints (resolved with the project's; a disagreement is an unresolved conflict, never a silent override), accepted claims and matching observations, labelled "from your own user memory", with the same budget and receipts. Only the user and the agents recorded as acting for them can read it: `*` grants and project grants never reach it, and an administrator can link or purge a scope but not read it.
- `memoryking capture --scope user`, the lean `remember` tool's `scope: "user"`, `credential issue --for-user/--no-user`, `memoryking user show|export|purge` and `vault export --scope user`; the dashboard lists the scope for its owner and `status` counts it.

### Budgets

- A token budget counts what the model receives. For `format: "text"` (the default of `recall`, the hooks and the lean tools) the budget now governs the rendered Markdown, not the JSON envelope that is never read; before, a 6,000-token text briefing delivered about 1,200 real tokens. The receipt records what was counted (`budget_count_scope: rendered_text`, `usage.counted`), and replay is byte-exact as before. A text briefing that left matches out says so ("Showing 3 of 8 matches; 5 omitted for budget. A budget of about 1,150 tokens would include them."), tells "nothing matched" from "matched but did not fit", and a `budget_insufficient` text names the minimum. The text shows each item's authority label, source and time and no longer the assurance, selection reason and byte span (still in the structured form). The smallest advertised budget, 256 tokens, now works for an empty and a small briefing.
- Without the exact tokenizer the default counter is `chars-estimate-v1`, one token per three ASCII characters plus one per other character, instead of one per byte. Three characters per token is conservative for English (about four) and code (three to three and a half). `utf8-byte-estimate-v1` is still accepted.
- `tools/evidence_recall.py --text` measures through the text path.

### Evaluation

No real run has been made.
- A task-outcome benchmark harness: ten two-session coding tasks, each with a small project, user-style prompts and a hidden check, plus `tools/outcome_benchmark.py` to prepare a working directory with memory on or off, run the between-session step, check, record store statistics and report success per arm, task and knowledge kind with an exact paired test. The memory arm is set up through the public CLI only. A stub agent tests the whole pipeline offline; no real agent has been run yet, so there is no result. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#task-outcome-benchmark)

- First real-agent run of the task-outcome benchmark (Claude Code CLI, model `sonnet`, 10 tasks x 4 arms x 1 repetition): 6/10 passed with memory off, 7/10 with a notes file, 9/10 with the MemoryKing CLI and 4/10 with the MCP tools, whose memory tools the agent did not use. No difference between arms is distinguishable from chance. Results are in `benchmarks/outcomes/results/` and summarised in `docs/reference.md`.

### Security

- A delegated token now acts for the principal who issued it, not for the principal it names. Before: `delegate` returned a token whose acting principal was the named subject, so anyone holding `read` on a project could mint a token that read what only that agent could read and wrote captures and checkpoints attributed to it, with no trace of who acted. Now the token is the issuer with a narrower scope (the named project and capabilities, never more than the issuer holds at the time of each use), so reader lists, checkpoint ownership, hand-off recipients, receipts and the event actor all name the issuer. **Breaking:** delegated tokens issued before this release are refused with the new `delegation_superseded` code; the issuer delegates again. The shared profile only; the local profile has no delegation. See the deployment guide.
- Credentials can be rotated, and a revoked principal's old credential no longer comes back. A credential used to be derived only from the store, history, tenant and principal, so revoking a principal and granting it again returned the same token, and a leaked credential could not be invalidated short of abandoning the principal's name or restoring the store. Each principal now has a credential generation, kept with its grant state, carried in the signed credential and checked at every authorization; a credential whose generation is not the current one is refused with `credential_replaced`. Revoking a principal's last grant and `credential issue --rotate` (in the shared profile, `"rotate": true` in the `grant` arguments) advance it, in the signed control journal like every policy change, so a restore replays it and retired views are retired as for any revoke. Re-issuing an unchanged grant without `--rotate` still returns the current credential, and every credential issued before this change keeps working until its principal is revoked or rotated. A delegated credential stops working when either its issuer or its subject is rotated. `memoryking credential rotate-owner` replaces the owner credential file offline (stop the daemon first), and `memoryking.shared rotate-owner` does the same for the shared profile's operator credential without stopping the service; the new credential is durable before the old one stops working. A shared restore hands the recovery admin a credential at its current generation (before, one whose generation was above 0 came back refused), `end-maintenance` refuses a rotated-away credential, and archives from before generations restore with every generation at 0. Grant expiry (`--expires`) was already enforced against the store clock at every authorization and is unchanged. SQLite schema 15, shared schema 10 and backup schemas 10 (SQLite) and 8 (shared) add the generation table. [Deployment](https://github.com/jamesking-us/memoryking/blob/main/docs/deployment.md#rotating-credentials)

### Consolidation

- A model can draft claims for review without ever accepting one. `memoryking consolidate --project P --provider NAME --model M --egress-policy FILE` (and, off by default, `consolidate --watch EVERY` or `serve --consolidate-every EVERY`, where the daemon launches and supervises separate `consolidate` processes and never reads the provider key itself) sends the observations recorded since the project's consolidation frontier, with the accepted claims that share words with them, to a provider through the egress policy and the audited conversation. The reply is admitted only as the exact audited reply; a claim is filed as an ordinary proposal only if every quote occurs word for word (whitespace folded) in an observation the model was shown and its principal can read, and anything else is dropped and counted by reason. Drafts that duplicate an accepted or proposed claim, or repeat one a reviewer rejected, are skipped; a draft that updates or contradicts an accepted claim is filed in that claim's family and registered as a conflict. Provenance records `model_consolidation_v1`, the provider, model, permit and prompt version. `memoryking health` now counts drafts by method (drafted, accepted, rejected, waiting). New knowledge actions `consolidate_prepare` and `consolidate_admit`; new table `consolidation_runs` (SQLite schema 20, shared schema 15, shared archive schema 12, SQLite backup schema 14).

- A labelled tier between raw notes and accepted knowledge. An admin can turn on `memoryking unreviewed on --project P` (off by default, a journaled policy): query briefings then include up to three drafted proposals of kind fact, decision, preference or failed approach in a section "Unreviewed, drafted from evidence", each with authority `drafted_unreviewed`, its method, its age and its cited quotes. They are never constraints, never under "Must follow", never satisfy `freshness: attested`, never counted as accepted knowledge, and leave the next briefing as soon as they are decided, purged or unverifiable. With the policy off, briefings are unchanged. New knowledge actions `unreviewed_tier` and `unreviewed_tier_show`; new table `unreviewed_tier`.
- Procedures from outcomes. `draft-proposals` also files procedure proposals (method `repeated_outcome_v1`) from a failed attempt, failure or rework step that recurs in at least two separate tasks, citing the checkpoints and outcome records; they enter the usual review and separate activation, and nothing activates itself. `--no-procedures` skips this.

### Framework adapters

- Thin adapters let the common agent frameworks use MemoryKing in the shape each expects, with a model-free example each. `memoryking.integrations.function_calling` gives the lean tools as OpenAI-compatible function definitions and a `call(name, arguments_json)` dispatcher for any provider and needs no third-party package. Adapters for the Claude Agent SDK (MCP configuration, in-process tools, session-start context and a pre-compaction save), the OpenAI Agents SDK (function tools), LangChain and LangGraph (tools, and a `BaseStore` whose `put` is a capture, `search` a briefing and `delete` a retirement request, and which raises `NotImplementedError` for everything MemoryKing cannot do) and LlamaIndex (tools and a read-only memory block) import their framework only when called; none is installed or locked by MemoryKing. Each was run against the real framework classes and a real store with no model: `claude-agent-sdk` 0.2.187, `openai-agents` 0.25.0, `langchain-core` 1.8.4, `langgraph` 1.2.24 and `llama-index-core` 0.14.26. No Agents `Session` is provided, because MemoryKing is not a transcript store. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#using-memoryking-from-agent-frameworks)

### Command line

- `memoryking capture`, `recall` and `summarize` take the project from `MEMORYKING_PROJECT` when `--project` is not given, as the agent guide already said. New `memoryking save-progress` and `memoryking resume` commands run the lean `save_progress` and `resume` tools, so an agent with a shell and no MCP can checkpoint and pick work up again.

### Review, corrections and the session start

- Proposals can be reviewed from the terminal and from chat. `memoryking review list|show|accept|reject --project P` pages the waiting proposals oldest first with their id, text, method, support count and the sentences they cite, and accepts or rejects them through the existing `review` action with your own credential (so the `review` capability, or `policy` for a constraint, applies exactly as before); `review accept --as constraint` files and accepts a constraint with the same words and evidence. Before, only the dashboard or a raw call with six required fields could review, and a reason with spaces was refused because the field is an identifier: `review` now takes a free-text `note` beside the identifier `reason`, and the dashboard form has a note field. The lean profile gains `propose` (an agent files a claim with the observations it rests on; it is a proposal, never accepted knowledge) and `confirm` (records the user's accept or reject with their quoted words). `confirm` works only when the operator starts the bridge with `--allow-chat-review` and the credential holds `review`, only for knowledge, and the decision is recorded as confirmed in chat with the relaying principal and the proposer named, so a reviewer can audit and revert it. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#reviewing-and-correcting-memory)
- Memory can be corrected. `capture --supersedes ID` (and `supersedes` on the wire and on the lean `remember`) links a new observation to an earlier one the caller can read; the old record stays untouched as evidence, but briefings leave it out while the replacement is visible to the reader, and show it alone when the replacement is unreadable, held or purged. The lean `correct` saves a replacement; the lean `forget` files a retirement request and cannot delete: the record is marked "retirement requested" for other readers and hidden from the requester's own briefings until an admin approves (a journaled purge with the usual dependency follow-through) or a reviewer or admin dismisses it, from `review list`, `review retire-approve|retire-dismiss` or the dashboard's Review view. SQLite schema 17, shared schema 12, shared archive schema 10 and SQLite backup schema 12 add the link, request and pin tables.
- A session start that needs no query. `memoryking recall --project P --start [--task T]` and the session-start hook (when no `--query` is given) print the mandatory constraints for the session's bindings, the project's pins, the task's latest checkpoint (objective, next actions, what not to repeat) and the most recent decisions (claims accepted in the last 14 days and the newest observations whose source is `decision`, `instruction` or `user`), within the token budget, with the usual receipt, permissions and holds, and a plain statement when nothing is recorded. `memoryking pin add|remove|list` (admin or reviewer; a journaled policy decision) keeps an accepted claim or an observation in it. The lean `recall` still needs a query.

### Retrieval

- Questions that carry time are understood. "What did we decide last week", "yesterday's failure", "before the March release", "in 2025", "three days ago", "since March 3" and "between January and March 2025" (English, UTC, no model) are resolved against the briefing's reference instant, their words are no longer searched as words, and records observed in the range (or claims valid in it) are raised by a bounded share of the best score. Nothing is filtered unless the caller passes the new `time_range` argument (`from_ms`/`to_ms`) or `memoryking recall --from/--to`; the receipt's trace has a `time_v1` stage with what was understood and any ambiguity. On the pooled LongMemEval oracle set the `temporal-reasoning` session recall at eight rose from 0.729 to 0.774 and the overall figure from 0.812 to 0.824.
- Reindexing no longer holds a corpus-sized transaction. `memoryking reindex [--project P] [--wait]` and `python -m memoryking.shared reindex ... [--wait]` start the rebuild into the current lexical configuration; the starting call does constant work (about 0.3 s at 100,000 observations; it was 4.1 s) and the projection jobs are reset in batches alongside the index rewrite, resumable from the stored cursor. `status` and `doctor` show percent complete and an estimate. A shared tenant advances an unfinished rebuild between requests, not only hourly.
- Retrieval quality is now measured in ways that can fail. `tools/evidence_recall.py` reports recall_any and recall_all at 5 and 10 and mean reciprocal rank at session and turn level, in the pooled setting or per question (`--no-pool`, the setting other systems publish for `longmemeval_s`); the check gates a committed 72-question sample (12 per question type, from LongMemEval under its MIT licence) instead of a three-question one that could not fail, and `--compare BASELINE.json` prints every metric's and question type's change and exits non-zero past a tolerance. `lexical-v2` measures session recall_any@5/@10 0.810/0.864 on the pooled oracle set and 0.924/0.942 per question on the full `_s` file. Answer-turn recall now counts only the question's own answer turns (it used to count any question's in the pooled set), and the harness asks for a 65,536-token budget so recall at ten is not cut by the briefing budget. `tools/stale_facts_benchmark.py` measures whether a corrected fact is returned, and ranked above the stale one, after a newer capture, a memory-file edit or a replaced accepted claim (the current statement is returned in every case but ranked first in 0.37 of them); `tools/scale_regression.py` measures capture, drain, briefing, status, reindex, backup and restore at 20,000 and 100,000 observations against budgets, and runs at 20,000 in the clean-checkout job. See the [reference](docs/reference.md#retrieval-quality-gate).
- Lexical ranking weighs word rarity and length, matches word forms, picks candidates by informativeness and breaks ties deterministically. Before: a note was scored by the fraction of query words it contained, "retry" did not find "retries", a note with two common words outranked the note with the one distinctive word, a note holding all three query words was missed when each word alone had hundreds of newer matches, equal scores came back in random-id order (a stale fact as often as its correction) and a 20-term query cost 62, 246 and 510 ms at 1,000, 10,000 and 20,000 observations. Now: a deterministic English suffix stemmer (never applied to words with digits or underscores, non-ASCII words, or anchors) and a real stop list are applied identically at index and query time on both backends; the score is a BM25-style weighting in millionths from per-project statistics kept at capture, purge and reindex; candidates are the records holding every query word, then fewer, rarest words first, newest first inside a step, with the full authorization filter before any limit; and equal scores order by authority, then newest recorded, then reference. Index text is normalised to plain tokens so SQLite and PostgreSQL return the same ordered list for paths, symbols and tickets. Receipts name the configuration (`lexical-v2`); a replay returns stored bytes. The retrieval benchmark gains four labelled cases (word forms, rarity, crowding, tie order) in its gate. SQLite schema 16, shared schema 11, shared archive schema 9 and SQLite backup schema 11 add the statistics tables. **Upgrade:** an existing store keeps working with the previous ranking (`lexical-v1`) until `reindex` rebuilds its lexical index in resumable batches that do not block captures; `status` and `doctor` report the state. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#lexical-index-and-upgrading) · [Design](https://github.com/jamesking-us/memoryking/blob/main/docs/design.md#how-lexical-ranking-works)

- A briefing quotes the passage that answers, shows each fact once and separates reviewed from unreviewed. Before: a 25 KB observation whose one relevant sentence sat in the middle was quoted from its first 4,096 bytes (cut around the first occurrence of any query word, sometimes mid-word) and ranked below short notes because length was judged on the whole capture; five notes that differed only by a run number came back as five items, the same sentence on two days as two identical items, and both versions of an edited memory file were listed; accepted claims and the observations they cite shared one `## Guidance` list. Now: a long observation (over 4,096 bytes) is read as passages (rule `passages-v1`: about 1,000 characters, cut after sentences and paragraphs, never inside a code or path line; computed when needed, nothing stored) and quoted by the best one (plus neighbours that score nearly as well, on word boundaries, within 4,096 bytes, with exact byte offsets that `fetch` returns); an observation of more than six passages scores as the larger of its whole-text score and its best passage's, and every other observation scores exactly as in `lexical-v2` (no reindex, no new configuration, no schema change). Duplicates (same text after case and whitespace, or at least eight words that differ only by numbers, with the same anchors and negations) collapse to the newest record's text with `also_recorded_in`, versions of one file to the newest with `supersedes`, and observations an accepted claim cites to the claim (`evidence_not_repeated`) unless they add text; all are additive packet fields and every collapsed record stays a dependency of the receipt. The Markdown shows `## Accepted knowledge` and `## Unreviewed observations` separately with the recorded time to the minute. The recall harness counts the records an item stands for as cited. The retrieval benchmark gate gains a long-document case (quote contains the answer, `fetch` of its range returns it exactly), a duplicate case and a versions case. [Design](https://github.com/jamesking-us/memoryking/blob/main/docs/design.md#how-lexical-ranking-works) · [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#current-limits)

### Operations

### Concurrency and durability

- Briefings no longer serialize a tenant. On the shared profile a briefing and a capture take the tenant gate shared and a policy change, purge or restore still takes it alone (queued ahead of later requests, so a stream of briefings cannot starve a revocation). Before: every briefing held the gate exclusively for its whole run, so concurrent agents queued and the excess failed after five seconds. The query embedding and the reranker run with no gate or store lock held, after which the briefing decides afresh (new evaluation instant, policy and history read again). A briefing's candidate rows and holds are read in batches and a principal's read grant once per project, which also makes a single briefing several times faster on the shared profile.
- Reads that change nothing are no longer durable writes. A request that committed no row (a status read, a grants listing) writes no control anchor and takes no commit serial, and writers whose commits precede one anchor write share it, each acknowledging only after it is durable; every committing request, receipts included, is still anchored before its bytes are released. `serve --anchor-interval-ms N` (local and shared, off by default) is an explicit opt-in to writing the commit serial and clock of a request that moved no position up to N ms late; the cost is that a rollback of only the last N ms of receipts, and a clock regression under N ms across a restart, are not detected. The shared service checks a pooled connection's role and durability once and then every five seconds, resets and configures it in fewer round trips, and an MCP tool call reuses the one context decision its HTTP request already made instead of two or three more.

### Fixes

- The TypeScript client asks the shared MCP endpoint for the full tool profile by name (`?profile=full`), since it depends on the full tool names and canonical-JSON replies; after the endpoint's default became the lean profile its calls failed with `unknown_tool`. The shared-service JavaScript tests need PostgreSQL and so were skipped where it cannot start; [CONTRIBUTING](https://github.com/jamesking-us/memoryking/blob/main/CONTRIBUTING.md) now lists them with the PostgreSQL-dependent checks.
- Tables that only grow are released, and the scans over them no longer grow with them. Finished jobs behind the projection frontier are deleted (the newest 512 stay; a reindex or restore creates the jobs it needs from the event history), artifact tombstones go 30 days after they expired, feedback and shadow experience records older than a year that nothing names lose their bodies, and above 80 percent of the checkpoint bound an ordinary stream keeps its newest 32 revisions (a stream that released revisions reports `history_complete: false`; plans keep everything). Events, idempotency tombstones and operation intents stay: they are history. A purge finds the receipts that list its observation through a join table instead of scanning a JSON column, and new indexes cover expiry, the as-of frontier, the harness candidates, evidence spans and purge. Measured on SQLite with 1,000,000 rows per table: the per-request expiry went from 55 ms to about 1 ms, the artifact-room check from 109 ms to under 1 ms, the as-of frontier from 109 ms to under 1 ms, the dashboard harness query from 365 ms to under 1 ms, the job grouping behind `status` and `/metrics` from 69 ms to 0.1 ms and `status` from 285 ms to 5 ms once the backlog is released (the backlog of a store that never released anything is cleared in bounded batches, each pass at most about 1.3 s, over about eight hourly passes at this size), and a purge from 1,009 ms to 232 ms end to end. SQLite schema 19, shared schema 14 (the migration fills the join table; the shared migration switches row-level security off for that one copy and back on).
- The shared service's retention has a thread of its own. It used to run inside whichever write request came first each hour, so a tenant with no write traffic was never cleaned and a failure was swallowed. A housekeeping thread now visits every tenant at start and then hourly, logs each failure (error type and code only) and keeps going, and waits a bounded time for a pool connection so a busy pool delays rather than starves it.
- Backups no longer stop the store. The store lock is held only to snapshot the database and list the live blobs; blob files, which are immutable and named by their hash, are copied afterwards while requests run, each hashed as it streams and fsynced once. A backup hard-links the blobs the previous one holds after verifying their hashes, so a repeat backup copies only new files (13,000 blobs: the longest stall of the store lock fell from 47.9 s to 51 ms and a repeat backup from 26 s to 2.3 s on the same disk), and scheduled backups run on a maintenance thread instead of the thread that accepts connections. A shared backup fences the tenant only while its snapshot is established, not for the whole copy (the docs said "briefly"; it was the whole copy). Restore streams the database and blobs instead of reading them into memory.
- Blob files are sharded by hash prefix (`blobs/<tenant>/ab/<hash>`). A store from an earlier release keeps working with the flat directory and the daemon moves files over in small atomic steps; backups and archives in either layout restore. Purge deletes its own blob file when no other observation names the same content instead of listing the whole directory and loading every hash, and a start sweeps only after an interrupted purge; `memoryking gc` remains the explicit full sweep (the shared service runs it daily on its housekeeping thread).
- Tool-operation records no longer grow the control journal, and a copied control tree cannot serve the same tenant by accident. Before: every intent and transition was appended to the one journal that is verified in full at every start and never compacted, about 3.9 MB per 1,000 operations. Now: they go to their own hash-chained operations log (`CONTROL/operations/`), checked against the anchor on every use, whose old segments are dropped once a retained backup holds them and every operation in them is resolved; consumed identities are kept for ever in a hash-committed index, and with no backup nothing is dropped. A lease in the database (`{holder, renewed_ms}`, holder from `--instance-id` or the control directory's device and inode) co-holds across processes of one tree, refuses another holder with `control_lease_held` until 60 seconds after its last renewal, renews at most every 15 seconds and is reset by a restore; hosts that do not share a volume must set the same `--instance-id`. Operation records already in a journal stay valid and keep replaying from it. Migrated in place: SQLite schema 19, shared schema 14, shared archive schema 11, SQLite backup schema 13 (older backups still restore). The shared worker role only reads the lease; it compares and leaves claiming and renewal to the runtime role. Delegated writes now record who they were for: events (both profiles) and receipts (shared) have a nullable `on_behalf_of`, shown in the team activity, timeline and audit export. Not done, by decision: verifying only the journal tail at a cold start, and any way to skip a journal record.

### Memory health report

`memoryking health --project P`, the **Memory health** section of the dashboard's Jobs & health view, and the `inspection` action `health` say whether memory is paying for itself, from records the store already keeps: the helpful share of rated feedback, briefings that found no relevant memory, observations no retained delivery ever carried, claims that lost their evidence to a purge or were replaced, and how long the oldest proposal has waited for review. Counts and ratios only, no text and no principal, fixed documented thresholds, five one-line signals. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#memory-health) · [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#is-memory-paying-for-itself-the-health-report)

### Memory as files: the Anthropic memory tool and the Markdown vault

`memoryking.memory_tool.MemoryTool` answers all six commands of Anthropic's `memory_20250818` tool from a project, so any Claude API agent can use MemoryKing as its memory backend without prompt changes: directories are sources, files are versioned observations with their provenance on top, claim files are proposals that wait for review, every view is a receipted fetch, and delete or rename are purges that need an administrator. `memoryking vault export|import` writes the same files to a private directory and reads them back as new versions and proposals. Both rest on a new read-only `inspection` action, `catalog`. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#memory-as-files-the-anthropic-memory-tool-and-the-markdown-vault) · [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#memory-tool-and-vault)

### Proposal drafts from repeated evidence

`memoryking draft-proposals --project P`, the `knowledge` action `draft` and a **Draft proposals** button in the Review view fill the review queue without a model: a name that several independent observations share (a path, a ticket, a host, a symbol, an error code, or failing that a rare term) becomes an ordinary proposal citing one evidence span per supporting observation. Nothing it drafts becomes knowledge until a reviewer accepts it. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#drafts-that-never-accept-themselves) · [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#proposal-drafts)

### Entity anchors, opt-in salience and a judge-free recall harness

Exact names in a capture (paths, symbols, tickets, URLs, hosts, error codes) are anchored at capture and found exactly at retrieval; the memory graph links records that share one. Briefings may ask for `salience: "on"` (`recall --salience`), which nudges the order by the caller's own past deliveries and helpful votes and ranks never-used records after active ones without deleting anything. `tools/evidence_recall.py` measures recall against a pooled oracle with no model as judge, and `tools/check.py` gates on a committed sample. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#anchors-the-exact-names-memory-hangs-on) · [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#anchors-and-salience)

### As-of briefings

`brief` accepts `as_of_ms` (`recall --as-of DATE`, the lean tool's `as_of`, the dashboard's **As of** field): the briefing is assembled from the project as it stood at that instant, and its receipt replays byte for byte. ### Source trust

`memoryking trust set|list|held|release` and the Review view hold every capture from a source marked untrusted: recorded, replayable and backed up, but invisible to every read, briefing, graph, resume and review until an admin releases it. ### Influence report

`memoryking influence OBSERVATION --project P` and the **Where did this go** view list every claim, checkpoint, handoff, summary and retained delivery built on one observation, and the principals those reached, from the same dependency graph a purge follows.
