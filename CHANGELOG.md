### Security

- A delegated token now acts for the principal who issued it, not for the principal it names. Before: `delegate` returned a token whose acting principal was the named subject, so anyone holding `read` on a project could mint a token that read what only that agent could read and wrote captures and checkpoints attributed to it, with no trace of who acted. Now the token is the issuer with a narrower scope (the named project and capabilities, never more than the issuer holds at the time of each use), so reader lists, checkpoint ownership, hand-off recipients, receipts and the event actor all name the issuer. **Breaking:** delegated tokens issued before this release are refused with the new `delegation_superseded` code; the issuer delegates again. The shared profile only; the local profile has no delegation. See the deployment guide.
- Credentials can be rotated, and a revoked principal's old credential no longer comes back. A credential used to be derived only from the store, history, tenant and principal, so revoking a principal and granting it again returned the same token, and a leaked credential could not be invalidated short of abandoning the principal's name or restoring the store. Each principal now has a credential generation, kept with its grant state, carried in the signed credential and checked at every authorization; a credential whose generation is not the current one is refused with `credential_replaced`. Revoking a principal's last grant and `credential issue --rotate` (in the shared profile, `"rotate": true` in the `grant` arguments) advance it, in the signed control journal like every policy change, so a restore replays it and retired views are retired as for any revoke. Re-issuing an unchanged grant without `--rotate` still returns the current credential, and every credential issued before this change keeps working until its principal is revoked or rotated. A delegated credential stops working when either its issuer or its subject is rotated. `memoryking credential rotate-owner` replaces the owner credential file offline (stop the daemon first), and `memoryking.shared rotate-owner` does the same for the shared profile's operator credential without stopping the service; the new credential is durable before the old one stops working. A shared restore hands the recovery admin a credential at its current generation (before, one whose generation was above 0 came back refused), `end-maintenance` refuses a rotated-away credential, and archives from before generations restore with every generation at 0. Grant expiry (`--expires`) was already enforced against the store clock at every authorization and is unchanged. SQLite schema 15, shared schema 10 and backup schemas 10 (SQLite) and 8 (shared) add the generation table. [Deployment](https://github.com/jamesking-us/memoryking/blob/main/docs/deployment.md#rotating-credentials)

### Review, corrections and the session start

- Proposals can be reviewed from the terminal and from chat. `memoryking review list|show|accept|reject --project P` pages the waiting proposals oldest first with their id, text, method, support count and the sentences they cite, and accepts or rejects them through the existing `review` action with your own credential (so the `review` capability, or `policy` for a constraint, applies exactly as before); `review accept --as constraint` files and accepts a constraint with the same words and evidence. Before, only the dashboard or a raw call with six required fields could review, and a reason with spaces was refused because the field is an identifier: `review` now takes a free-text `note` beside the identifier `reason`, and the dashboard form has a note field. The lean profile gains `propose` (an agent files a claim with the observations it rests on; it is a proposal, never accepted knowledge) and `confirm` (records the user's accept or reject with their quoted words). `confirm` works only when the operator starts the bridge with `--allow-chat-review` and the credential holds `review`, only for knowledge, and the decision is recorded as confirmed in chat with the relaying principal and the proposer named, so a reviewer can audit and revert it. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#reviewing-and-correcting-memory)
- Memory can be corrected. `capture --supersedes ID` (and `supersedes` on the wire and on the lean `remember`) links a new observation to an earlier one the caller can read; the old record stays untouched as evidence, but briefings leave it out while the replacement is visible to the reader, and show it alone when the replacement is unreadable, held or purged. The lean `correct` saves a replacement; the lean `forget` files a retirement request and cannot delete: the record is marked "retirement requested" for other readers and hidden from the requester's own briefings until an admin approves (a journaled purge with the usual dependency follow-through) or a reviewer or admin dismisses it, from `review list`, `review retire-approve|retire-dismiss` or the dashboard's Review view. SQLite schema 17, shared schema 12, shared archive schema 10 and SQLite backup schema 12 add the link, request and pin tables.
- A session start that needs no query. `memoryking recall --project P --start [--task T]` and the session-start hook (when no `--query` is given) print the mandatory constraints for the session's bindings, the project's pins, the task's latest checkpoint (objective, next actions, what not to repeat) and the most recent decisions (claims accepted in the last 14 days and the newest observations whose source is `decision`, `instruction` or `user`), within the token budget, with the usual receipt, permissions and holds, and a plain statement when nothing is recorded. `memoryking pin add|remove|list` (admin or reviewer; a journaled policy decision) keeps an accepted claim or an observation in it. The lean `recall` still needs a query.

### Retrieval

- Retrieval quality is now measured in ways that can fail. `tools/evidence_recall.py` reports recall_any and recall_all at 5 and 10 and mean reciprocal rank at session and turn level, in the pooled setting or per question (`--no-pool`, the setting other systems publish for `longmemeval_s`); the check gates a committed 72-question sample (12 per question type, from LongMemEval under its MIT licence) instead of a three-question one that could not fail, and `--compare BASELINE.json` prints every metric's and question type's change and exits non-zero past a tolerance. `lexical-v2` measures session recall_any@5/@10 0.810/0.864 on the pooled oracle set and 0.924/0.942 per question on the full `_s` file. Answer-turn recall now counts only the question's own answer turns (it used to count any question's in the pooled set), and the harness asks for a 65,536-token budget so recall at ten is not cut by the briefing budget. `tools/stale_facts_benchmark.py` measures whether a corrected fact is returned, and ranked above the stale one, after a newer capture, a memory-file edit or a replaced accepted claim (the current statement is returned in every case but ranked first in 0.37 of them); `tools/scale_regression.py` measures capture, drain, briefing, status, reindex, backup and restore at 20,000 and 100,000 observations against budgets, and runs at 20,000 in the clean-checkout job. See the [reference](docs/reference.md#retrieval-quality-gate).
- Lexical ranking weighs word rarity and length, matches word forms, picks candidates by informativeness and breaks ties deterministically. Before: a note was scored by the fraction of query words it contained, "retry" did not find "retries", a note with two common words outranked the note with the one distinctive word, a note holding all three query words was missed when each word alone had hundreds of newer matches, equal scores came back in random-id order (a stale fact as often as its correction) and a 20-term query cost 62, 246 and 510 ms at 1,000, 10,000 and 20,000 observations. Now: a deterministic English suffix stemmer (never applied to words with digits or underscores, non-ASCII words, or anchors) and a real stop list are applied identically at index and query time on both backends; the score is a BM25-style weighting in millionths from per-project statistics kept at capture, purge and reindex; candidates are the records holding every query word, then fewer, rarest words first, newest first inside a step, with the full authorization filter before any limit; and equal scores order by authority, then newest recorded, then reference. Index text is normalised to plain tokens so SQLite and PostgreSQL return the same ordered list for paths, symbols and tickets. Receipts name the configuration (`lexical-v2`); a replay returns stored bytes. The retrieval benchmark gains four labelled cases (word forms, rarity, crowding, tie order) in its gate. SQLite schema 16, shared schema 11, shared archive schema 9 and SQLite backup schema 11 add the statistics tables. **Upgrade:** an existing store keeps working with the previous ranking (`lexical-v1`) until `reindex` rebuilds its lexical index in resumable batches that do not block captures; `status` and `doctor` report the state. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#lexical-index-and-upgrading) · [Design](https://github.com/jamesking-us/memoryking/blob/main/docs/design.md#how-lexical-ranking-works)

### Clients

- Client libraries for the everyday five operations. The Python `LocalClient` and `SharedClient` gain `remember`, `recall`, `save_progress`, `resume` and `hand_off`, thin typed wrappers over the code the lean MCP tools of the same names run (same authorization, receipts, idempotency and budgets), returning small dataclasses with the full reply as `.raw`. `MemoryKing.connect()` builds a client from a profile or the `MEMORYKING_*` variables the command line reads (and `MEMORYKING_URL`, `MEMORYKING_TENANT` for a shared service). `AsyncLocalClient` and `AsyncSharedClient` offer the same surface with no new dependency; they run the synchronous client on worker threads. A new `@memoryking/client` package (`packages/client`, ready to publish, not published) is a zero-dependency ES-module TypeScript client with `remember`, `recall`, `saveProgress`, `resume` and `handOff` against the shared service, and `recall` against a local daemon's loopback agent endpoint, which serves retrieval only; failures throw `MemoryKingError` with the service's `code` and `hint`. The clean-checkout contracts-package job now also packs the client and runs it from an installed tarball. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#using-the-client-libraries)
- Python 3.13 is supported for the core install. `requires-python` is now `>=3.12,<3.14`; the hash-pinned lock files already install on 3.13, and the test suite was run on it. Python 3.14 is not claimed. Windows remains unsupported; the reference now lists every POSIX-only dependency and what a port needs. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#runtimes-python-versions-and-windows)

### Fixes

- Tool-operation records no longer grow the control journal, and a copied control tree cannot serve the same tenant by accident. Before: every intent and transition was appended to the one journal that is verified in full at every start and never compacted, about 3.9 MB per 1,000 operations. Now: they go to their own hash-chained operations log (`CONTROL/operations/`), checked against the anchor on every use, whose old segments are dropped once a retained backup holds them and every operation in them is resolved; consumed identities are kept for ever in a hash-committed index, and with no backup nothing is dropped. A lease in the database (`{holder, renewed_ms}`, holder from `--instance-id` or the control directory's device and inode) co-holds across processes of one tree, refuses another holder with `control_lease_held` until 60 seconds after its last renewal, renews at most every 15 seconds and is reset by a restore; hosts that do not share a volume must set the same `--instance-id`. Operation records already in a journal stay valid and keep replaying from it. Migrated in place: SQLite schema 18, shared schema 13, shared archive schema 11, SQLite backup schema 13 (older backups still restore). Delegated writes now record who they were for: events (both profiles) and receipts (shared) have a nullable `on_behalf_of`, shown in the team activity, timeline and audit export. Not done, by decision: verifying only the journal tail at a cold start, and any way to skip a journal record.
- The shared service's MCP endpoint answered every `memory_brief`, `memory_resume`, `memory_checkpoint` and `memory_handoff` call with an internal error, and `SharedClient` could not call `tool()` for them, because their per-request clients had no session bindings. Both now default to the empty binding, and `SharedClient` accepts `bindings`. A `SharedClient` error now carries the service's `hint`, like the local client's.
- The control journal no longer costs more on every request as it grows. The shared service built a control handle per request, so each transaction read and HMAC-verified the whole journal under the tenant gate (about 0.3 s at 10,000 records, 3.3 s at 100,000, against a five-second deadline), and a local append re-read and re-hashed the whole file (about 0.3 s at 100,000). A process now keeps the verified prefix per control tree and verifies only what was appended since, comparing the anchor on every call, so rollback, torn-tail and damage detection are unchanged; a shared request costs under 1 ms and a local append 1 to 3 ms at any size, the shared service verifies every tenant once in the background at start, and a cold start still verifies everything. [Deployment](https://github.com/jamesking-us/memoryking/blob/main/docs/deployment.md#journal-cost-and-records-that-fail-to-apply)
- A journal record that takes longer than a request no longer fences a tenant for good. Unapplied records were applied inside the next request's five-second decision, so a long purge made every write fail with `release_expired` and every read with `journal_replay_required`. They are now applied before the request, one record per transaction without the request budget, with the anchor advancing after each commit, and a local purge that ran out of budget is applied at once instead of stopping the daemon. `memoryking journal pending` (local, offline) and `memoryking.shared journal-pending` list records that still cannot apply with their sequence, kind, tenant and last error code and no content; no record is ever skipped. [Deployment](https://github.com/jamesking-us/memoryking/blob/main/docs/deployment.md#journal-cost-and-records-that-fail-to-apply)
- The local daemon accepts connections while all eight workers are busy. A connection that finds no free worker now waits on its own thread (up to 16 waiting at once, each for at most five seconds, together rather than one after another) and then receives `service_busy`; connections beyond that bound receive it at once. Before, the accept thread itself waited five seconds per rejected connection. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#current-limits)
- A wall clock that jumped forward and was corrected is now diagnosable. `memoryking doctor` has a `clock` check that says how far ahead the store's recorded time is, the `clock_untrusted` hint names the cause, and the deployment guide has a Clock recovery procedure. The rollback protection is unchanged. [Deployment](https://github.com/jamesking-us/memoryking/blob/main/docs/deployment.md#clock-recovery)
- The shared service no longer reveals which tenants exist. A request for an unknown tenant now answers 400 `invalid_token`, the same as a bad credential for a known tenant, instead of a 503 with an error log. A lock timeout, statement timeout, deadlock or serialization failure inside a request now answers `service_busy` with 429 and a warning log (SQLSTATE only) instead of 503 `service_unavailable` with an error log; a saturated pool still answers 503. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#current-limits)
- Shared restore no longer trusts the role name alone. It refuses a `mk_migration` role that is a superuser or has `BYPASSRLS`, and the statements in restore, shared result expiry and optional-state retirement now carry an explicit tenant predicate instead of relying on row-level security. Local restore stays store-wide by design. [Deployment](https://github.com/jamesking-us/memoryking/blob/main/docs/deployment.md#shared-postgresql)
- A database that is ahead of its control journal is refused. Opening a local or shared store now fails closed with `journal_rollback` when the database has applied more journal records than the verified journal holds (a lost journal tail or a mismatched control tree), instead of skipping the missing records silently. Control files, the journal, the anchor and backup files use `F_FULLFSYNC` where the platform has it. [Deployment](https://github.com/jamesking-us/memoryking/blob/main/docs/deployment.md#backup-and-recovery)
- `memoryking hooks install` accepts the repeatable `--binding key=value` flag and writes it into each installed hook command, so hooks on a host that does not pass its environment through resolve scoped constraints as the MCP bridge does. Re-running with the same arguments changes nothing, a different set replaces the entries in place, and `--remove` still removes them. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#hooks-that-load-and-save-memory-by-themselves)
- A resume blocked only by unresolved constraint applicability now shows the whole of the caller's own state: the checkpoint it already returned plus the stream's operations (with `operations_truncated`) and the latest summary the reader may see, rendered in the Markdown as in an ordinary resume, so an agent sees that an earlier tool effect is still uncertain. The packet is still `blocked` with constraints unresolved, and adding a memory from it is still refused. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#resume-status)
- A reviewer can list procedures in a project with more than 256 procedure revisions. The reviewer listing (`diagnostic` on the experience `query`, used by the dashboard's Review view) now returns the newest revisions, at most 256 and fewer when large bodies would exceed the response limit, with `truncated` and `next_before_position`, and takes `before_position` to continue with the next older page, instead of returning `procedure_resolution_incomplete`. Briefings still resolve active procedures completely or block. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#current-limits)
- The lean `recall` and `resume` tools advertise the budget the contracts accept. Their `budget` maximum was 100,000 tokens while `max_output_tokens` is capped at 65,536, so a model following the schema could send a value that was refused; the advertised maximum is now 65,536 and the stdio bridge test sends it.
- A scoped constraint no longer locks simple readers out. The lean tools, the CLI and the hooks accept session bindings once instead of sending empty ones on every call: `--binding key=value` (repeatable; on the stdio bridge, `recall`, `summarize` and `hook`), `MEMORYKING_BINDINGS` (`environment=prod,role=implement`, or a JSON object), and a `bindings` entry in a store profile (`profile add --binding`), all validated against the selector fields. A blocked briefing or resume now names the missing binding fields (`unbound_fields`, and "Missing binding fields" in the Markdown), never a constraint's text, and the `applicability_unknown` hint says how to supply them. A resume blocked only by unresolved constraint applicability still returns the checkpoint the caller may read, with the constraints marked unresolved and the packet still blocked, so lean `save_progress` keeps working and a model is still never fed an unresolved packet. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#session-bindings-telling-the-tools-where-you-work)
- Checkpoints, hand-offs, hand-off views and experience records no longer count every row they ever wrote. Each bound (4,096, 4,096, 4,096 and 10,000) counts live rows only and appears under `status` capacity with `checkpoint_bytes`; superseded, cancelled, expired, retired and purged rows stop counting, so a restored tenant that was full can checkpoint again. Old revisions of an ordinary checkpoint stream (beyond the latest and the 129 before it) are retired to tombstones by housekeeping and at write time, unless a retained briefing, summary or live hand-off names them; plan revisions are kept. Hand-off views without a retained briefing and superseded experience revisions beyond the newest eight are deleted unless a record or ranking configuration depends on them. The capacity hints and the reference table now describe how each bound releases.
- Backups work at any store size. The signed backup manifest no longer lists every blob (which failed past about 13,000 observations); it commits to a separate `blob-index` file by hash, and restore verifies the index and every blob. Backups from earlier releases still restore. A scheduled backup that fails for any reason now removes its partial directory and records the failure.
- Captures no longer slow down or stall as the store grows. A new `jobs(tenant,position)` index (SQLite schema 14, shared schema 9, applied by the normal migrations) serves the job-frontier lookup, the drain idle probe is per tenant, a drain pass stops before the transaction deadline, and jobs reset by a `reindex` or restore no longer count toward the 1,000-job capture limit.
- Accepted knowledge and mandatory constraints stay in briefings however many proposals a project holds. The registry bound of 256 now counts only revisions accepted at the queried position, so unreviewed drafts (for example daily `draft-proposals` runs), rejected and deprecated revisions never block a briefing; more than 256 accepted revisions still blocks rather than dropping any silently. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#current-limits)
- A long task stays resumable. Resume, summaries, hand-off and the task snapshot return every unresolved operation plus the newest resolved ones up to 32 in all, and report `operations_truncated: true` when older resolved history was left out, instead of failing with `operation_limit` on a task's 33rd recorded effect. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#what-the-host-must-do) · [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#current-limits)
- `memoryking draft-proposals` works against a running daemon; the socket contract now admits the `draft` action it sends. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#drafts-that-never-accept-themselves)
- The lean `save_progress` and `resume` tools behave as described: a save with `findings` is accepted, a later save keeps the next actions, failed attempts, blockers and constraints it does not repeat, and resuming a lean checkpoint no longer reports `recovery_reconciliation_required` merely because defaulted sections were filled in (it still does for a real reconciliation gap). [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#lean-profile-for-any-host)
- Session hooks save what matters and nothing secret. They capture user turns and tool errors as well as assistant text, never read tool-call inputs or successful tool results, replace common secret shapes (keys, tokens, private-key blocks) before capture and report how many were scrubbed (best effort, not a guarantee), and keep the newest part of the transcript tail. Hook checkpoints go to their own `<task>--mkhook` stream with a retry key per hook, so an agent's own checkpoint is never overwritten and `pre-compact` followed by `session-end` both succeed; session start resumes both streams. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#hooks-that-load-and-save-memory-by-themselves)
- `memoryking trust set` without `--key` works for a glob source such as `scraper-*` (and for the project `*`): when the default key `trust-PROJECT-SOURCE-LEVEL` would contain characters a key may not, it derives a stable one from a hash of the rule. Keys for plain sources are unchanged, so earlier calls still replay. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#source-trust)
- A reviewer can list proposals in a project with more than 256 knowledge revisions. The reviewer listing (`diagnostic` on the knowledge `query`, used by the dashboard's Review view) now returns the newest 256 revisions of any state with `truncated` and `next_before_position`, and takes `before_position` to continue with the next older page, instead of returning `knowledge_resolution_incomplete`; the Review view says when the listing is truncated. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#current-limits)
- A request sent right after the daemon starts could be refused with `denied` or `internal_error`. The daemon's idle-summary scan ran on its service thread without the store lock, sharing the connection with request threads; it now holds the lock.

## 0.1.0a3 (2026-11-03)

The ten items of the November 2026 gap analysis, in one pre-release. Install with `pip install --pre memoryking==0.1.0a3`; the local-daemon image is `ghcr.io/jamesking-us/memoryking:0.1.0a3`.

### Optional local reranker

A pinned cross-encoder (`cross-encoder/ms-marco-MiniLM-L6-v2`, Apache 2.0) installed with `python -m memoryking.model_install --model reranker` and loaded with `serve --reranker-model DIR` reorders the top 16 fused candidates of a briefing that asks for it (`rerank: "on"`, `recall --rerank`, lean `recall(rerank=true)`). Off unless requested, no egress, never admits or removes a record; each item reports `rerank_score_ppm`, the trace reports the stage, and the recall harness measures it with `--reranker-model`: on the pooled LongMemEval oracle set, session recall at eight 0.576 to 0.682 and MRR 0.477 to 0.633 for about 0.7 s more per briefing. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#local-reranker) · [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#reranking-the-shortlist-with-a-local-cross-encoder)

### Memory health report

`memoryking health --project P`, the **Memory health** section of the dashboard's Jobs & health view, and the `inspection` action `health` say whether memory is paying for itself, from records the store already keeps: the helpful share of rated feedback, briefings that found no relevant memory, observations no retained delivery ever carried, claims that lost their evidence to a purge or were replaced, and how long the oldest proposal has waited for review. Counts and ratios only, no text and no principal, fixed documented thresholds, five one-line signals. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#memory-health) · [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#is-memory-paying-for-itself-the-health-report)

### Memory as files: the Anthropic memory tool and the Markdown vault

`memoryking.memory_tool.MemoryTool` answers all six commands of Anthropic's `memory_20250818` tool from a project, so any Claude API agent can use MemoryKing as its memory backend without prompt changes: directories are sources, files are versioned observations with their provenance on top, claim files are proposals that wait for review, every view is a receipted fetch, and delete or rename are purges that need an administrator. `memoryking vault export|import` writes the same files to a private directory and reads them back as new versions and proposals. Both rest on a new read-only `inspection` action, `catalog`. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#memory-as-files-the-anthropic-memory-tool-and-the-markdown-vault) · [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#memory-tool-and-vault)

### Proposal drafts from repeated evidence

`memoryking draft-proposals --project P`, the `knowledge` action `draft` and a **Draft proposals** button in the Review view fill the review queue without a model: a name that several independent observations share (a path, a ticket, a host, a symbol, an error code, or failing that a rare term) becomes an ordinary proposal citing one evidence span per supporting observation. Nothing it drafts becomes knowledge until a reviewer accepts it. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#drafts-that-never-accept-themselves) · [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#proposal-drafts)

### Entity anchors, opt-in salience and a judge-free recall harness

Exact names in a capture (paths, symbols, tickets, URLs, hosts, error codes) are anchored at capture and found exactly at retrieval; the memory graph links records that share one. Briefings may ask for `salience: "on"` (`recall --salience`), which nudges the order by the caller's own past deliveries and helpful votes and ranks never-used records after active ones without deleting anything. `tools/evidence_recall.py` measures recall against a pooled oracle with no model as judge, and `tools/check.py` gates on a committed sample. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#anchors-the-exact-names-memory-hangs-on) · [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#anchors-and-salience)

### As-of briefings

`brief` accepts `as_of_ms` (`recall --as-of DATE`, the lean tool's `as_of`, the dashboard's **As of** field): the briefing is assembled from the project as it stood at that instant, and its receipt replays byte for byte. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#as-of-briefings)

### Source trust

`memoryking trust set|list|held|release` and the Review view hold every capture from a source marked untrusted: recorded, replayable and backed up, but invisible to every read, briefing, graph, resume and review until an admin releases it. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#source-trust-holding-captures-you-do-not-yet-trust) · [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#source-trust)

### Influence report

`memoryking influence OBSERVATION --project P` and the **Where did this go** view list every claim, checkpoint, handoff, summary and retained delivery built on one observation, and the principals those reached, from the same dependency graph a purge follows. [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#influence-report)

### Host hooks

`memoryking hooks install` installs session hooks for Claude Code, Codex, Grok or any stdio host that load memory at the start of a session and save it before compaction and at the end; `memoryking hook` is the command they run, and captures from pytest or git use the same path. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#hooks-that-load-and-save-memory-by-themselves)

### Structured plans in the dashboard and the graph

Named plans with phases, prerequisites, completed steps and blockers, ported from the Codex line: `memory_plan` in the MCP catalog, plan listing and detail routes on the dashboard, plans beside checkpoints in Task activity, and plan nodes in the memory graph, which also gained zoom, pan and persistent selection. The file-backed development-record view was retired. [Agent guide](https://github.com/jamesking-us/memoryking/blob/main/docs/agent-guide.md#structured-plans) · [Reference](https://github.com/jamesking-us/memoryking/blob/main/docs/reference.md#dashboard-plans)
